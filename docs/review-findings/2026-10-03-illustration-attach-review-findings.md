## 1. 構造（単一責任）の指摘

### S1. 「新しい関係」を足したとき、既存の関数に責務が混ざった

**発生する状況**
既存の機能に、1つの新しい関係（ここでは「ノードにイラストがある」）を足すとき、新しい規則を、いちばん近い既存の関数の中に、そのまま書き足したとき。

**問題**
実装の直後（タスクごとのレビューは通った状態）で、次の混在が残った。
- `mapDocumentNode.ts`: ノードの各項目の検証に、イラストの検証（形式、寸法）と、高さの下限の規則が、同居した。変更理由が「保存形式」と「イラストの規則」の2つになる。
- `useIllustrationGeneration.ts`: 状態を React の状態に結び付ける処理に、「画像を取得し、縮小し、失敗の種類を分類する」という生成の手順そのものが、同居した。
- `IllustrationPanel.tsx`: 「どの表示を出すか」の判定（プレビュー、設定済み、なし）と、描画（DOM）が、1つの関数の中の条件分岐に混ざった。同じ `<img>` の記述も、2か所に重複した。
- `mapSvgNodes.ts` と `renderMapNodes.ts`: 1つの関数のループの中に、矩形、イラスト、テキストの生成が、並んで書かれた。

**原因（詳細）**
- 計画は、タスクを「テストできる単位」で切る。イラストの検証は、「保存形式を version 3 にする」という1つのタスクに含まれていたので、そのタスクの実装者は、その場で検証を書き足すのが最短だった。タスクの完了条件（テストが通る、仕様を満たす）には、「責務が分かれている」は含まれない。
- タスクごとのレビュー（仕様適合と品質）は、1つのタスクの差分だけを見る。後のタスクで、同じ関数に別の規則が積まれていくこと（`mapDocumentNode.ts` に高さの規則が加わる、など）は、1つのタスクの差分からは見えにくい。
- 既存のコードには、「重要度の正規化」を別ファイル（`mapDocumentNodeImportance.ts`）に分ける前例があった。しかし、前例に合わせるかどうかは、計画に書かれていなければ、実装者の判断になる。

**修正**
- 検証を `mapDocumentNodeIllustration.ts`、高さの下限を `nodeIllustration.ts` の関数に分けた（重要度の正規化と同じ形）。
- 生成の手順とエラーの分類を `services/illustration/illustrationGeneration.ts` に移し、フックは、状態と中断の制御だけを持つ。
- パネルの表示判定を純粋関数 `illustrationPanelView.ts`、画像の表示を `IllustrationImage.tsx` に分けた。判定は、状態の全組み合わせをテストできる。
- 描画と SVG の生成は、同じファイル内の非公開関数に分けた（ファイルを増やすほどではない）。式と加算の順序は、そのまま移した（B6、T6）。

**汎用的な教訓**
- 既存の機能に新しい関係を足したら、「この関数の変更理由は、いくつに増えたか」を確認する。計画の段階で、既存の前例（兄弟ファイル）に合わせる分割を書いておくと、実装者が迷わない。
- 単一責任の確認は、タスクごとのレビューとは別に、機能が全部できたあとに、まとめて行う。タスクをまたぐ重なりは、そこでしか見えない。
- 分割の効果が最も大きいのは、「純粋な判定」を「描画・副作用」から切り出すとき（テストが、全ての組み合わせを網羅しやすくなる）。

### S2. 型の置き場所が、依存の向きを逆にした

**発生する状況**
複数の層（フックと、純粋関数と、コンポーネント）が使う型を、最初にそれを作った層（フック）のファイルに定義したとき。

**問題**
純粋なドメインの関数（`illustrationPanelView.ts`）が、フックのファイルから型を import することになり、「純粋な関数は、副作用のある層に依存しない」という向きが逆になった。

**原因（詳細）**
- 型 `IllustrationGenerationState` は、生成フックが返す値の形として、最初にフックの中で定義された。
- その後、パネルの判定を純粋関数に切り出した（S1）とき、その関数が同じ型を必要としたので、フックのファイルから import した。型の移動は、リファクタリングの手順に含まれていなかった。
- 型だけの import は、実行時には影響がなく、lint も通る。そのため、テストでも見つからず、依存の向きという観点で見ない限り、気付かない。

**修正**
型を `types/illustrationGeneration.ts` に移した（フックからの再エクスポートはしない。import 元を全て直す）。既存に前例（`types/operationNotice.ts`）があった。

**汎用的な教訓**
複数の層で共有する型は、最初から `types/` に置く。リファクタリングで関数を切り出したときは、「切り出した先が、どこから import しているか」を確認する。

### S3. 分割しない判断も、根拠とともに残す

**発生する状況**
「責務が複数ある」という見た目の指摘（長い関数、複数の副作用を持つフック）に対して、分割するかどうかを判断するとき。

**問題**
分割すると、かえって、責務が散る、確認する範囲が広がる、新しい依存が生まれる、というケースがあった。

**原因（詳細）**
次の候補は、1つの目的の手順にまとまっていたので、分割しなかった。
- `useIllustrationTextures.ts`: 「実行環境（runtime）ごとに、テクスチャの読み込みと破棄を管理する」1つのリソース管理。参照（ref）、effect、状態更新が連携しているので、複数のファイルに分けると、連携が見えにくくなり、React Compiler の lint で確認する範囲が広がる。
- `illustrationThumbnail.ts` と `illustrationTextureLoader.ts` の、画像のデコード（3行）の重複: 戻り値が違い、共通化すると、描画の層（`components/map/pixi`）から `services` への新しい依存が生まれる。
- `isIllustrationDataUrl` を呼ぶ4か所（保存形式の読み込み、画像の設定、SVG への埋め込み、縮小の出力）: それぞれ別の信頼境界での検証で、判定の本体は1か所にある。意図的な多層防御として説明できる。
- `mapExportBounds.ts` の、イラストの有無による分岐: 浮動小数点の結果を変えないための、意図的な形（T6）。

**修正**
なし（判断の記録のみ）。

**汎用的な教訓**
「分割しない」と判断した場合は、理由を記録する。後から同じ指摘が出たときに、議論を繰り返さずに済む。分割の基準は、「変更理由が複数あるか」であって、「行数が多いか」ではない。

### S4. 単一責任の確認は、観点を変えて繰り返すと、見つかるものが変わる

**発生する状況**
単一責任の確認を、同じ観点（ファイルや関数の責務）で行ったとき。

**問題**
1回目は6件を見つけたが、依存の向き（S2）は、別の観点（層と依存の向き）で見て、初めて見つかった。3回目の観点（関数内の抽象度、テストの責務、エラー処理の置き場所、命名と配置、副作用の分離）では、新しい指摘はなかった。

**原因（詳細）**
1回目の観点は、「1つのファイル・関数が、いくつのことをしているか」だった。型の置き場所は、ファイルの内側からは見えず、「どの層が、どの層を参照しているか」という外側からの観点でないと、見つからない。

**修正**
観点を、ラウンドごとに変えた（1: ファイル・関数、2: 依存の向き・変更理由の軸・テスト・重複・公開 API、3: 関数内の抽象度・テストの責務・エラー処理・命名・副作用）。指摘が0件になったラウンドで打ち切った。

**汎用的な教訓**
繰り返す確認は、毎回、観点を変える。同じ観点の繰り返しは、同じ結果になる。打ち切りは、「観点を変えても、新しい指摘が出ない」ことで判断する（オーバーレイ型メニューの整理 P1 と同じ）。

## 2. 挙動（不具合）の指摘

### B1. 外部から来る画像のサイズを検証せず、デコードでメモリを使い尽くせた【Important】

**発生する状況**
利用者が他人から受け取ったデータファイル（JSON）をインポートしたとき。または、そのデータが、ブラウザの保存領域（localStorage）に書かれたあと、再び読み込まれたとき。データの中の画像（`illustration`）が、細工されている場合。

**問題**
検証は、「文字列の長さが 100,000 文字以下」と「画像の形式（jpeg、png、webp）の base64」だけだった。画像の縦横のピクセル数は見ていなかった。圧縮率の高い画像（単色など）は、小さなデータのまま、数万ピクセル四方を宣言できる。ブラウザは、画像を表示するとき、全体を展開する（縦×横×4 バイト）ので、数百 MB から GB 級のメモリが必要になり、タブが落ちる。しかも、データは自動保存されるので、アプリを開き直すたびに、同じ画像を読み込み、同じ失敗が起きる。利用者は、ブラウザの保存データを手で消すまで、アプリを使えない。

**原因（詳細）**
- 検証の目的を、「データが壊れていないか（形式）」と「保存領域を使い切らないか（長さ）」の2つだと考えていた。長さの上限は、保存容量（約5MB）の観点で決めたもので、「展開後の大きさ」を制限するものではなかった。
- 「データの大きさ」と「展開したときの大きさ」は、別の量である。圧縮された画像では、両者の比が、数千倍から数万倍になりうる。
- 検証を入れた時点では、画像は、アプリ自身が縮小して作るもの（128px の JPEG）だけだと考えていた。しかし、保存データを読み込む入口は、アプリが作るデータだけでなく、手で編集したファイルや、他人から受け取ったファイルも受け付ける。**信頼境界（外から来たデータが、内側のコードに入る場所）では、「アプリが作るはずの値」ではなく、「作れる全ての値」を想定する必要がある。**
- タスクごとのレビュー、最終レビュー、リファクタリングのレビューは、すべて、この点を見逃した。これらは、「仕様どおりに実装されているか」と「コードの品質」を見るレビューで、「外から来たデータが、何を引き起こせるか」という攻撃者の観点を、明示的には含んでいなかった。マージ前の全体レビューで、観点に「セキュリティ（巨大データ、信頼境界）」を、具体的に挙げて、初めて見つかった。

**修正**
- 保存データから読み込む画像は、JPEG だけを許可する（アプリが出力するのは JPEG だけ）。PNG や WebP の方が、圧縮率が高く、細工しやすい。
- JPEG のヘッダ（SOF マーカー）から、縦横を読み、512px 以下のものだけを許可する純粋関数 `getJpegDimensions` と `isAcceptableIllustrationSize` を追加した。デコード境界（保存形式の読み込み、バージョン 3）で検証する。
- パーサーの安全性: 先頭が SOI であること、マーカーの長さが範囲内であること、毎回、1バイト以上進むこと（無限ループしない）、壊れた入力は `null` を返すこと。複数の SOF がある場合は先頭を採用する（主要なブラウザのデコーダは、2つ目の SOF をエラーにするので、「先頭は小さく、後ろは巨大」という偽装は成立しない）。EXIF のサムネイルは、別のセグメントの中にあるので、読み飛ばされる。
- テスト: 実在する JPEG と、寸法だけを宣言する偽のヘッダ（SOF で 20000×20000 を宣言する最小の JPEG）を使い、受理と拒否の両方を確認する。

**汎用的な教訓**
- 外から来るデータの検証は、「形式」「データの大きさ」に加えて、**「展開した後の大きさ」**を確認する。画像、圧縮ファイル、音声など、展開すると大きくなる形式では、必須。
- 検証は、「自分のコードが作る値」ではなく、「その入口に入れられる全ての値」を基準にする。信頼境界ごとに、「ここに細工されたデータが来たら、何が起きるか」を、レビューの明示的な観点にする。
- 検証を入れる場所は、データが内側に入る1か所（ここでは、保存形式の読み込み）に集める。

### B2. 生成したあとで対象のテキストを変えても、古いプレビューが残った【Minor】

**発生する状況**
ノードのテキスト「予算」から画像を生成し、プレビューが出ている状態（または、生成中）で、そのノードのテキストを別の内容に編集したとき。

**問題**
プレビューは「予算」から作った画像のまま残り、パネルの表示は、新しいテキストのノードのものとして見える。そのまま「ノードに設定」を押すと、新しいテキストと内容が合わない画像が、ノードに紐付く。

**原因（詳細）**
- 生成の状態（生成中、成功）は、「どのノードのためのものか」を、ノードの識別子（`nodeId`）だけで持っていた。パネルは、選択中のノードの識別子と一致するかどうかだけで、プレビューを出していた。
- 識別子が同じなら、「同じ対象のもの」だと見なしていたが、画像の生成の入力は、識別子ではなく、**ノードのテキスト**である。テキストが変わると、入力が変わるので、生成結果は、もう「このノードの、今のテキストに対するもの」ではない。
- 既存の仕組み（マップの置き換えで状態を破棄する、別のノードを選ぶとプレビューを隠す）は、識別子の変化と世代の変化に対応していた。しかし、「同じ識別子で、中身が変わる」ケースは、想定されていなかった。
- ノードのテキストを更新する関数は、生成の状態に触れない。この関数と、生成のフックは、別の責務なので、これは正しい分離だが、そのために、状態の整合性は、表示の側（判定）が担う必要があった。

**修正**
- 生成の状態に、生成を始めた時点のノードのテキスト（`label`）を持たせた。正規化後の値ではなく、生の値を保存して、比較を単純な一致にする（正規化の違いによる誤判定を避ける）。
- 表示の判定（純粋関数）で、識別子と生成時のテキストが両方とも一致するときだけ、プレビューを出す。一致しなければ、設定済みのイラストがあればそれを、なければ何も出さない。テキストを元に戻せば、プレビューは再び出る。
- 採らなかった案: テキストの更新時に生成状態を破棄する。テキスト編集の機能と生成のフックの結び付きが増え、テキストを戻したときにプレビューを復元できない。
- テスト: テキストが違うときのプレビューの有無、同じときの有無、生成中に変更して完了したとき、パネルに「ノードに設定」が出ないこと、フックが生成時のテキストを保存すること。

**汎用的な教訓**
非同期の結果（生成、検索、取得）を、対象に紐付けて保持するときは、**結果の入力になった値そのもの**（ここでは、テキスト）を、一緒に保持して、表示時に照合する。識別子だけでは、「同じ識別子で、中身が変わる」ケースを見落とす。これは、世代で無効化する仕組み（外部 API 連携の整理 B7）の、もう1つの軸（対象の中身の変化）にあたる。

### B3. SVG の宣言と中身が、仕様の版で食い違った【Minor】

**発生する状況**
書き出した SVG ファイルを、SVG 1.1 までしか対応していない外部のツール（古い画像変換ツールやエディタ）で開いたとき。

**問題**
SVG のルートに `version="1.1"` を宣言しているのに、画像の参照を、SVG 2 の書き方（`href`）だけで出していた。SVG 1.1 では、画像の参照は `xlink:href` だけが有効なので、そのツールでは、イラストだけが表示されない（図形とテキストは出る）。

**原因（詳細）**
- 最近のブラウザは、`href` を理解するので、アプリ内の表示と、画像（PNG）への変換（ブラウザが SVG を読み込む）では、問題が起きない。そのため、テストでも、実際の画面確認でも、見つからない。
- もともとの SVG の出力には、`version="1.1"` が書かれていた。画像の要素を足したとき、その宣言と、足す要素の書き方が、同じ版の規則に従っているかを、確認しなかった。
- 宣言は、ファイルの先頭に1行あるだけで、要素を足す場所（ノードごとの生成）とは、別のファイルにあった。離れた場所の記述の整合は、見落としやすい。

**修正**
ルートに `xmlns:xlink` を宣言し（`version="1.1"` の後ろ）、`<image>` に `href` と `xlink:href` の両方を出す。宣言なしに `xlink:href` だけを足すと、名前空間の接頭辞が未定義になって、XML として不正になり、ブラウザの読み込み（PNG エクスポート）ごと失敗する。ルートの宣言と要素の変更を、必ず同時に行った。テストでは、文書全体を XML として読み込み（`parsererror` がないこと）、`xlink:href` が画像のデータになっていることを確認する。

**汎用的な教訓**
出力形式に要素を足すときは、その形式が宣言している版（`version`）や名前空間と、足す要素の書き方が一致しているかを確認する。「主要なブラウザで動く」ことは、「宣言した版に準拠している」ことの証拠にならない。

### B4. 透過のある画像を JPEG に変換すると、背景が黒になる【対応しない】

**発生する状況**
アルファ（透過）を持つ画像（PNG や WebP）を、背景を塗らずに、キャンバスを経由して JPEG に変換したとき。

**問題**
JPEG は透過を持てないので、透過部分は、不透明の黒に合成される。

**原因（詳細）**
キャンバスの `toDataURL("image/jpeg")` は、透過のピクセルを、黒の不透明な背景に合成する（HTML の仕様）。変換の前に、背景を塗る処理がない。

**対応しない理由**
- 現在の構成では、透過画像が、この変換に届く経路がない。画像の生成は、特定のモデルで固定されていて、そのモデルは JPEG（透過なし）を返す。サーバーの戻り値の型も、`mimeType: "image/jpeg"` のリテラル型で固定されている。クライアントの検証が PNG と WebP を許可しているのは、応答を検証する幅にすぎず、実際に届くことはない。
- モデルや出力形式を変えるときは、サーバーの型と生成処理の変更が必ず伴うので、気付かずに PNG が混ざることはない。透過への対応（背景を白で塗る）は、その変更と同時に入れる。
- 影響のない予防的な指摘で、修正自体（2行）は無害だが、現時点で必要としない。

**汎用的な教訓**
「届く経路がない」ことを、型や固定された設定（コードの事実）で確認できるなら、予防的な指摘は、理由を書いて見送ってよい。ただし、**経路を開く変更（出力形式の変更）が起きたときに、同時に直す**ことを、判断の記録に残す。

### B5. 派生値と元の値が食い違う入力（イラストがあるのに、高さが足りない）【Minor】

**発生する状況**
手で編集した保存データ（JSON）で、イラストを持つノードの高さが、イラスト付きの高さ（116）より小さいとき。

**問題**
テキストの中心が、ノードの外にはみ出す。テキストの編集欄の高さが極小、または負になる。

**原因（詳細）**
- イラスト付きのノードの高さは、「イラストの領域の分だけ伸びる」という規則から決まる派生値だが、ノードのデータの中に、独立した値（`height`）として保存される。アプリ自身は、イラストを設定するとき、必ず高さも更新するので、食い違いは作れない。
- しかし、保存データの読み込みは、「`height` が正の数であること」だけを確認し、「イラストの有無と高さの整合」を確認しなかった。派生値を保存する設計では、読み込み時に、整合を保証する必要がある。
- 逆の食い違い（高さが 116 で、イラストなし）は、余白が出るだけで、表示は壊れない。

**修正**
読み込み時に、イラストがあるノードの高さを `max(高さ, イラスト付きの高さ)` にそろえる。イラストがないノードの高さは変えない。なお、イラストを設定するときは、高さを固定値にする（読み込み時とルールが異なる点は、今は実害がないので、統一するかどうかは、判断待ち）。

**汎用的な教訓**
派生できる値を、独立した値として保存するときは、「読み込み時に、整合を確認または補正する」処理を入れる。保存データの入口は、アプリ自身が作った値だけでなく、手で作った値も受け付ける。

### B6. 1つの事実（テキストの位置）を、複数の場所が別々に計算した【実装者が、計画外で発見】

**発生する状況**
ノードの中のテキストの位置が、イラストの有無で変わる機能で、テキストの位置を使う場所が複数あるとき（キャンバスの描画、SVG エクスポート、エクスポート範囲の計算、テキストの編集欄）。

**問題**
描画とエクスポートだけを直すと、編集欄が、ノード全体（116）を覆い、中心が、ノードの中央（58）にずれる。キャンバスのテキスト（86）と編集欄の中心が食い違って、編集を始めた瞬間に文字が跳ぶ。

**原因（詳細）**
- 「テキストの中心は、ノードの高さの半分」という規則が、複数の場所に、それぞれ式として書かれていた。1つの規則が、複数の場所に分散している。
- 計画には、描画とエクスポートだけが書かれ、編集欄は書かれていなかった。実装者が、「高さの半分」を使っている箇所を検索して（`height / 2` の全箇所の確認）、編集欄を見つけた。
- 検索で見つかった残りの箇所（エッジの端点、ノードの中心へのフォーカス）は、ノードの矩形の中心を使う処理で、テキストの位置ではないので、変更しなかった。

**修正**
テキストの中心を、1つの関数 `getNodeLabelCenterOffset` にまとめ、4か所すべてで使う。計画外の変更だが、必要で、イラストのないノードの結果は、変わらない（テストで確認）。

**汎用的な教訓**
ある値の意味が変わる変更では、その値を使っている箇所を、検索で全て洗い出す。計画に書かれていない箇所が見つかったら、変更するか、しない理由を書く。1つの規則は、1つの関数に集約する（側面パネルの整理 S1「値と規則の共有」と同じ）。

### B7. 非同期の読み込みが、再実行のたびにキャンセルされ、永久に読み込まれなくなる落とし穴

**発生する状況**
画像のテクスチャを非同期に読み込むフックで、依存する値（ノードの配列）が変わるたびに、effect が再実行されるとき。

**問題**
読み込み中に、ノードが1つ追加されるなど、配列が変わると、前の実行の cleanup が「キャンセル済み」にする。その実行の読み込み結果は、捨てられる。ところが、「読み込みを要求済みの URL」の記録は残るので、次の実行は、その URL を再度読み込まない。結果として、その画像は、永久に表示されない。

**原因（詳細）**
- effect の cleanup は、依存する値が変わるたびに実行される。キャンセルの旗を「effect の実行ごと」に持つと、実行が変わるたびに、前の実行の非同期の結果が捨てられる。
- 一方で、「要求済み」の記録を、実行をまたいで持つと、「捨てられた読み込み」と「再度読み込まない」が組み合わさって、結果が失われる。
- 計画の段階で、この落とし穴を、注意書きとして書いておいたので、実装者は避けられた。

**修正**
状態（要求済みの URL、読み込み済みのテクスチャ、破棄済みの旗）を、effect の実行ごとではなく、**実行環境（runtime）ごと**に持つ。実行環境が変わる、またはアンマウントされるときだけ、破棄する。「読み込み中にノードの配列が変わっても、最終的にテクスチャが返る」テストを追加した。アンマウント後に届いたテクスチャは、その場で破棄する。

**汎用的な教訓**
非同期の結果を、依存する値の変化でキャンセルする設計では、「キャンセルの単位」と「重複排除の単位」を、同じにする。キャンセルの単位が、重複排除の単位より短いと、結果が失われる。

### B8. 保存形式のバージョンを上げたときの、移行と後戻り【既存の方針どおり】

**発生する状況**
保存データの形式を、バージョン 2 から 3 に上げたとき。

**問題**
- 古いバージョン（2）の保存データは、読み込めるが、読み込んだ直後には書き換わらず、次に編集があるまで、バージョン 2 のまま残る。
- 古いビルドに戻すと、バージョン 3 のデータを読めず、空のマップから始まり、次の編集で上書きされる。

**原因（詳細）**
- 1つ目: 復元の処理は、「バージョン 1 のときだけ、移行後のデータを保存する」という既存の条件を持っていた。バージョン 2 の保存データは、読み込みと同じ内容を再生成しても、意味が同じなので、書き換える必要がないと判断されていた。
- 2つ目: 古いビルドは、新しいバージョンを知らないので、「未対応の形式」として扱う。これは、前回のバージョン上げ（1 から 2）のときと同じ方針で、既存の挙動である。

**修正（対応）**
どちらも、データが失われる問題ではなく、既存の方針と同じなので、変更しなかった。後戻りの注意は、PR 本文の「影響範囲」に書いた。

**汎用的な教訓**
保存形式のバージョンを上げるときは、「古いデータを読めるか」「古いビルドに戻したら、何が起きるか」を、影響範囲に書く。

### B9. 中断のガードが二重にあり、片方が壊れても気付けない【テスト観点は T3】

**発生する状況**
生成の結果を、「中断されたか」の判定と、「状態の世代が現在のものか」の判定の、2つで守っているとき。

**問題**
縮小の途中で、マップが置き換わったとき、結果は捨てられるべきだが、世代の判定だけで、すでに「無効」と見なされるので、中断の判定が壊れても、テストが通ってしまう（T3）。

**原因（詳細）**
外部 API 連携の整理 B7 で、状態に世代（`resetRevision`）を付ける仕組みを入れた。その後、縮小という新しい非同期の段階が増えた。結果を捨てる仕組みは、中断の判定（旗）と世代の判定（状態の世代）の2つになった。どちらか1つで、同じ結果になるので、片方の不具合が見えなくなる。

**修正**
挙動は正しいので、実装は変えなかった。テストの検出力の問題として記録した（T3）。ロックの解除が、世代の変化と中断の両方で、正しく行われることは、レビューで確認した。

**汎用的な教訓**
二重の防御は、安全だが、テストでは、片方を無効にしたときに、もう片方だけで守られることが、区別できるように書く（T3）。

### B10. 軽微な性能・メッセージの指摘【対応しない】

次の指摘は、影響が小さい、または既存の方針なので、対応しなかった。
- テクスチャを1枚読み込むたびに、シーン全体を作り直す（イラストが N 個あるマップを復元すると N 回）。正しく動き、数十枚までなら問題ない。
- 読み込みに失敗した画像は、再試行せず、ノードの上部が空いたままになる。計画で意図された挙動で、PR 本文に既知の制限として書いた。
- 保存領域が一杯になったとき、汎用のメッセージが出る。README に説明があり、JSON のエクスポートで残せる。
- 細い幅（48px 未満）のノードに、イラストが付くとはみ出す。手で作ったデータでしか起きず、安全性に影響しない。
- 保存データの末尾（画像の終端の後ろ）に付け足されたデータの検査がない（確信度が低く、影響は限定的）。
- イラストを設定する関数が、寸法を検証しない（入力は、アプリが縮小して作る 128px の画像だけ。信頼できる入力）。

## 3. テストの指摘

### T1. 「入力」と「期待値」を区別せずに、テストのデータを書き換えた

**発生する状況**
保存形式のバージョンを上げたとき、既存のテストが、同じデータ（fixture）を、入力と期待値の両方に使っていたとき。

**問題**
実装者が、期待値を合わせるために、データのバージョンを 2 から 3 に書き換えた。その結果、同じデータを入力にしていたテスト（古いバージョンの保存データを読み込み、書き換えないことを確認するテスト）まで、バージョン 3 の入力に変わり、古い形式との互換性を確認するテストが、実質的に失われた。

**原因（詳細）**
入力と期待値で、同じ定数を共有しているテストでは、定数を変えると、両方が変わる。実装者は、「期待値だけを変える」べきところを、「データ全体を変える」ことで、手っ取り早く合わせた。変更の差分では、「データの定数の更新」としか見えず、意味が変わったことは、テスト名と照らさない限り、気付かない。

**修正**
入力側のデータを、元のバージョン 2 に戻した。出力側（期待値）の定数だけを 3 のままにした。

**汎用的な教訓**
互換性のテストでは、入力に、古い形式の実データを使い、期待値と同じ定数を共有しない。テストのデータを変えるときは、「入力か、期待値か」を区別する。

### T2. 拒否のテストが、拒否の「理由」を検証しなくなった

**発生する状況**
検証の条件を厳しくした（PNG と WebP を拒否し、JPEG だけにした）あと、既存の拒否のテストの入力が、PNG のまま残ったとき。

**問題**
「base64 でない」「本体が空」「属性を壊す文字を含む」「改行を含む」といった拒否のテストが、すべて、「PNG だから」という別の理由で拒否されるようになった。テストは通るが、それぞれのラベルが示す理由を、検証していない。

**原因（詳細）**
元の入力は、`data:image/png;base64,…` の形式で、各テストは、その一部（base64 の部分）だけを壊していた。検証の条件に、「形式が JPEG であること」が加わると、一番先に、形式の判定で拒否されるので、壊した部分まで、判定が届かない。拒否のテストは、「拒否される」という結果だけを確認するので、理由が変わっても、赤くならない。

**修正**
各拒否のテストの入力を、形式を JPEG にしたうえで、それぞれの部分だけを壊す形に直した。形式の拒否（PNG、WebP、SVG）は、独立したケースとして残した。

**汎用的な教訓**
検証の条件を変えたら、既存の拒否のテストが、「元の理由」で拒否されているかを確認する。拒否のテストは、他の条件を全て満たした入力から、1か所だけを壊して作る。

### T3. 二重の防御のうち、片方を外しても、テストが通る

**発生する状況**
結果を捨てる仕組みが、中断の旗と状態の世代の2つで二重になっているとき（B9）。

**問題**
「縮小の途中でマップが置き換わったら、結果を捨てる」テストが、中断の旗の判定を外しても、世代の判定だけで通る。判定の有無を、検出できない。

**原因（詳細）**
遅れて届いた結果は、置き換わる前の世代で保存されるので、世代の比較だけで、「無効」と見なされる。テストは、最終的な表示（idle）しか見ないので、どちらの仕組みが守ったかが区別できない。

**修正**
今回は、実装が正しいことをレビューで確認し、テストは変えなかった（任意の改善案として、置き換え後に再度生成できること、つまり、ロックが解除されることまで確認する）。

**汎用的な教訓**
二重の防御のテストでは、片方の防御だけを無効にした状態（変異）で、テストが赤くなるかを確認する（側面パネルの整理 T1 と同じ）。

### T4. 失敗経路のテストが、「未処理の拒否」を検証できていない

**発生する状況**
読み込み失敗（Promise の reject）を、実装が握りつぶすことを確認するテストで、テストの側が、失敗する Promise に `catch` を付けていたとき。

**問題**
テストの側で `catch` を付けると、実装がハンドラを持たなくても、「未処理の拒否」が検出されない。つまり、「例外を投げず、握りつぶす」という要件を、検証できていない。

**原因（詳細）**
JavaScript の「未処理の拒否」は、どこにも `catch` されていない Promise が拒否されたときだけ起きる。テストが、準備した Promise の変数に `catch` を付けると、その Promise は、処理済みになる。実装が処理しなくても、イベントが出ない。

**修正**
今回は、実装側にハンドラ（`() => {}`）があることを確認したので、変更しなかった。改善案は、毎回新しい拒否を返すモックにし、テスト側で `catch` を付けず、実装のハンドラだけが処理することを確認する。

**汎用的な教訓**
「握りつぶすこと」を検証するときは、テスト側が拒否を処理しない形にする。

### T5. 安全性に関わる解析処理の、分岐のテストが不足した

**発生する状況**
外から来るデータを解析する関数（JPEG のヘッダの解析）を、実装した直後に、主要な正常系と異常系だけをテストしたとき。

**問題**
解析の分岐（詰め物のバイト、長さのないマーカー、複数の SOF）のテストがなかった。実装は正しく動いたが、将来の変更で壊れたときに、検出できない。

**原因（詳細）**
実装者は、仕様に書かれたテスト（正常、上限、0、切り詰め、不正な長さ、非マーカー、非 JPEG）を実装した。仕様に書かれていない、「規格上は起こりうる分岐」は、書かれていない限り、テストに含まれない。

**修正**
詰め物の 0xFF、RST と TEM の読み飛ばし、複数の SOF（先頭を採用）の3ケースを追加した。偽のヘッダ（寸法だけを宣言する最小の JPEG）は、テスト用の fixture として、`testing/` に置いた。

**汎用的な教訓**
安全性に関わる解析処理は、規格上ありうる分岐を、すべてテストする。実在する最小のデータと、寸法だけを宣言する偽のヘッダの両方を用意する。

### T6. 浮動小数点の「式の形」を保つ

**発生する状況**
既存の計算式（`node.y + node.height / 2`）を、新しい関数（テキストの中心）に置き換えるとき。

**問題**
計算の順序や形を変えると、浮動小数点の丸めが変わり、既存のテスト（小数を含む座標の、厳密な比較）が、わずかにずれて失敗する。

**原因（詳細）**
`a + b/2` と `(a + b)/2` は、数学的には同じではないが、数が整数なら同じに見える。小数や大きな値では、丸めの違いで、結果が変わりうる。エクスポート範囲の計算は、桁あふれを避けるために、特定の形（`node.y / 2 + nodeBottom / 2`）で書かれていた。

**修正**
- 新しい関数は、`node.height / 2 + (イラストがあるときだけの項)` の形にして、イラストがないときは `+ 0` になるようにした。
- エクスポート範囲では、イラストがないノードに、既存の式をそのまま使い、イラストがあるノードだけ、新しい式にした。
- 既存のテストは、変更しない。

**汎用的な教訓**
既存の数値計算を共通化するときは、**既存の式の形のまま**移す。既存のテストが変わらずに通ることが、挙動が変わっていないことの証拠になる。

## 4. ドキュメント・PR 本文の指摘

### D1. 計画の記述が、実装後の変更とずれた

**発生する状況**
計画に書いた仕様（`png` と `webp` を許可する）が、レビューの指摘で変わった（`jpeg` だけ）あと、計画の記述が、そのまま残ったとき。

**問題**
計画ファイルは、リポジトリに残る記録なので、後から読むと、実装と食い違う。

**原因（詳細）**
実装とテストは、レビューの指摘で更新されたが、計画は、「過去の記録」と見なされて、更新の対象から漏れた。

**修正**
計画の該当箇所（テスト例、パターン、方針）を最小限だけ直し、末尾に、「実装後の変更」として、変更の理由を1行だけ追記した。

**汎用的な教訓**
計画を、リポジトリに残す場合は、実装後の仕様の変更を反映する（計画の他の部分は、記録として変えない）。

### D2. 実機で確認していない項目を、完了にしたときの扱い【Important】

**発生する状況**
実ブラウザ（キャンバスの描画、PNG への画像の出力、Safari と Firefox、実際の外部サービスの応答）でしか確認できない項目が、自動テストだけでは確認できないまま、ROADMAP の項目を完了にしたとき。

**問題**
「完了」という表示が、実機での確認を、含んでいるように見える。PNG エクスポートに画像が出ないなど、実機でしか見つからない不具合が残る可能性がある。

**原因（詳細）**
テストとビルドは、描画の結果（実際のピクセル）や、ブラウザごとの違いを検証しない。計画の最後のタスクに、手動確認の手順を書いたが、実行する主体（利用者のブラウザ、利用者の外部サービスの無料枠）は、自動の実装の外にあった。ROADMAP は、実装と同じブランチで更新するルールなので、手動確認の前に「完了」にする。

**修正**
- PR 本文の「テスト方法」に、「実装者は、実ブラウザでの手動確認を行っていない」と明記し、マージ前の確認手順を書いた。
- 「既知の制限」と「要確認」に、未検証の範囲（PNG への描画、Pixi の実描画）を書いた。
- レビューは、実機でしか確認できない点を、「未検証」と書き、推測で OK としない。

**汎用的な教訓**
実機でしか確認できないことは、未確認の事実を、PR 本文とレビューに明記する。「テストが通った」を、「動作を確認した」と書かない（側面パネルの整理 P3 と同じ）。

### D3. 計画の制約と、リポジトリのルールの食い違い

**発生する状況**
計画の制約（「git worktree を使わない」）と、リポジトリのルール（「`.worktrees/<branch>` で作業する」）が、食い違っているとき。

**問題**
レビューが、指摘として挙げた。ただし、利用者が、worktree を使わないことを明示的に指示していたので、計画は、利用者の指示に従っていた。

**修正**
ルールの文面は、変更しない（利用者の指示は、このリポジトリのルールへの追加を求めていない）。次の計画からは、利用者の指示に従う。

**汎用的な教訓**
リポジトリのルールと、利用者の明示的な指示が食い違うときは、利用者の指示に従い、レビューの指摘には、その旨を、理由として返す。

## 5. レビューの進め方・作業手順

### P1. 観点を明示すると、それまでのレビューが見落とした重大な指摘が出る

**発生する状況**
タスクごとのレビュー、最終レビュー、リファクタリングのレビューが、すべて「承認」で通ったあとの、マージ前のレビューで、Important の指摘（B1）が出たとき。

**問題**
同じ機能について、複数のレビューが、同じ見落としをした。

**原因（詳細）**
各レビューの観点が、仕様適合、コードの品質、既存機能への副作用、計画との整合だった。「外から来たデータが、何を引き起こせるか」は、1つの観点として、明示されていなかった。最終レビューの観点には「セキュリティ」を含めていたが、「巨大データ」「信頼境界」の具体的な例を挙げていなかったため、形式の検証があることで安心した。マージ前のレビューで、「データの大きさ（展開後）」「信頼境界」「ブラウザのメモリ」を、観点に具体的に挙げて、初めて見つかった。

**修正**
レビューの観点に、具体的な失敗の型（巨大データ、信頼境界、SVG への注入）を、毎回、書く。

**汎用的な教訓**
レビューの観点は、「セキュリティ」のような抽象語ではなく、**具体的な失敗の型**で書く。観点を変えると、見つかるものが変わる（オーバーレイ型メニューの整理 P1）。

### P2. 未コミットの変更を、レビューに渡す方法

**発生する状況**
コミットしない制約（利用者の指示）のもとで、作業ツリーの変更を、レビューに渡すとき。

**問題**
通常の差分（`git diff main..HEAD`）には、未コミットの変更や、新規のファイルが含まれない。

**修正**
一時的な index（`GIT_INDEX_FILE`）に、全ての変更を追加し、ツリーを書き出して、基準との差分を取る方法を使った（本物の index とワーキングツリーは変更しない）。作業のたびに、本物の index に、ステージされたものがないことを確認した。

**汎用的な教訓**
コミットしない制約のもとでは、一時的な index のスナップショットで、差分を作る（オーバーレイ型メニューの整理 P4 と同じ）。

### P3. 実装者が、ブリーフの外の変更をしたとき、レビューで判断する

**発生する状況**
実装者が、ブリーフに書かれていない変更をしたとき（テスト用のデータの書き換え（T1）、編集欄の位置の修正（B6））。

**問題**
必要な変更（B6）と、不要でテストを弱める変更（T1）の両方があった。

**修正**
レビューの依頼に、「ブリーフ外の変更があるので、妥当かを判断する」ことを、具体的に書いた。T1 は、元に戻し、B6 は、必要なので、そのまま採用した。

**汎用的な教訓**
実装者の報告にある「ブリーフ外の変更」は、必ずレビューの観点に入れる。採用するかは、「テストの意味を弱めていないか」「必要な修正か」で判断する。

### P4. 指摘の確信度が低いときの判断

**発生する状況**
レビューが、「確信度は低い」と明記した指摘を出したとき（保存データの末尾に付けられたデータによる寸法の偽装）。

**問題**
修正すると、正しいデータを拒否する、または、複雑な処理が増える。

**修正**
実際の影響が、特定のブラウザの実装に依存し、データの大きさの上限もあるので、見送った。見送った理由を、記録した。

**汎用的な教訓**
確信度の低い指摘は、修正の副作用（正しいデータを拒否するか）と、影響の大きさで、判断する。見送った理由を残す。

### P5. コミットを分ける境界と、依存関係

**発生する状況**
複数の種類の変更（リファクタリングと、セキュリティの修正）を、コミットを分けて残したいとき。

**問題**
2つの変更が、同じファイル（検証の部品）に入り込んでいて、片方だけのコミットが、単体で、ビルドとテストを通らなくなる。

**修正**
無理に分けず、コードの変更は、1つのコミットにまとめ、コミットメッセージの本文に、両方を書いた。計画ファイルの修正は、別のコミットにした。

**汎用的な教訓**
コミットは、1つ1つが、単体でビルドとテストを通ることを優先する。変更が依存し合うなら、1つにまとめる。

### P6. 対応しない指摘も、スレッドに理由を返して、Resolve する

**発生する状況**
PR のレビューで、対応しないと判断した指摘があるとき（B4）。

**修正**
理由（根拠となる事実、影響の有無、変更が必要になる条件）を、スレッドに返信してから、Resolve した。理由のコメントなしでは、Resolve しない（リポジトリのルール）。

**汎用的な教訓**
対応しない指摘には、事実に基づく具体的な理由を書く。「いつ対応するか」（出力形式を変えるとき）も添えると、後から読む人が判断できる。

## まとめ: 同種の機能のレビューチェックリスト

外部から来るデータ（画像、ファイル）を、アプリのデータに組み込み、描画、保存、出力する機能のレビューでは、次を確認する。

1. **信頼境界の検証**: 形式、データの大きさ、**展開後の大きさ**。入口（インポート、保存データの復元）ごとに、「その入口に入れられる全ての値」を基準にしているか（B1）。
2. **状態の対象と中身**: 非同期の結果を、識別子だけでなく、入力にした値（テキストなど）と一緒に持っているか（B2）。
3. **出力形式の準拠**: 宣言している版、名前空間と、出力する要素の書き方が一致しているか（B3）。
4. **派生値の整合**: 派生できる値を保存する設計では、読み込み時に整合を保証しているか（B5）。
5. **1つの規則は1か所**: ある値の意味が変わる変更では、使っている箇所を全て洗い出したか（B6）。既存の数値計算は、式の形を保って移したか（T6）。
6. **非同期のキャンセルの単位**: キャンセルの単位と、重複排除の単位が同じか（B7）。
7. **構造**: 新しい関係を足した関数の、変更理由が増えていないか。共有する型は、`types/` にあるか（S1、S2）。分割しない判断に、根拠があるか（S3）。
8. **テスト**: 互換性のテストの入力は、古い形式の実データか（T1）。拒否のテストは、理由を検証しているか（T2）。二重の防御は、片方を外すと赤くなるか（T3）。安全性に関わる解析は、規格上の分岐を全て網羅しているか（T5）。
9. **確認できていない範囲の明示**: 実機でしか確認できないことを、未確認と明記したか（D2）。
10. **レビューの観点**: 抽象語ではなく、具体的な失敗の型で書いたか。観点を変えて繰り返したか（P1、S4）。
