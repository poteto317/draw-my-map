## 1. 構造（単一責任）の指摘

### S1. 外部呼び出しの共通処理が、呼び出し先ごとに重複しかけた

**発生する状況**
同じ外部サービスの、複数の機能（ここでは、画像生成と翻訳）を呼び出すとき、それぞれの呼び出し先に、時間切れ、エラーの分類、認証情報を漏らさない処理を、書き写したとき。

**問題**
共通の規則（時間切れの扱い、無料枠の超過、不適切な内容の拒否の判定、エラー文にトークンを含めない）が、呼び出し先の数だけ重複する。後から、規則を直すとき（B4 のタイムアウトのように）、片方だけを直し忘れる。

**原因（詳細）**
- 最初に、画像生成の処理だけを実装したので、外部呼び出しの詳細（URL の組み立て、認証ヘッダー、タイムアウト、エラーの分類）が、画像生成の関数の内側に書かれた。
- 翻訳の追加（B3 の対策）が決まった時点で、そのまま書き写すと、規則が2か所になることが明らかだった。
- さらに、共通部品を、画像生成のファイルから import すると、翻訳の部品が、画像生成のファイルに依存し、依存の向きが不自然になる。エラー型を、共通部品とは別のファイルに分けないと、循環 import になるおそれがあった。

**修正**
- 共通の呼び出し部品（`runCloudflareModel`）に、URL、認証、タイムアウト（本文の読み込みまで）、エラーの分類、固定のエラー文を集約した。
- エラー型と設定の型は、別ファイル（`cloudflareErrors.ts`）に置いた（共通部品は、このファイルだけに依存し、画像生成のファイルは、再エクスポートで、既存の import を維持した）。
- 画像生成と翻訳は、モデル名と入力の組み立て、結果の取り出しだけを持つ。
- 画像生成の既存のテストは、変更せずに通ること（挙動を保つリファクタリング）を、先に確認した。

**汎用的な教訓**
外部呼び出しの共通の関心事（認証、タイムアウト、エラーの分類、機密の扱い）は、呼び出し先の機能から分離する。共通部品が依存する型は、共通部品の側（または別ファイル）に置き、依存の向きを一方向にする。

## 2. 挙動・不具合の指摘

### B1. 公式ドキュメントが必須としたパラメータを、実際の API が拒否した

**発生する状況**
外部サービスの公式ドキュメントのスキーマを信じて、リクエストを組み立て、偽の `fetch` を使うテストだけで確認したとき。

**問題**
実際に呼ぶと、HTTP 400 で、次のエラーになる。認証は通っているのに、機能は一切動かない。

```
AiError: Bad input: Error: Additional or unevaluated properties '/seed' at '/' not allowed（コード 5006）
```

**原因（詳細）**
1. 画像生成モデルの公式ページには、`seed`（乱数の種）が「必須、ランダムな正の整数」と書かれていた。実装も、それに従って、リクエストに `seed` を含めた。
2. 実際の API の入力検証は、`prompt` と `steps` 以外の項目を許さなかった。公式ページのスキーマの記述と、実際の API の挙動が、食い違っていた。
3. 計画の段階で、「`seed` の型を、公式ページで確認する」と記載したが、確認できたのは、**ページの記述**であり、**実際の API の挙動**ではなかった。
4. テストは、偽の `fetch` を使い、「`seed` を含む本文を送ること」を前提に書かれていた。偽の応答は、テストを書いた人の仮定を、そのまま映すので、仮定が間違っていても、テストは通る。
5. 認証情報を持たないエージェントは、実際の API を呼べない。実際の呼び出しは、認証情報を持つ利用者の環境でしかできなかった。

**修正**
- `seed` を、リクエストから外した（本文は `{ prompt, steps: 4 }`）。
- 「本文のキーが、`prompt` と `steps` だけである」ことを、完全一致で検証するテストを追加した（実際の API の挙動を根拠にしたコメント付き）。
- 利用者向けの手順書の `curl` の例からも外した（D2）。

**汎用的な教訓**
- 外部サービスのドキュメントは、実際の挙動と食い違うことがある。「ドキュメントで確認した」は、「実際の API で確認した」ではない。
- 外部 API を呼ぶ機能は、実装の早い段階で、1回、実際の API を呼んで、リクエストとレスポンスの形を確かめる（P1）。
- 偽の応答を使うテストは、リクエストの形を、実際の API の応答で確認した値に固定する。

### B2. 不適切な内容の判定が、無害な入力にも、ランダムに反応する

**発生する状況**
外部サービスの安全フィルタ（不適切な内容の判定）が、確率的に動作し、同じ入力でも、結果が変わるとき。

**問題**
同じプロンプトで、成功したり、HTTP 400（コード 8007、「Input prompt contains NSFW content」）で拒否されたりする（測定では、5回中2回が拒否）。利用者には、「生成に失敗しました」としか表示されず、再試行すれば成功することが分からない。

**原因（詳細）**
- 安全フィルタは、プロンプトのテキストだけでなく、内部の確率的な処理を含むと見られ、同じ入力でも、判定が一定ではなかった。ノードのテキストの内容とは、無関係に、一定の確率で起きる。
- 実装は、「無料枠の超過」以外の失敗を、すべて「上流のエラー」にまとめていたため、この拒否も、区別されなかった。
- この挙動は、ドキュメントにも、単体テストにも、現れない。同じプロンプトを、複数回、実際に送って、初めて分かった（P1）。

**修正**
- 拒否の判定（コード 8007、または、メッセージに `NSFW`）を、専用のエラーの種類（`content-rejected`）にした。無料枠の判定との優先順位は、「不適切な内容」が先。
- リクエストの処理が、この種類のエラーだけを、自動で再試行する（最初の1回を含めて、最大 3 回。再試行は最大 2 回）。ほかのエラー（無料枠の超過、上流のエラー）は、再試行しない。
- 3回とも拒否されたときは、HTTP 422 を返し、ブラウザ側が、専用のメッセージ（「誤判定のことがあります。もう一度お試しください」）を表示する。
- 優先順位と、HTTP 200 でも失敗している応答（`success: false`）の分岐は、変異に耐えるテストで固定した（T1）。

**汎用的な教訓**
外部サービスの安全フィルタや、確率的な処理による失敗は、「利用者の入力の問題」と「一時的な失敗」を区別して扱う。後者は、自動の再試行と、再試行を促すメッセージで、利用者に負担をかけない。再試行の回数と、リクエストごとの上限は、定数にして、テストで固定する。

### B3. API は成功しているのに、機能の目的を満たさない（日本語が、文字として描かれる）

**発生する状況**
英語中心の画像生成モデルに、日本語を含むプロンプトを渡したとき。

**問題**
HTTP 200 で、画像が返り、機能は「成功」しているように見えるが、画像は、イラストではなく、**ノードのテキストを、漢字のような文字として描いただけの、白地の画像**になる。「文字は描かない」という指示も、効かなかった。

**原因（詳細）**
1. プロンプトは、「`the concept "アイデア"` を表すイラスト、文字なし」という、英語の文に、日本語のテキストを、引用符つきで埋め込む形だった。
2. 画像生成モデルのテキスト理解（エンコーダー）は、英語が中心で、日本語の意味を、十分に捉えられない。日本語の文字列を、「そのまま描く対象の文字」として扱った。
3. 引用符を外す、「文字を描かない」という指示を足す、といったプロンプトの書き方の工夫では、改善しなかった（日本語の文字が、プロンプトに1文字でもあると、文字を描く傾向が残った）。
4. この問題は、API の応答コードにも、単体テストにも、現れない。**実際に生成された画像を、目で見て**初めて分かった（P1）。レビューも、コードを読むだけでは、気付けない。

**修正**
- サーバーが、ノードのテキストを、先に、Cloudflare の翻訳モデル（`@cf/meta/m2m100-1.2b`）で英語にし、その英語で、プロンプトを組み立てる。翻訳の消費は、1回あたり 0.3〜0.5 Neurons と、ごくわずか。
- プロンプトのテンプレートを、英語の概念を埋め込む形にし、「被写体を大きく、画面の中央に」という指示も加えた。概念は、500 文字までに切り詰める（API の上限 2048 文字に収める）。
- 翻訳が失敗したときは、日本語のテキストに戻さず、エラーにする（日本語に戻すと、同じ問題が起きるため）。
- 実際の API で、5種類のテキストを生成し、画像を見て確認した（例: 「スケジュール」→カレンダー、「予算」→お金の袋、「企画の背景」→鉢植えの芽）。

**汎用的な教訓**
- 外部の生成 AI を使う機能は、「API が成功した」ことと、「機能が目的を満たしている」ことを、別に確認する。出力の中身を、実際に見る。
- モデルの得意な言語や形式に合わせた、前処理（翻訳、整形）を、入力と生成の間に入れる。
- 入力の変換が失敗したときに、変換前の入力で、そのまま続行しない（品質の悪い結果を、静かに返さないため）。

### B4. タイムアウトが、応答の本文の読み込みを、保護していなかった

**発生する状況**
外部サービスが、応答のヘッダーを返した後で、本文を送らずに、止まったとき。

**問題**
タイムアウトが効かず、サーバーの処理が、いつまでも終わらない。ブラウザ側の画面は、生成の進行中を示す状態のまま止まり、同時に1件までの制限（二重実行の防止）のため、別の生成も、実行できなくなる。

**原因（詳細）**
- タイムアウトは、中断用の制御（`AbortController`）と、タイマー（`setTimeout`）で実装した。
- タイマーの解除（`clearTimeout`）は、`finally` ブロックに書いたが、そのブロックが囲んでいたのは、`fetch` の呼び出しだけだった。`fetch` は、ヘッダーを受け取った時点で完了するので、**その直後に、タイマーが解除**された。
- 本文の読み込み（`response.json()`）は、`try` の外にあり、タイマーの保護がなかった。

**修正**
- `fetch` と、本文の読み込みの両方を、1つの `try ... finally` で囲み、タイマーの解除を、本文の読み込みの後にした。
- 本文の読み込み中に時間切れになったときも、固定の文言で、上流のエラーにする。ただし、HTTP 429 は、ステータスだけで判定できるので、本文を読めなくても、無料枠の超過とする。
- テストは、ヘッダーはすぐに返るが、本文の読み込みが、中断されるまで終わらない、応答に似たオブジェクトを使い、偽のタイマーで時間を進めて検証した。

**汎用的な教訓**
タイムアウトは、**リクエストの開始から、本文の読み込みの完了まで**を、1つの単位として保護する。ヘッダーが返っても、本文は、まだ終わっていない。保護の範囲を、`try` ブロックの範囲で確認し、解除を、全体の完了後に置く。

### B5. 日本語以外の、日本語でないテキストまで、日本語として翻訳に回していた

**発生する状況**
「日本語かどうか」を、「ASCII 以外の文字を含むか」で判定したとき。

**問題**
絵文字だけのテキスト、アクセント付きの英字（`café`）、中国語・韓国語などが、すべて「日本語」として、日本語から英語への翻訳モデルに渡される。翻訳モデルが、空文字や、意味のない文字列を返すと、生成が失敗する（以前は、生成できたテキストが、失敗するようになる）。

**原因（詳細）**
- B3 の修正で、「ASCII だけのテキストは、翻訳しない」という規則を導入した。この規則は、「ASCII 以外 = 日本語」という暗黙の仮定に基づいていた。
- 翻訳モデルの入力言語は、「日本語」に固定されている。日本語でない、ASCII 以外のテキストは、想定外の入力になる。

**修正**
- 「日本語の文字（ひらがな、カタカナ、漢字、全角形、半角カタカナ）を含むときだけ」翻訳する規則に変えた（Unicode の文字種のプロパティを使った正規表現）。ほかは、そのまま使う。
- 「絵文字だけ」「`café`」「英語」「数字」「空文字」は翻訳しない、「混在（`AI予算`）」「全角英字」「半角カタカナ」は翻訳する、というテストで、境界を固定した。
- 漢字は、中国語にも使われるが、日本語として翻訳する（許容する制限として記録）。

**汎用的な教訓**
前処理の「適用条件」は、「対象の性質」を、肯定的に定義する（「日本語の文字を含む」）。「それ以外ではない」という否定的な定義（「ASCII でない」）は、想定外の入力を、巻き込む。

### B6. 状態を、識別子だけで管理して、世代の違う対象と混ざった

**発生する状況**
非同期処理の結果（生成した画像）を、「ノードの識別子」だけで、対象のノードに結び付け、その識別子の採番が、リセットされる操作（別のマップの読み込み）があるとき。

**問題**
次の流れで、誤った画像が表示される。
1. ノード 1（「予算」）で、イラストを生成する。
2. 別のマップを、JSON で読み込む（ノードの識別子は、1 から振り直される）。
3. 新しいマップのノード 1（「旅行」）を選ぶと、**「旅行のイラスト」という説明で、お金の袋の画像**が表示される。

生成中に、マップを読み込んだ場合は、進行中を示すロックが残り、ボタンが、最大で約 210 秒、無効のままになる。完了後は、結果が、新しいマップのノードに付く。

**原因（詳細）**
1. 生成の状態は、`nodeId`（ノードの識別子）だけで、対象のノードを識別していた。
2. ノードの識別子は、同じマップの中では、単調に増え、削除しても再利用されない。一方、マップを置き換える操作（`replaceMap`）は、採番を、1 から振り直す。読み込んだマップの識別子も、1 から始まるのが普通。
3. つまり、「識別子は、一意」という前提が、**マップの世代をまたぐと、成り立たない**。
4. 進行中のリクエストは、世代が変わっても、中断されず、ロック（進行中を示す参照）も、解除されなかった。

**修正**
- 既存の仕組み（マップの置き換えごとに増える `resetRevision`）を使い、`useIllustrationGeneration(nodes, resetRevision)` が、状態を保存するときに、その時点の世代を添える。
- 返す状態は、世代が現在と同じときだけ。違えば、`idle`（何も無い状態）として扱う（描画中に導出するので、effect の中で状態を更新しない）。
- 世代が変わったときは、進行中のリクエストを中断し、ロックを解除する（初回のマウント時は、何もしない）。
- 遅れて届く、中断済みのリクエストの結果は、既存の中断の確認で無視される。
- テストは、成功・失敗・生成中の各状態で、世代を上げたときの挙動（状態の破棄、中断、遅れた応答を無視する、すぐに新しい生成を受け付ける）と、ページが世代を渡すことを、検証した。修正前は、6件のテストが失敗することを確認した。
- 補足: React Compiler のルール（描画中に ref を読まない）のため、状態を保存する関数が、世代を依存に持ち、生成の入口の関数の参照が、世代が変わると変わる。この関数は、イベントハンドラの中でだけ使われるので、再実行などの副作用はない。

**汎用的な教訓**
- 非同期処理の結果や、画面の状態を、「識別子」で対象に結び付けるとき、**識別子の再利用や、採番のリセット**がないかを確認する。
- 識別子が、世代をまたいで、再利用されうるなら、状態に「世代」を添え、世代が違う状態を、無効として扱う。同時に、進行中の処理を、世代の変化で中断する。
- 次の機能（生成結果を、ノードに紐付けて保存する）で、この状態を土台にするときに、誤った紐付けを生まないための、先行する修正でもある。

### B7. 設定ファイルの見本が、無視される設定に、巻き込まれた

**発生する状況**
環境変数の見本ファイル（`.env.example`）を、リポジトリに入れようとしたとき、アプリのフォルダの `.gitignore` が、`.env*` を、まとめて無視していたとき。

**問題**
`.env.example` が、Git に追跡されず、リポジトリに入らない（利用者が、見本を入手できない）。

**原因（詳細）**
- 計画の段階で、リポジトリ直下の `.gitignore` にある、`client/.env*.local` だけを読み、「`.local` の付くファイルだけが無視される」と想定した。
- アプリのフォルダ（`client/`）に、別の `.gitignore`（Next.js の標準の設定）があり、そこに `.env*` があることを、確認しなかった（出力を途中で切って読んだため）。
- 実装者が、実際にファイルを追加し、`git check-ignore` で確認して、想定が違うことに気付いた。

**修正**
- アプリのフォルダの `.gitignore` に、`!.env.example`（例外）を追加した。`.env`、`.env.local`、`.env.production` などが、引き続き無視され、`.env.example` だけが追跡されることを確認した。

**汎用的な教訓**
無視の設定は、リポジトリの階層ごとに、複数のファイルが影響する。新しい種類のファイルを追加するときは、`git check-ignore` で、実際の結果を確認する（想定ではなく）。

### B8. 秘密を、誤った場所・形式で保存した（利用者の設定ミス）

**発生する状況**
利用者が、環境変数のファイルを、手順書とは違う場所（リポジトリの直下）に、「名前=値」の形式ではなく、値だけの1行で作ったとき。

**問題**
- アプリは、アプリのフォルダ（`client/`）の設定ファイルしか読まないので、設定が反映されない。
- リポジトリ直下の `.env.local` は、**Git に無視されていなかった**。秘密の値が入ったファイルが、未追跡ファイルとして見え、誤ってコミットされる危険があった。

**原因（詳細）**
- 手順書は、「`client` フォルダで、見本をコピーして、`.env.local` を作る」と書いていたが、利用者にとって、「設定ファイルを作る」の「どこで」は、見落としやすい。
- リポジトリ直下の `.gitignore` に、`client/.env*.local` だけがあり、直下の `.env.local` は、対象外だった。
- 値だけを貼り付けたファイルは、キー名が無いので、形式の検証が必要だった。

**対応**
- 利用者が作った設定ファイルの中身は、**読まない**。ファイルの有無、行数、キー名、値の長さ（文字数）、前後の空白・引用符の有無だけを、値を表示せずに確認した。
- 誤った場所のファイルを、利用者が削除するよう、案内した。正しい場所のファイルは、見本のコピー（値は空）を、先に作っておいた。
- 設定ファイルの形式（アカウント ID が 32 文字、トークンが 53 文字など）が、想定の範囲か、値を出さずに確認した。

**汎用的な教訓**
- 手順書は、「どのフォルダで」実行するかを、各コマンドの直前に明記する。コマンドは、絶対パス付きの形で書く。
- 秘密を含むファイルが、誤った場所に作られても、Git に載らないように、無視の設定を、リポジトリの直下にも用意することを検討する。
- 秘密の検証は、「値を表示しない」方法で行う（長さ、形式、空かどうか）。

### B9. 無料枠の超過のメッセージが、実際の原因より、断定的だった

**発生する状況**
HTTP 429（リクエストが多すぎる）を、すべて「今日の無料枠を使い切った」と表示したとき。

**問題**
429 は、1日の無料枠の超過だけでなく、一時的な頻度の制限でも返りうる。利用者が、「今日は、もう使えない」と誤解する。

**原因**
実装が、429 を、無料枠の超過として、一律に扱っていた。さらに、エラー文に「limit」などの語を含む、HTTP 200 番台でない応答を、無料枠の超過とする規則があり、無関係な 5xx を、同様に扱う可能性があった（計画の規則に従った実装で、明確な誤りではないと判断した）。

**修正**
メッセージを、「無料の利用上限に達しました（1日の無料枠を使い切ったか、一時的な制限です）。時間をおいて（無料枠は毎日 0:00 UTC にリセット）、再度お試しください」に変えた。

**汎用的な教訓**
外部サービスのエラーの原因が、複数ありうるとき、メッセージは、断定せずに、考えられる原因を並べる。

## 3. テストの指摘

### T1. 変異に耐えないテスト（応答の分岐、規則の優先順位）

**発生する状況**
「コードの分岐を消したり、判定の順序を入れ替えても、テストが通ってしまう」とき。

**問題**
- 「HTTP 200 なのに、`success: false` で、不適切な内容のコード」という応答を、専用のエラーとして扱う分岐を、消しても、テストが落ちない。
- 「不適切な内容」の判定を、「無料枠」の判定より先に置く順序を、入れ替えても、テストが落ちない。

**原因（詳細）**
- 既存のテストは、実際に観測された応答（HTTP 400 で、不適切な内容）だけを、使っていた。
- この実際のメッセージは、無料枠の判定の正規表現に、たまたま、一致しなかった。そのため、順序を入れ替えても、結果が変わらず、順序の効果を検証できなかった。
- 「HTTP 200 で失敗」という分岐は、実際の観測にはなかったが、コードには、防御として書かれていた。

**修正**
- 2件のテストを追加した。(a) HTTP 200 + `success: false` + コード 8007 → 不適切な内容。(b) HTTP 400 + コード 8007 で、メッセージに「limit」を含む → 無料枠ではなく、不適切な内容（順序を固定）。
- 実装を、実際に壊して（(a) の条件から `success` の判定を外す、(b) 規則の順序を入れ替える）、新しいテストが失敗することを確認し、元に戻したことを、控えとの比較で確認した。

**汎用的な教訓**
複数の規則を、順序で優先する実装は、「両方に当てはまる入力」を使った、順序の検証が必要。防御的な分岐は、その分岐だけが処理する入力で、テストする。確認は、変異で行う。

### T2. 実態とずれたテストの名前（アンマウント後に、状態を更新しない）

**発生する状況**
テストの名前が、「アンマウント後に、状態を更新しないこと」を主張するが、実際には、それを検証できていないとき。

**問題**
`console.error` を監視して、呼ばれないことを確認していたが、React 19 は、アンマウント後の状態の更新を、警告しない。この確認は、何も証明しない。実際に検証できているのは、「リクエストが中断されたこと」だけ。

**原因（詳細）**
- 以前のバージョンの React では、アンマウント後の状態の更新に、警告が出たため、その警告の有無が、検証の代わりになった。
- 現在のバージョンでは、警告が廃止されたので、検証の根拠が、失われていた。
- 「中断された後の結果を無視する」ための、条件分岐は、描画の結果として観測できない（アンマウント後の更新は、無視されるため）。

**修正**
- 監視を削除し、名前を、実際に検証していること（進行中のリクエストを中断する）に合わせた。
- 加えて、「最後に描画された状態が変わらない」ことを確認した。ただし、実装の条件分岐を、取り除く変異でも、テストが通る（描画からは、観測できない）ことを確かめ、報告に正直に書いた。

**汎用的な教訓**
テストの名前が主張する内容と、実際に検証できる内容を、一致させる。観測できない保証は、「テストで保証した」と書かない。

### T3. 偽の `fetch` と、実環境の違い（テストの環境、タイマー）

**発生する状況**
- ブラウザ向けのテスト環境（`jsdom`）に、`Response` が無い。
- 時間切れを、`AbortSignal.timeout` で実装すると、偽のタイマーで、時間を進められない。

**問題**
`Response` が無く、テストが、`ReferenceError` で失敗する。タイマーのテストを、書けない。

**修正**
- サーバー側と、`Response` を使うクライアントのテストの先頭に、`/** @jest-environment node */` を書いた。
- 時間切れは、`AbortController` と `setTimeout` で実装し、偽のタイマーで時間を進めて検証した。タイマーが、完了後に残らないこと（`jest.getTimerCount()` が 0）も確認した。

**汎用的な教訓**
テストしやすい実装（タイマーを差し替えられる、`fetch` を注入できる）を選ぶ。テスト環境の制約は、先に確認する。

### T4. 秘密の漏洩を検証するテストは、すべての失敗の経路を通す

**状況**
エラーの文言に、トークンを含めないことを確認するテストが、1つの経路（上流が返したエラー）しか通っていなかった。実際には、`fetch` が投げた例外の文言に、トークンが含まれる経路が、最も危険だった。

**修正**
2つの経路（HTTP エラーの応答、`fetch` の例外の文言にトークンが含まれる場合）の両方を検証するテストにした。固定の文言だけを返し、元の例外を、原因（`cause`）に付けない実装も、確認した。

**汎用的な教訓**
漏洩の検証は、「漏れうる、すべての経路」で行う。意図的に、トークンを含む例外を投げて、実装がそれを、転記しないことを確かめる。

## 4. ドキュメント・PR 本文の指摘

### D1. 利用者がそのまま開く URL の綴りの誤り（セキュリティ）

**発生する状況**
利用者向けの手順書に、外部サービスのサインアップの URL を、手で書いたとき。

**問題**
`https://dashloudflare.com/sign-up`（正しくは `https://dash.cloudflare.com/sign-up`）と、`.` が1つ抜けていた。別のドメインを開くことになり、メールアドレスとパスワードを入力するページなので、**偽サイトによる認証情報の窃取**につながるおそれがあった。

**原因（詳細）**
- 文書を、手で書き、URL を、機械的に検証する仕組みが、なかった。
- README の同じ URL は正しく、同じ内容が、2つの文書で、別々に書かれていた。
- 実装を確認するレビュー（コードの読解）では、利用者向けの手順書の細部が、見落とされやすい。

**修正**
- 正しい URL に直し、手順書と README の、すべての URL を、1文字ずつ確認した（含まれるホストは、正規のものだけ）。
- 2人目のレビュアーにも、「すべての URL を、1文字ずつ照合する」ことを、依頼の項目に加えた。

**汎用的な教訓**
利用者が、認証情報を入力するページへの URL は、セキュリティ上、特に慎重に確認する。ドメイン名の末尾が、正規のものであるかを、機械的に検査する（`grep` で、文書内のホストを抽出し、許可するホストの一覧と、突き合わせる）。

### D2. 手順書の例が、コードの修正に追従しなかった

**発生する状況**
コードの不具合を直した後、その不具合を前提にした、文書の例（コマンド）が、更新されなかったとき。

**問題**
手順書の `curl` の例が、実際の API が拒否する `seed` を、送り続けた。利用者が、手順どおりに実行すると、正しい認証情報でも、HTTP 400 で失敗する。手順書の次の手順（画像の取り出し）も、`KeyError` で失敗する。利用者は、表の案内に従い、トークンを作り直すなど、**原因を誤って判断する**。

**原因（詳細）**
- `seed` を外す修正で、手順書を更新するよう依頼したが、手順書には、同じ `curl` の例が、複数あったか、編集が、別の箇所に当たった。修正者の報告は、「手順書から外した」だったが、実際には、1か所が残っていた。
- 修正後に、文書内の `seed` を、`grep` で網羅的に確認していなかった。

**修正**
- 本文を `{"prompt":"…","steps":4}` だけにした。「うまくいかないとき」に、不適切な内容の誤判定（コード 8007）は、ランダムなので、再実行する案内を追加した。
- 両方の文書で、`seed` が、残っていないことを、`grep` で確認した。

**汎用的な教訓**
- コードの挙動を直したら、その挙動を前提にした、文書、例、コマンドを、`grep` で、すべて探して直す。
- 手順書のコマンドは、実際に実行して、動くことを確認する。

### D3. 同じ内容を、2つの文書で、別々の情報として書いた

**発生する状況**
README と手順書の両方に、無料枠の消費量を書き、片方だけが、実測値に更新されたとき。

**問題**
手順書は、「1日に生成できる枚数は、確認できていない」と書いたまま、README は、「実測で、1枚 172.8 Neurons、約 57 枚/日」と書いた。手順書だけを読む利用者に、古い情報が伝わる。

**原因**
無料枠の測定は、実装の後半で行われ、README は、そのときに更新されたが、手順書は、更新の対象から漏れた。同じ情報が、複数の文書に、書き写されていた。

**修正**
手順書の記述を、README と同じ実測値（測定日、変わりうること、再試行の分も消費しうること）に書き換えた。

**汎用的な教訓**
同じ事実を、複数の文書に書くときは、1か所を正本にし、他は、リンクにする。書き写すなら、更新の対象の一覧に、すべての文書を入れる。

### D4. 文書が、存在しない挙動を説明し、実際のメッセージと食い違った

**発生する状況**
手順書の「困ったとき」の表や説明が、実装を確認せずに、想像で書かれたとき。

**問題**
- 「60 秒たっても返らないときは、時間切れのメッセージが出ます」と書かれていたが、時間切れ専用のメッセージは、存在せず、「イラストの生成に失敗しました」と表示される。
- 時間切れは、呼び出しごと（翻訳 30 秒、生成 60 秒）で、再試行を含めると、最大で約 210 秒かかる。「60 秒」では終わらない。
- 画面に出る、不適切な内容のメッセージが、表になかった。

**原因**
手順書を、機能の実装の完了前に書き、画面に出る実際の文言を、コードから転記しなかった。後続の変更（再試行、翻訳の追加）で、挙動が変わった。

**修正**
時間切れの説明を、実際の挙動に直し、不適切な内容のメッセージの行を、実際の文言どおりに表へ追加した。

**汎用的な教訓**
画面のメッセージを、文書に書くときは、コードの定数から転記する（レビューで、文書の文言と、コードの定数を、1文字ずつ照合する）。

### D5. 手順の細部の誤りが、利用者の秘密を失わせうる

**問題と原因**
- 手順書が、「`cp .env.example .env.local`」と案内していた。`.env.local` が、すでにあると、確認なしに、空の見本で上書きされ、**設定済みのトークンが消える**。トークンは、1度しか表示されないので、作り直しになる。
- 手順書の、クレジットカードの登録を求められたときの案内が、「6. 困ったとき」を参照するとしていたが、その節は「7」で、しかも、該当する案内がなかった。

**修正**
- `cp -n`（既存のファイルを上書きしない）にし、「すでにあるときは、コピーを飛ばし、値があるかだけを確認する」と書いた。
- 参照を直し、案内（進めずに止め、料金ページで、Free プランであることを確認する）を、実際に追加した。

**汎用的な教訓**
利用者の手元のデータ（秘密、設定）を、破壊しうるコマンドは、上書きを防ぐ形にする。文書内の参照（節の番号）は、移動や追加のたびに、確認する。

### D6. 回数の表現が、実装と食い違った（再試行の回数）

**問題と原因**
文書と PR 本文が、「最大 3 回まで再試行」と書いたが、実装の定数（`MAX_GENERATION_ATTEMPTS = 3`）は、**最初の1回を含む試行の合計**で、再試行は最大 2 回。無料枠の消費の見積もりが、ずれる表現だった。「回数」を、「試行の合計」と「再試行の回数」のどちらで数えるかが、書き手の頭の中で、混ざっていた。

**修正**
「自動で再試行し、生成は最大 3 回まで試す（再試行は最大 2 回）」に統一した。

**汎用的な教訓**
回数を書くときは、「合計」か「追加」かを、明記する。数値は、実装の定数と、突き合わせる。

### D7. PR 本文の細部が、実装と食い違った

**問題**
- 「時間切れ 60 秒は、画像生成と翻訳で共通」とあったが、翻訳は 30 秒、画像生成は 60 秒。
- 「パネルに『生成中…』と表示する」とあったが、パネルの状態表示は「生成中です」で、「生成中…」は、ボタンの文言。

**原因**
本文を、実装の途中の理解で書き、最終的な値や文言を、コードから転記しなかった（前回までの整理の D1、D2 と同種）。

**修正**
本文を訂正した。

**汎用的な教訓**
PR 本文の、数値と画面の文言は、最終的なコードから転記する。

### D8. 履歴として残した計画書に、古い表現が残った

**問題と原因**
実装計画に、古い再試行の表現が、1か所残り、同じファイルの別の箇所が、「その表現を直した」と書いていたので、矛盾して読めた。履歴としての文書は、残してよいが、最終的な挙動を誤解させる記述は、注記か修正が必要。

**修正**
該当の1か所を、最終的な挙動に直した。

**汎用的な教訓**
履歴の文書でも、「最終的な状態を、誤解させる記述」は、直す（または、注記する）。

### D9. 対応しなかった指摘（根拠の記録）

| 指摘 | 判断の根拠 |
|---|---|
| 手順書に、個人の絶対パス（`/Users/...`）が、書かれている | 現状は、リポジトリの所有者本人が、自分のパソコンで使う前提。絶対パスは、そのまま実行できる利点がある。共同開発や公開のときに、相対パスに直す |
| 生成中に、右クリックメニューの項目を選んでも、何も表示されない | 同時に1件までという仕様どおり。生成中は、右パネルのボタンが「生成中…」で無効になり、状態が分かる。メニュー項目の無効化は、見た目の改善の範囲（YAGNI） |
| API ルートに、認証、アクセス元（Origin）の確認、レート制限、本文サイズの上限がない | ローカルでの1人利用が前提で、被害は、無料枠の消費だけ。README と手順書に、「公開しない」「公開前に、これらの追加が必須」と明記した |
| ブラウザが中断しても、サーバーが、上流（翻訳と最大3回の生成）の呼び出しを続ける | ローカルの1人利用で、頻度が低く、影響は、無料枠の数枚分。README に制限として明記した |
| 不適切な内容で拒否されて再試行した分が、無料枠を消費するか、未確認 | 確認する手段がない（公式ドキュメントに記載なし）。最悪の見積もり（1回の操作で、3回分）を、README に書いた |
| 漢字は、中国語にも使われるが、日本語として翻訳する | 日本語のアプリで、許容できる制限 |
| 生成結果が、毎回変わり、意図と離れた絵や、被写体が小さい絵になる | 生成 AI の性質。プロンプトの工夫で改善した（被写体を大きく）が、完全には制御できない |

## 5. 作業手順（プロセス）の学び

### P1. 実際の API を呼ぶ確認は、レビューやテストの代わりにならない（そして逆も）

**状況**
実装の各タスクのレビュー、最終レビュー、再レビューは、すべて承認された。単体テストも、すべて通った。しかし、実際の API を呼ぶと、**3つの、機能を壊す問題**（B1 の `seed`、B2 の確率的な拒否、B3 の文字が描かれる）が、見つかった。

**原因**
- テストは、偽の `fetch` を使い、書いた人の仮定を映す。レビューは、コードと計画書を読む。どちらも、「外部サービスの、実際の挙動」を知る手段を持たない。
- 認証情報を持たないエージェントは、実際の API を呼べない。実際の呼び出しは、認証情報を持つ利用者の環境で、利用者の許可のもとで、行うしかない。

**対策**
- 外部 API を使う機能は、実装の早い段階で、利用者の認証情報を使い、実際の API を、最小限（1〜数回）呼び、(1) リクエストの形、(2) レスポンスの形、(3) エラーの種類、(4) 出力の中身（画像なら、実際に見る）を確認する。
- 確認で見つかった事実（拒否される項目、エラーコード、消費量）を、テストと文書に、固定する。
- 確認は、無料枠や課金の消費を、最小限にして、行う。

### P2. 秘密の扱い: 値を見ずに、確認する

**状況**
診断のために、利用者の認証情報を使って、外部サービスを呼ぶ必要があった。

**やり方（安全に診断する）**
- 設定ファイルは、プログラムの中で読み込み、値を、**画面にも、ログにも、報告にも、出さない**。
- 表示するのは、HTTP のステータスと、サービスが返すエラーの内容（コードとメッセージ。秘密ではない）だけ。例外のメッセージを表示するときは、トークンを、伏せ字に置き換える。
- 設定の形式の検証は、長さ、空かどうか、前後の空白、引用符の有無で行う。
- 誤った場所に作られたファイルは、中身を読まずに、「値だけの1行か、`名前=値` の形か」を、構造（`=` の有無）で判断する。
- コミットの前に、トークンとアカウント ID が、コミット対象のファイルに含まれていないことを、機械的に検索する。
- 利用者には、トークンを、チャットに貼らないよう、念を押す。

**汎用的な教訓**
秘密を扱う診断は、「秘密を、人間にも、ログにも、見せない」設計で行う。診断のために、利用者の認証情報を使うことは、目的の範囲を、利用者に伝えたうえで行う。

### P3. 情報源の信頼度: ブログより公式、公式より実測

**状況**
画像生成の提供元を、従量課金にならないものから選ぶ調査で、複数のブログが、「Google の画像モデルは、1日 500 枚が無料」と述べていた。

**確認**
公式の料金ページで確認すると、画像生成モデルは、すべて無料枠の対象外（有料のみ）だった。ブログの記述は、公式と食い違っていた。さらに、採用した提供元でも、公式ページの記述（`seed` が必須）が、実際の API と食い違った（B1）。

**対策**
- 比較・選定は、公式のページを、直接確認して行う。ブログの要約は、手がかりにとどめる。
- 数値（1枚あたりの消費量）は、実測する。応答に、使用量（`usage.neurons`）が含まれていたので、実測の根拠になった（172.8 Neurons/枚、1日あたり約 57 枚）。実測値には、測定日と、「変わりうる」の注記を付ける。

### P4. レビューのレンズに、「利用者向けの文書の校正」を加える

**状況**
1回目のレビューは、利用者向けの手順書の、URL の誤りと、実際の API が拒否するコマンドを見つけた。依頼文に、「文書の例が、コードの実際の送信内容と一致するか」と「文書内のエラー文言が、コードの文字列と一致するか」を、含めていたため。2人目の確認者の依頼文には、「すべての URL、コマンド、環境変数名、画面の文字列を、1文字ずつ照合する」を加え、追加の誤り（節の番号、上書きされる `cp`、回数の表現）が見つかった。

**対策**
レビューの依頼に、(1) コードの正しさ、(2) テストの強さ（変異）、(3) PR 本文の事実確認、(4) **利用者向け文書の校正（URL、コマンド、文言、参照）**、(5) 秘密の検査、(6) ルール文書との整合、(7) コミットの体裁、を、最初から含める。

### P5. コミットの体裁: trailer の確認

**状況**
コミットのメッセージを、後から修正したとき（共著者の行を、指定の文言に直す操作）、件名と共著者の行の間に、空行が入らず、共著者の行が、件名の一部になった。Git は、これを、trailer として認識しない。最終レビューで指摘された。

**原因**
メッセージの置換を、既存のメッセージの文字列に対して行い、元のメッセージの形（空行の有無）を、確認しなかった。

**修正**
未 push のブランチだったので、コミットを、作業ツリーに触れない方法で、メッセージだけ作り直した（内容のツリーは、同一）。以降のコミットは、「件名、空行、trailer」の形で作り、`git interpret-trailers --parse` で、認識されることを確認した。

**補足（サブエージェントの trailer）**
サブエージェントが、指定の共著者の行ではなく、自分のモデル名を書いたことがあった。依頼文に、「この文字列を、そのまま書く」と明記し、コミット後に、確認する。

**汎用的な教訓**
コミットのメッセージを書き換えたら、trailer が認識されることを、コマンドで確認する。公開前のコミットの修正は、安全にできるが、公開後は、避ける。

### P6. 計画と実際のずれは、計画書に残す

**状況**
実装計画は、`seed` を送る、翻訳なしで日本語を渡す、という前提で書かれていた。実際の API で、前提が崩れ、計画と実装が、離れた。

**対策**
計画書の末尾に、「実装後の変更」の節を設け、変更の理由と最終的な形（B1〜B5、B6、D2〜D6 の修正）を、追記した。当初案は、履歴として残し、誤解を生む箇所には、注記した（D8）。

## 6. 汎用チェックリスト（外部 API を、自分のサーバーから呼ぶ機能を作るとき）

### 設計・構造
- [ ] 認証情報は、サーバーの環境変数だけが持ち、ブラウザに渡らないか。エラー、ログ、レスポンス、テストのデータ、文書に、含まれないか。
- [ ] 外部呼び出しの共通処理（認証、タイムアウト、エラーの分類、機密の扱い）が、呼び出し先ごとに、重複していないか。依存の向きは、一方向か。
- [ ] 入力は、ブラウザ側とサーバー側の両方で検証したか（型、長さ、空）。検証は、設定の確認より先か。
- [ ] 環境変数から作る URL の部品を、検証したか。

### 挙動（実際の API で確認する）
- [ ] 実装の早い段階で、実際の API を最小限（1〜数回）呼び、リクエストとレスポンスの形を確認したか。ドキュメントの記述だけを、根拠にしていないか。
- [ ] 同じ入力で、複数回、呼び、結果が一定か（確率的な拒否、安全フィルタ）。
- [ ] 生成物の中身を、実際に見たか（API の成功は、目的の達成ではない）。モデルの得意な言語・形式に、入力を整えたか。
- [ ] 前処理（翻訳など）の適用条件は、肯定的に定義したか。失敗時に、元の入力で、静かに続行していないか。
- [ ] タイムアウトは、リクエストの開始から、本文の読み込みの完了までを保護しているか。
- [ ] 非同期の結果を、識別子で対象に結び付けるとき、識別子の再利用や、採番のリセットがないか。世代を添えたか。進行中の処理は、世代の変化で中断されるか。
- [ ] 無料枠、レート制限、不適切な内容の拒否、設定なし、通信失敗に、それぞれ、利用者向けのメッセージがあるか（原因が複数ありうるときは、断定していないか）。
- [ ] 新しい種類のファイル（`.env.example` など）が、`git check-ignore` で、期待どおりに扱われるか。

### テスト
- [ ] 実際のネットワーク呼び出しを、していないか。テストの環境（`jsdom` か `node` か）は、適切か。タイマーを、偽のタイマーで進められる実装か。
- [ ] リクエストの本文のキーを、実際の API で確認した値に、完全一致で固定したか。
- [ ] 規則の優先順位を、両方に当てはまる入力で検証したか。防御的な分岐を、その分岐だけが処理する入力で検証したか。実装を壊して（変異）、落ちることを確認したか。
- [ ] 漏洩の検証は、漏れうるすべての経路（例外の文言を含む）を通したか。
- [ ] テストの名前が、実際に検証していることと一致しているか（観測できない保証を、主張していないか）。

### ドキュメント・PR
- [ ] 利用者が、認証情報を入力するページへの URL を、1文字ずつ確認したか。文書内のホストを、許可する一覧と突き合わせたか。
- [ ] 手順書のコマンドは、実際に実行して動くか。コードの挙動を直したら、文書の例を、`grep` で全件、直したか。
- [ ] 手順書の画面のメッセージは、コードの定数から転記したか。節の参照は、正しいか。
- [ ] 利用者の手元のデータ（設定、秘密）を、壊しうるコマンド（上書き）は、防止されているか。
- [ ] 回数は、「合計」か「追加」かを明記したか。数値は、実装の定数と一致しているか。
- [ ] 同じ事実を、複数の文書に書いていないか（書くなら、正本を1つにし、他はリンク）。
- [ ] PR 本文の数値と画面の文言は、最終的なコードから転記したか。
- [ ] 公開してはいけない前提（認証がない、など）を、README と手順書に、明記したか。

### 作業手順
- [ ] 診断のために、秘密を使うとき、値を表示せず、ステータスとエラーの内容だけを出したか。コミットの前に、秘密が混ざっていないか、機械的に検索したか。
- [ ] 提供元の選定は、公式ページで確認したか。数値は、実測し、測定日と注記を付けたか。
- [ ] コミットの trailer が、`git interpret-trailers --parse` で認識されるか。
- [ ] 計画と実際がずれたら、計画書の「実装後の変更」に、理由と最終的な形を書いたか。
- [ ] レビューの依頼に、コード、テスト（変異）、PR 本文、利用者向け文書の校正、秘密の検査、ルール文書との整合、コミットの体裁、のレンズを入れたか。
