# レビュー指摘の整理: 側面パネル（右パネル）と共有ルールの実装

対象: PR #14「右パネルにイラスト生成ボタンを配置し、生成の入口を共有する」で行った、実画面での確認、ローカルのレビューループ（単一責任の確認2ラウンド、正しさ・テストの確認2ラウンド）、PR 上のレビュー（2回）で指摘・発見された内容。

目的: 個別の機能に依存しない形で、「どういう時に」「どんな問題が起き」「なぜ起きたか」「どう直したか」を残し、同種の機能（既存の画面に、別の表示面〈パネル、ステータス、ツールチップなど〉を追加し、既存の表示面と同じ情報を見せる機能）を作るときのレビュー観点として再利用する。

前回の整理（`2026-10-02-overlay-menu-review-findings.md`）の項目と重なる学びは、重複して書かず、項目 ID で参照する。

## 読み方

- 各項目は「発生する状況」「問題」「原因」「修正」「汎用的な教訓」の順で書く。
- 項目 ID の頭文字は分類を表す。**S**: 単一責任・構造、**B**: 挙動・不具合、**T**: テスト、**D**: ドキュメント・PR 本文、**P**: レビューの進め方。
- 「対応しない」と判断した項目も、判断の根拠ごと記録する（同じ指摘が再度出たときに、議論を繰り返さないため）。

## 全体像

| 区分 | 件数 | 主な傾向 |
|---|---|---|
| 構造（S） | 3 | 「規則」の重複（共有されていたのは定数だけ）、配線の部品に、レイアウトの CSS が混在 |
| 挙動（B） | 2 | 別の表示面と、同じ状態の表示がずれる（実画面でのみ発見）、レビューの観点の盲点 |
| テスト（T） | 3 | 変異に耐えるテストの不足、冗長なアサーション、移動後の所有者 |
| ドキュメント（D） | 4 | PR 本文の基準のずれ（再発）、計画書と最終コードのずれ、ランドマーク構造 |
| プロセス（P） | 4 | レビューのレンズの追加が効いた、レビュー同士の事実の食い違い、補助スクリプトのパス |

## 1. 構造（単一責任）の指摘

### S1. 「ラベルが空なら代替文言」という規則が、3か所に重複していた

**発生する状況**
同じ情報（ノードの表示名）を、複数の表示面（キャンバスの描画、画像エクスポート、新設したパネル）で見せるとき。表示のための小さな規則（「空のときは代替の文言を出す」）を、それぞれの表示面が、自分で実装したとき。

**問題**
規則の条件（いつ置き換えるか）が3か所に分かれる。たとえば、空白だけのラベルを「空」とみなす（`trim()` する）方針に変えたとき、1か所だけを直すと、表示面ごとに表示が食い違う。これは、最初に実画面で見つかった問題（B1）と同じ種類の不整合を、再び生む。

**原因（詳細）**
1. 最初の実装では、パネルが、独自の文言「（ラベルなし）」を使っていた（B1）。
2. B1 の修正で、3か所が同じ文言を使うように、共通の定数 `FALLBACK_NODE_LABEL` を導入した。ここで解消されたのは「文言が3か所で違う」ことだけだった。
3. 規則そのもの、つまり「`label || FALLBACK_NODE_LABEL`」という式（条件と代替の組）は、3か所にそれぞれ書かれたまま残った。定数を共有しても、「いつ置き換えるか」という判断は共有されない。
4. この規則には、暗黙の決定が含まれる。それは「空文字だけを置き換え、空白だけのラベルは置き換えない」という点で、`||` が文字列の真偽（空文字だけが偽）で判定する性質に依存している。この決定は、どこにも名前が付いておらず、テストでも固定されていなかった。

**修正**
- 純粋関数 `getNodeDisplayLabel(label)`（`domain/nodes/nodeDisplayLabel.ts`）に、規則を集約した。3か所は、この関数を呼ぶだけにした。
- 暗黙の決定を、関数のテストで固定した（空文字は代替、通常の文字列はそのまま、空白だけは置き換えない、代替文言と同じ文字列もそのまま）。
- 画像エクスポートでは、「代替文言への置き換え」の後に、XML 向けの正規化を行う順序を、変更していない。

**汎用的な教訓**
- 「値」（文言の定数）の共有と、「規則」（いつその値を使うか）の共有は別。複数の表示面で同じ情報を見せるなら、規則を関数にして、1か所に置く。
- 規則が暗黙に依存している言語仕様（`||` の真偽判定など）は、テストで明示的に固定する。
- 例外として、規則が似て見えても、別の目的のものは共通化しない。たとえば、編集欄の初期値は、生のラベルを使う（代替文言を入れると、「新しいノード」が確定した文字として保存されてしまう）。`title` 属性（空のとき付けない）も、表示の代替とは別の規則。

### S2. 配線の部品に、レイアウトの CSS が混在していた

**発生する状況**
アプリ全体を組み立てる部品（ここではページ）に、画面の領域を並べるための CSS（`flex`、`min-w-0`、`flex-1` など）を、直接書いたとき。

**問題**
- ページが、「何を何につなぐか」（配線）と、「どう並べるか」（レイアウト）の2つの変更理由を持つ。
- ページのテストが、CSS クラスの有無（レイアウトの詳細）を検証することになり、レイアウトを直しただけで、配線のテストが落ちる。逆に、レイアウトの回帰を検知したいのに、重い配線のモックを必要とするテストでしか、検証できない。

**原因（詳細）**
- パネルの追加は、「ページの `<main>` の中を、キャンバスだけから、キャンバスとパネルの2つへ変える」変更だった。最短の実装は、ページに `flex` のラッパーを書き足すこと。
- 既に、ヘッダー（`AppHeader`）には、`ReactNode` のスロットを受け取る部品にするという前例があった。しかし、パネルの追加の時点では、その前例が参照されなかった。
- テストも、実装の置き場所に従い、ページのテストにクラスの検証を足した。

**修正**
- `AppWorkspace`（`canvas` と `sidePanel` のスロットを受け取る部品）に、レイアウトを分離した。DOM とクラスは、分離の前後で同一。
- クラスの検証を、持ち主の部品のテストへ移した。レイアウトの枠は `AppWorkspace` のテスト、パネルの固定幅（`w-60 shrink-0`）は `IllustrationPanel` のテスト。
- ページのテストは、配線（`main` の中に、キャンバスとパネルが、同じ作業領域として含まれること）の検証だけにした。

**汎用的な教訓**
組み立ての部品（ページ、ルート）は、配線だけを持つ。領域を並べる CSS は、スロットを受け取るレイアウト部品へ。テストは、持ち主の部品に置き、組み立ての部品のテストは「つながっていること」だけにする。

### S3. 対応しなかった構造の指摘（根拠の記録）

| 指摘 | 判断の根拠 |
|---|---|
| 生成の入口（`useIllustrationGeneration`）が、1つの関数だけを返す小さなフックである | 入口が1つであることが設計の意図。後続の項目で、中身を置き換える1か所になる。分割すると、むしろ入口が分散する |
| パネルの「対象ノードの表示」と「生成ボタン」を、別の部品に分ける | 41行で、分割しても利用者が増えない（YAGNI）。状態は「ノードが選択されているか」の1つだけで、3つの分岐は、同じ条件を参照している |
| 定数（`config/nodeLabel.ts`）と関数（`domain/nodes/nodeDisplayLabel.ts`）が、別のファイルにある | `config/` には、同様の定数（`shapes.ts` など）があり、慣例どおり。関数の横へ移しても、インポート先が変わるだけで責務は改善しない |
| `title` 属性の規則（空のとき付けない）を、`getNodeDisplayLabel` に寄せる | 表示の代替とは別の規則。寄せると、2つの規則が1つの関数に混ざる |
| パネルの幅（`w-60 shrink-0`）が、`AppWorkspace` ではなく、パネルにある | 各部品が自分の見た目（幅）を持つ流儀と一致する。パネルが複数になり、幅を揃えたくなったときに、移せばよい |
| ページが、配線・導出（選択ノード）・スロットの組み立てを兼ねる | ページは組み立ての起点であり、ヘッダーのスロットの前例とも揃う。選択ノードの導出は、この変更より前から存在していた |
| 異なるモジュールが、共通のモジュールに、同じ向きで依存する（`domain/imageExport` から `domain/nodes` など） | 既に同じ向きのインポートの前例があり、循環もない |

## 2. 挙動・不具合の指摘

### B1. 別の表示面で、同じ状態の表示がずれる（実画面でのみ発見された）

**発生する状況**
既存の表示面（キャンバス、画像エクスポート）が既に扱っている状態（ここでは「ラベルが空のノード」）を、新しい表示面（パネル）が、別の文言で表示したとき。

**問題**
同じノードが、キャンバスでは「新しいノード」、パネルでは「（ラベルなし）」と表示され、利用者は、両者が同じノードを指すのか、判断しにくい。

**原因（詳細）**
1. 計画書を書く段階で、パネルの空ラベルの扱いを「（ラベルなし）と表示する」と、Global Constraints に書いた。その時点で、既存のコードが空ラベルをどう表示しているかを、検索して確認しなかった。実際には、キャンバス（`renderMapNodes.ts` の `node.label || "新しいノード"`）と画像エクスポート（`mapExportText.ts` の定数）が、既に「新しいノード」で一致していた。
2. 実装者は、計画書どおりに実装し、テストも、計画書の文言を検証した。ページのテストは、キャンバスを置き換えたモックを使うため、キャンバスの表示と比較する機会がなかった。
3. タスクごとのレビューも、最終レビューも、「差分」を「計画書」と照合する形だった。不整合は、「新しい差分」と「変更していない既存のコード」の間にあり、差分の外にある。そのため、どのレビューも気付かなかった。
4. 実画面（開発サーバーとブラウザ）で、ノードを追加して選択したときに、キャンバスの「新しいノード」と、パネルの「（ラベルなし）」が並んで見えて、初めて発見された。

**修正**
- 共通の定数 `FALLBACK_NODE_LABEL` を導入し、3か所を同じ文言に統一した。
- その後、規則の重複（S1）も、関数に集約した。
- 計画書の Global Constraints と、「実装後の変更」の節も、最終的な形に更新した。

**汎用的な教訓**
- 既存の表示面がある状態に、新しい表示面を足すときは、計画の段階で、既存の表示（文言、順序、省略の仕方）を検索して確認する。計画書に、新しい文言を発明して書かない。
- UI の機能は、実画面で確認する。差分と計画書の照合だけでは、差分の外にある既存のコードとの不整合は、見つからない。
- レビューに、「同じ情報を見せる、他の表示面との一貫性」というレンズを、明示的に加える。

### B2. 重要度フィルタで非表示になった選択ノードの扱いについて、レビュー同士の事実が食い違った

**発生する状況**
複数のレビュー（あるいはレビュアー）が、同じ挙動について、異なる事実を述べたとき。

**問題**
あるレビューは、「重要度フィルタで選択中のノードが非表示になっても、パネルにそのラベルが出て、生成ボタンも有効のまま」と述べた。別のレビューは、「選択が外れ、パネルが案内に戻る」と述べた。PR 本文の手動確認の手順（手順5）に、どちらを書くかで、本文の正しさが変わる。

**原因（詳細）**
- 実際の挙動を決めているのは、ページではなく、キャンバスの部品（`MapStage`）が持つフック `useHiddenNodeInteractionReset` である。選択中のノードが非表示になると、このフックが `onSelectNode(null)` を呼んで、選択を解除する。
- ページだけを読むと、「選択は `selectedNodeId` で保持される」としか見えず、フックの存在に気付かない。ページのテストは、キャンバスをモックに置き換えているため、このフックは動かない。
- つまり、「どの範囲のコードを読んだか」で、結論が変わっていた。

**対応**
PR 本文の手順は、実際のコードを読んだ上で、「選択が外れ、パネルが案内に戻る」と書いた。2人目のレビュアーが、手順1〜8のそれぞれを、コードと照合して、正しいと確認した。

**汎用的な教訓**
- レビュー同士で事実が食い違ったら、どちらかを選ぶのではなく、コードまたは実画面で確認する。
- 挙動を決めている部品が、レビューの対象の外にある（モックされている）ときは、そのモックされた部品の側のコードまで読む。

## 3. テストの指摘

### T1. 変異に耐えるテストが不足していた（選択ノードの導出）

**発生する状況**
状態を「ID で探して導出する」実装（`nodes.find(id が一致)`）を、テストが、「ノードが1つだけの場合」でしか検証していなかったとき。

**問題**
実装が、「先頭のノードを返す」（`nodes[0]`）に壊れても、すべてのテストが通る。実際の利用では、2番目以降のノードを選択したときに、パネルが、別のノードの情報を表示し、別のノードの ID で生成を要求してしまう。

**原因（詳細）**
- テスト用のモック（キャンバス）には、「選択」のボタンがあり、その実装が `nodes[0]` の ID で `onSelectNode` を呼んでいた。
- テストは、毎回、ノードを1つだけ追加していた。このため、「選択されたノード」と「先頭のノード」が、常に同じノードだった。
- 偶然の一致によって、`find(id)` と `nodes[0]` を区別するデータが、テストに存在しなかった。

**修正**
- モックに、「2番目のノードを選択する」ボタンを足した。
- ノードを2つ作り、2番目を選択して、生成の入口へ渡される ID が、2番目の ID であり、1番目の ID ではないことを検証するテストを追加した。
- 選択を、2番目から1番目へ切り替えたとき、渡される ID も、順序どおりに追従することを検証するテストを追加した。
- 実際に、実装を `nodes[0] ?? null` へ変異させて、新しいテストが失敗することを確認し、元に戻した（バイト単位で同一であることも、保存した控えとの比較で確認）。

**汎用的な教訓**
- 「選ぶ」処理のテストは、候補を2つ以上用意し、先頭ではないものを選ぶ。
- 実装を壊して（変異させて）テストが落ちることを、実際に確認する。確認後は、元に戻したことを、控えとの比較で確認する。

### T2. 冗長なアサーション

**問題と原因**
定数のテストが、「文字列型である」「空ではない」「値が一致する」の3つを、順に確認していた。最後の「値が一致する」が、前の2つを含んでおり、前の2つは、情報を加えない。実装者が、型や非空の確認を、慣例として足した。

**修正**
値の完全一致の1件に絞った（値の変更や、空文字への変更は、これで検出される）。

**汎用的な教訓**
より強いアサーションが、他を含んでいるときは、弱いものを重ねない。重ねると、「何を保証するテストか」が、読み手に分かりにくくなる。

### T3. リファクタリングで、検証を持ち主の部品へ移す

S2 の修正で、クラスの検証を移した。移した後に、「カバレッジが減っていない」ことを確認する手順も、重要だった。

- 移す前の検証（`main` の `flex`、キャンバス枠の `min-w-0 flex-1`、パネルの `w-60 shrink-0`）が、移した先のテストに、すべて存在することを、1つずつ照合した。
- 移した先のテストでは、DOM の並び順（キャンバスの枠の直後にパネルがあること）も、新たに検証した。
- 移した後も、ページのテストには、配線（`main` の中に、キャンバスとパネルがあること）が残っていることを確認した。

**汎用的な教訓**
テストを移すときは、「消えた検証」と「移った先の検証」の一覧を作り、1つずつ照合する。

## 4. ドキュメント・PR 本文の指摘

### D1. PR 本文の記述が、作業の履歴の視点で書かれ、基準ブランチとの差分と食い違った（再発）

**発生する状況**
PR 本文に、「既存のテストの検証を、新しい部品のテストへ移した」「DOM とクラスは従来と同一」と書いたとき。

**問題**
- 基準ブランチ（main）との差分では、既存の `page.test.tsx` のレイアウトテストは変更されていない。移したのは、このブランチの中で、先に追加したテストの検証だった。
- 「従来と同一」は、このブランチの中でのリファクタリングの前後の比較であり、main との比較ではない。main と比べると、`main` 要素に `flex` が加わり、キャンバスを包む `div` が1つ増えている。
- レビュアーは、main との差分を見るので、記述が事実と異なって見える。

**原因（詳細）**
- PR 本文を、作業の経緯（途中でテストを追加し、後でリファクタリングして移した）をもとに書いた。レビュアーが見る対象は、最終的な差分であり、経緯ではない。
- 前回の整理（`2026-10-02-overlay-menu-review-findings.md` の D2）で、同じ種類の誤りを、既に記録していた。しかし、本文を書く手順に、「差分を基準に書く」というチェックが組み込まれていなかったため、同じ誤りが再発した。
- 「従来」「以前」という言葉は、基準が曖昧になる。何と比べているのかが、文中に書かれていなかった。

**修正**
- 「既存のテストは変更していない（main にあるレイアウトテストも、そのまま）。このブランチで先に追加した検証を、リファクタリングで部品のテストへ移した」と書き直した。
- 「DOM とクラスは、この分離の前後で同一（main と比べると、`main` 要素に `flex` が加わり、キャンバスを包む `div` が1つ増えている）」と、比較の基準を明記した。

**防止の効果**
今回は、最初のレビューの依頼文に、「PR 本文の記述のすべての事実を、差分と照合する」を、明示的に加えた。このため、1回目のレビューで、この誤りが検出された（前回は、1回目で検出されず、2回目の独立確認で見つかった）。

**汎用的な教訓**
- PR 本文は、基準ブランチとの差分を基準に書く。作業の経緯を書かない。
- 「従来」「以前」「元の」といった言葉には、比較の基準を、必ず併記する。
- 件数、ファイル一覧、動作の説明は、差分から機械的に確認する。
- レビューの依頼には、本文の事実確認を、最初から含める。

### D2. 計画書の記述が、最終コードとずれた

**発生する状況**
実装計画に、当初案（手順、コード）を詳しく書いた後、実装中や、リファクタリングで、設計が変わったとき。

**問題**
後から計画書だけを読むと、最終的なコードの形を誤解する。今回のずれは、次の2点だった。
- 計画書は、「ラベルが空のとき `title` は空文字になる」と書くが、最終コードでは、属性自体を付けない。
- 計画書の手順は、レイアウトを `page.tsx` に直接書く形だが、最終コードでは、`AppWorkspace` に分離している。表示ラベルの規則も、`getNodeDisplayLabel` に移っている。

**原因（詳細）**
計画書は、「実施時点の手順と判断」の記録であり、実装後の修正（レビューや、実画面での確認による変更）を、自動では反映しない。一方で、読み手は、計画書を「最終的な仕様」として読むことがある。

**修正**
- 当初案の記述は、記録として残した。
- ずれのある箇所に、「当初案」と注記し、末尾の「実装後の変更」の節に、最終的な形と、変更の理由、後続の計画書への参照を追記した。

**汎用的な教訓**
計画書は、履歴として残してよい。ただし、最終コードを誤解させる記述には、注記と、「実装後の変更」の節で、最終的な形を示す。

### D3. 計画書の制約が、実際の作業とずれる（対応しなかった）

**状況**
リファクタリングの計画書に、「コミットしない」という制約が書かれているが、実際には、後からコミットされた、という指摘があった。

**判断**
対応しない。計画書は、実施時点の指示の記録であり、その後のコミットは、`git log` で確認できる。最終的なコードや履歴の理解を誤らせず、動作やルールへの影響もない。

**D2 との違い**
D2 は、「最終的なコードの形」を誤解させる（読み手が、誤った前提でコードを扱う危険がある）ため、対応した。D3 は、「当時の指示」の記録であり、現在のコードの理解に影響しないため、対応しなかった。計画書の記述を直すかどうかは、「最終的な状態の理解を誤らせるか」で判断する。

### D4. 補足的なランドマークが、メインのランドマークの内側にある（対応しなかった）

**状況**
`<aside>`（補足領域、`complementary` ランドマーク）が、`<main>` の内側にある。axe のベストプラクティス（`landmark-complementary-is-top-level`）は、補足領域をトップレベルに置くことを推奨している。

**判断**
対応しない。
- WCAG の達成基準の違反ではなく、ベストプラクティスの推奨にとどまる。
- パネルは、名前（`aria-label`）と見出し（`h2`）を持つランドマークで、スクリーンリーダーでの移動や読み上げはできる。
- 既存のレイアウトテスト（`main` に高さを割り当てる検証）が、この構造を前提にしている。`main` をキャンバス側だけに限ると、`AppWorkspace` とテストの変更が広がる。

**将来の扱い**
ランドマークの構造を、アプリ全体で見直す機会があれば、そのときに扱う。

**補足（ROADMAP の最終更新日）**
レビューの確認で、「最終更新」の日付が、PR の作成日（翌日）と異なることが指摘された。日付は、ロードマップを最後に編集した日（コミットの日付）であり、正しい値だった。「最終更新」は、「最後に、その文書を編集した日」であって、「今日」ではない。

## 5. レビューの進め方（プロセス）の学び

### P1. レビューのレンズを、最初から広げると、1回目のレビューで見つかる

前回の整理（P1）では、「1回目は『指摘なし』でも、観点を変えると新しい指摘が出る」ことを記録した。今回は、1回目のレビューの依頼文に、次のレンズを、最初から入れた。

- コードの正しさと、テストの強さ（変異の観点）。
- PR 本文の事実確認（ファイル一覧、件数、手動確認の手順、影響範囲、既知の制限）。
- ルール文書との整合（`AGENTS.md`、`.github/copilot-instructions.md`、`ROADMAP.md`）。
- コミット履歴と、PR タイトル。

その結果、1回目で、PR 本文の誤り（D1）が検出された。2回目の独立確認は、1回目の結論の検証（件数、手動確認の手順）と、敵対的な視点（ランドマーク、計画書の整合）に集中でき、見つかるのは軽微な指摘だけになった。

**汎用的な教訓**
レビューの依頼文に、過去に見落とした種類の指摘を、レンズとして追加する。2回目の確認者には、「1回目を信用せず、独立に確認する」ことと、「1回目の結論の評価」の両方を依頼する。

### P2. レビュー同士の事実の食い違いは、コードで確認する

B2 のとおり。レビューの結論を、そのまま PR 本文などに書き写さない。事実を、コードまたは実画面で確認する。

### P3. 実画面での確認は、レビューの代わりにならず、レビューも、実画面での確認の代わりにならない

B1 は、実画面でのみ見つかった。一方で、レビューは、実画面では気付きにくい別の問題（変異に耐えないテスト（T1）、本文の食い違い（D1））を見つけた。

- UI の機能では、実画面での確認を、実装の完了の手順に含める。開発サーバーを起動し、操作して、レイアウトの寸法（DOM の寸法を取得する）と、連携（選択と表示の更新、メニューとの併用）を確認する。
- 実画面での確認は、使い終わったら、サーバーとタブを片付ける。

### P4. 補助スクリプトが返すパスの形式（絶対パスか相対パスか）に注意する

**発生した問題**
作業ツリーのスナップショットを作るために、一時的なインデックスのパス（`$PWD/<ワークスペース>/idx`）を組み立てたとき、`sdd-workspace` が返す値は、すでに絶対パスだった。`$PWD/` を前に付けたため、パスが二重になり、`Unable to create ... idx.lock: No such file or directory` で失敗した。

**原因**
補助スクリプトの戻り値が、絶対パスであることを確認せずに、相対パスとして扱った。

**対応**
相対パス（`.superpowers/sdd/<名前>`）を、明示的に変数に持ち、そこから、`$PWD/` を付けて組み立てた。失敗は、エラーが明示されたため、すぐに検出できた。

**汎用的な教訓**
補助スクリプトの戻り値を、他のパスと連結するときは、絶対パスか相対パスかを、先に確認する。

その他の、プロセスに関する学び（コミットしない制約のもとでの差分の渡し方、自分の PR に Approve を付けられないこと）は、前回の整理（P4、P5）と同じ。

## 6. 汎用チェックリスト（既存の画面に、新しい表示面を足すとき）

### 構造
- [ ] 同じ情報を見せる複数の表示面で、「いつ、どう表示するか」という規則が、関数1つに集まっているか（値の定数だけを共有していないか）。
- [ ] 規則が、言語仕様に暗黙に依存している（`||` の真偽判定など）場合、その決定をテストで固定したか。
- [ ] 組み立ての部品（ページ、ルート）が、配線だけを持ち、レイアウトの CSS は、スロットを受け取る部品にあるか。
- [ ] 規則が似ていても、目的が別のもの（編集欄の初期値、`title` 属性）を、共通化していないか。

### 挙動
- [ ] 既存の表示面が、すでに同じ状態を表示しているか、実装の前に検索したか。新しい文言を、計画に発明していないか。
- [ ] 実画面で、既存の表示面と新しい表示面を、並べて確認したか（文言、順序、省略の仕方、寸法）。
- [ ] モックされている部品が、挙動を決めている場合（選択の解除など）、そのモックされた側のコードまで読んだか。

### テスト
- [ ] 「選ぶ」処理のテストに、候補が2つ以上あり、先頭ではないものを選ぶ検証があるか。
- [ ] 実装を壊して（変異させて）、テストが落ちることを確認し、元に戻したことを、控えとの比較で確認したか。
- [ ] より強いアサーションが含む、弱いアサーションを、重ねていないか。
- [ ] テストを移したとき、「消えた検証」と「移った先の検証」を、1つずつ照合したか。

### ドキュメント・PR
- [ ] PR 本文は、基準ブランチとの差分を基準に書いたか。作業の経緯を書いていないか。「従来」「以前」に、比較の基準を併記したか。
- [ ] 件数、ファイル一覧、手動確認の手順を、差分とコードから確認したか。
- [ ] 計画書に、最終コードを誤解させる記述がないか。ある場合は、当初案への注記と、「実装後の変更」の節を追加したか。
- [ ] 「対応しない」と決めた指摘は、理由をスレッドに返信してから Resolve したか。

### レビュー
- [ ] 1回目のレビューの依頼文に、コード、テスト（変異）、PR 本文の事実確認、ルール文書との整合、履歴のレンズを、最初から入れたか。
- [ ] 2回目の確認者に、「1回目の評価」と「独立した再確認」の両方を依頼したか。
- [ ] レビュー同士の事実が食い違ったとき、コードまたは実画面で確認したか。
- [ ] 実画面での確認を、UI の機能の完了の手順に含めたか。
