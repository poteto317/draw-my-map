## 1. 構造（単一責任）の指摘

### S1. 小さな差分でも、観点を変えて確認した結果、分割すべきものは見つからなかった

**発生する状況**
既存の機能に、小さな差分（本番コード8ファイル、58行の追加）を足したあと、単一責任の確認を、観点を変えて2回行ったとき。

**問題**
問題はなかった。ただし、確認では「分割するか」が何度も候補に挙がり、そのたびに、「分割しない」という判断の根拠を示す必要があった。

**原因（詳細）**
- 候補が挙がった理由は、変更したファイルの責務が、見た目には増えたため。例えば、パネルのコンポーネントは、props が3つから4つに増え、表示する要素（プレビュー、設定済み、削除ボタン、生成ボタン、エラー）が1つの関数に並んでいる。ビューモデル（`illustrationPanelView`）の戻り値は6項目になった。
- しかし、変更理由は、どちらも「パネルの見た目」の1つだった。表示の判定（どれを出すか）は、前の機能で、すでに純粋関数に分けてあった。今回増えたのは、条件付きのボタン1つ（約9行）と、ラベルを読む1行だけだった。
- 「高さの規則（設定時 116、削除時 60、読み込み時 116 を下限）を1か所にまとめる」という候補は、3つの規則が別の意味を持つため、1つの関数にすると、引数で分岐する関数になる。2つの高さの関係は、すでに定数（`ILLUSTRATED_NODE_HEIGHT = RECT_HEIGHT + ILLUSTRATION_AREA_HEIGHT`）で1か所に定義されている。
- 「生成／再生成のラベルを決める関数を `domain` に置く」ことは、利用者向けの文言を返す `domain` として違和感があるが、その関数は、パネル（`components/layout`）と右クリックメニュー（`components/map`）の両方から使う。どちらかに置くと、2つの部品の間に、横の依存が生まれる。`domain` が利用者向けの文言を返す前例（`mapDocumentDecoder.ts` のエラー文）がある。

**修正**
なし（判断の記録のみ）。分割しなかった主な候補と理由は、次のとおり。
- 高さの規則を1つの関数にまとめる: 3つの規則は意味が違い、定数の参照を関数呼び出しに変えるだけで、過剰分割。
- 型の判定（`illustration !== undefined`）の共通化: 規則ではなく型の判定で、既存の約10ファイルも同じ書き方。共通化すると、変更が差分の外に広がる。
- `MapStage` が対象ノードを求めてメニューに渡す: 1行の追加で、メニューを真偽値の props だけで描画する形のほうが、`Node` 型に依存せずに済む。

**汎用的な教訓**
- 確認の打ち切りは、「観点を変えても、新しい指摘が出ない」ことで判断する（イラストの紐付けの整理 S4）。今回は、1回目（広い観点）と2回目（テスト、依存の向き、命名、副作用、状態の残留）の両方が0件だった。
- 見た目の肥大（props の数、戻り値の項目数、1つのコンポーネントの要素数）は、責務の増加と同じではない。判断の基準は、「変更理由が複数あるか」。
- 「分割しない」判断の根拠は、記録する（イラストの紐付けの整理 S3）。次の機能で、同じ候補が挙がったときに、議論を繰り返さずに済む。

### S2. テストの重複（毎回同じ props を並べる）は、今回は共通化しなかった

**発生する状況**
コンポーネントに必須の props を1つ足したとき、既存のテスト（`IllustrationPanel.test.tsx`、28回の `render`）の全てに、その props を足す必要が生じたとき。

**問題**
テストの変更が、機能の変更より大きくなる（既存の22か所を機械的に直した）。

**原因（詳細）**
各テストが、`render(<IllustrationPanel ... />)` を、props を全て書き下す形で持っていた。props は全て必須なので、足し忘れは型エラーで見つかるが、足す作業は、props の数だけ増える。

**対応しない理由**
- 共通のヘルパー（`renderPanel(overrides)`）に置き換えると、今回の機能と関係のない既存のテストの大半を書き換えることになり、差分が100行以上増える。モックの取り出し方を変える際に、検証を見落とすリスクもある。
- 重複のコストは手間だけで、props を足し忘れても、型エラーで必ず見つかる。
- ただし、ヘルパーの前例（`NodeLabelEditor.test.tsx` の `renderEditor`、`createTestNode` の `overrides`）はあるので、次に props を増やすときは、**別の PR で、先にヘルパー化する**価値がある、と記録した。

**汎用的な教訓**
機能の差分に、既存テストの大規模な書き換えを混ぜない。重複を直す作業は、機能の変更とは別の PR で、先に行う。

## 2. 挙動・設計の指摘

### B1. 破壊的な操作の文言が、画面の状態によって、別の対象に読める【最終レビューの指摘】

**発生する状況**
すでにイラストがあるノードで、「再生成」を押してプレビューを表示し、「ノードに設定」ボタンと並んで、「イラストを削除」ボタンが見えているとき。

**問題**
利用者は、「プレビューが気に入らないので、削除したい」と考え、「イラストを削除」を押す。しかし、削除されるのは、プレビューではなく、ノードに設定済みのイラストである。取り消しの操作はないので、元のイラストが失われる。

**原因（詳細）**
- パネルは、プレビューを表示している間、設定済みのイラストを表示しない（プレビューを優先する、前の機能の仕様）。そのため、画面に見えている画像は、プレビューの1枚だけである。
- 削除ボタンは、「ノードに設定済みのイラストがある」ことを条件に表示される。この条件は、画面に何が見えているかとは、独立している。つまり、プレビュー表示中でも、削除ボタンは出る（出す必要がある。設定済みのイラストは、見えていなくても、存在する）。
- 削除ボタンの文言が、対象を示さない「イラストを削除」だったため、画面上で、いちばん近くに見える画像（プレビュー）を指しているように読める。ボタンの配置も、「ノードに設定」の直下だった。
- タスクごとのレビューでは、各状態（未選択、イラストなし、設定済み、生成中、失敗、プレビュー中）でのボタンの出し分けは、確認された。しかし、「その状態で、利用者がボタンの文言をどう読むか」は、確認の観点になかった。出し分けの条件の正しさと、文言の誤読は、別の問題である。

**修正**
- 文言を、「イラストを削除」から「設定済みのイラストを削除」に変更した。対象が、プレビューではなく、ノードに設定済みのものであることが、文言から分かる。
- 変更は、ボタン、テスト、README、ROADMAP、計画の全体に及ぶ（D1）。
- 採らなかった案: プレビュー表示中も、設定済みのイラストを小さく併記する（画面の構成を変える範囲の広い変更）、削除の確認ダイアログ（計画で範囲外）。

**汎用的な教訓**
- 破壊的な操作（削除、上書き）のボタンの文言には、**対象**を入れる。「削除」だけでは、画面上の、どの要素を指すのかが、状態によって変わる。
- 1つの画面に、「見えている対象」と「操作の対象」が異なりうる状態がある場合（プレビューと確定済みの値が共存する画面など）は、状態ごとに、「この文言を読んだ利用者は、何を消すと思うか」を、レビューで確認する。
- 取り消しのない操作は、特に、文言の誤読の影響が大きい。

### B2. 操作したボタンが消えると、フォーカスが失われ、キーボードのショートカットが誤って働く【PR レビューの指摘。対応しない】

**発生する状況**
キーボード（またはマウス）で、「設定済みのイラストを削除」や「ノードに設定」を押し、そのボタンが画面から消えたあと、続けて Tab、Enter、Backspace などを押したとき。

**問題**
ボタンが消えると、フォーカスが、ページ本体（`body`）に落ちる。アプリのキーボードショートカットは、`body` へのキー入力にも反応するため、Tab で子ノードが追加され、Enter で兄弟ノードが追加され、Backspace や Delete で選択中のノードが削除される。

**原因（詳細）**
- ブラウザは、フォーカスのあった要素が DOM から取り除かれる（または無効になる）と、フォーカスを `body` に移す。ボタンの押下で、そのボタンの表示条件（「イラストがある」）が false になり、ボタンが取り除かれる。
- ショートカットの処理は、`window` のキー入力を受け、`event.target` が `button`、`input`、`textarea`、`select`、リンク、`contenteditable` の中にある場合だけ、反応しない。`body` は、この除外に含まれない。このアプリでは、`body` にフォーカスがある状態が、「マップのショートカットが効く」通常の状態として設計されている（キャンバスはフォーカスできない要素なので、ノードをクリックしたあとも、フォーカスは `body` にある）。
- ボタンにフォーカスがある間は、反応しない。ボタンが消えた後は反応する。この違いが、指摘された現象の原因である。

**対応しない理由（検証の結果）**
- **同じ現象が、既存の UI にもある**。右クリックメニューは、項目を `autoFocus` で開き、選ぶと閉じる（フォーカスは `body` に落ちる）。「ノードに設定」も、プレビューごとボタンが消える。生成ボタンは、生成中に `disabled` になる。PNG エクスポートや重要度のセレクタも、`disabled` になる。**本番コードには、フォーカスを移す処理（`focus()`）が1つもない**。削除ボタンだけ直すと、扱いが食い違う。
- **提案の修正（生成ボタンへフォーカスを移す）に副作用がある**。マウスで削除した直後の Enter が、ノードの追加ではなく、イラストの生成（外部サービスの無料枠の消費）になる。生成中は、生成ボタンが `disabled` なので、`focus()` が効かず、結局 `body` に落ちる。
- **実害は、元に戻せる範囲**。追加された空のノードは、Escape で編集を抜けて削除できる。Backspace によるノードの削除は、`body` にフォーカスがあれば、いつでも起きる既存の動作で、今回の変更で新しく生じたものではない。また、ノードを選択した状態で、`body` から Tab を押すと、子ノードが追加されるため、キーボードだけで、パネルのボタンへ届く経路は、ほとんどない。実際に起きやすいのは、マウスでクリックした場合で、その場合は、「ノードをクリックしたあと」と同じ状態になる。
- 重大度は、レビュアーの「中」より低い（「低」）と判断した。
- 直す場合は、閉じた、消えた、無効になったあとの**フォーカスの戻し先を、アプリ全体で決める**必要がある（例: マップのコンテナを `tabIndex=-1` にして、戻し先にする）。Phase 7 の最後の項目の範囲を超えるため、別の課題とした。

**修正（対応）**
コードは変更しない。PR 本文の「既知の制限」に、この挙動を追記し、スレッドに、対応しない具体的な理由を返信してから、Resolve した。

**汎用的な教訓**
- 「フォーカスしている要素が消える、または無効になる」と、フォーカスが `body` に落ちる。`body` のキー入力を拾うショートカットがあるアプリでは、誤作動の原因になる。UI に、消える要素（条件付きの表示、メニュー、モーダル）を足すときは、消えたあとのフォーカスを意識する。
- ただし、アプリ全体の方針（フォーカスを戻さない）がある場合、1つの部品だけで直すと、扱いが食い違う。直すなら、全体の方針として、まとめて決める。
- 指摘を、既存の慣習と照らして検証する。「同じ現象が、すでに複数の場所にある」という事実が、対応しない判断の、強い根拠になる。
- 修正案に副作用がないかを確認する（今回は、フォーカスの移動が、外部サービスの課金を伴う操作を、誤って起動しうる）。

### B3. 逆向きの操作は、元の操作と対になっているかを確認する

**発生する状況**
状態を変える操作（イラストを設定する: ノードの高さを 116 にする）に、逆向きの操作（イラストを外す）を足すとき。

**問題**
逆向きの操作の規則（外すとき、高さをどうするか）が決まっていないと、元の操作と食い違う。例えば、外すときに「高さを 116 から、イラスト分（56）だけ引く」とすると、手で編集したデータ（高さ 200）で、144 になり、元の 60 に戻らない。

**原因（詳細）**
- 前の機能（イラストの紐付け）では、高さについて、3つの規則が別々の場所にあった。設定時は 116 に固定、読み込み時は 116 を下限にする（`max`）、イラストがないノードは触らない。この3つの関係は、「設定した値と、読み込み時の補正値が、必ずしも一致しない」という、あいまいな状態のまま残っていた（最終レビューの未決事項として、判断待ちになっていた）。
- 逆向きの操作を足すとき、このあいまいさが、そのまま「外したあと、何を高さとするか」の、設計の問題になる。

**修正（計画で決めたこと）**
- アプリが作るノードの高さは、2つの値（イラストなし 60、あり 116）だけとする。設定時は 116 に、削除時は 60 に、**固定する**（対の規則）。
- 保存データの読み込みは、イラストがあるノードの高さだけを `max(高さ, 116)` に補正し、イラストがないノードには触れない（そのまま）。
- 手で編集した JSON（高さ 200 のイラスト付きノード）を、削除すると 60 になる。設定時が 116 に固定されるのと対称で、仕様どおりである。
- テストで、往復（設定→削除→設定が元に戻る）を確認する。自動レイアウトでは、設定前の兄弟ノードの位置に、**厳密に**戻ることを確認する（T3）。

**汎用的な教訓**
- 逆向きの操作を足すときは、元の操作と**往復して元に戻る**かを、最初に決め、テストにする（設定→削除→設定が同じ状態、削除前後で、他の要素の位置が元に戻る）。
- 前の機能で「判断待ち」にした点は、次の機能で、設計の問題として、表面化する。計画の段階で、決めておく。

### B4. 対象を決める判定が、「どのノードか」を取り違えていないかを確認する

**発生する状況**
右クリックしたノードに、イラストがあるかどうかで、メニューのラベルを切り替えるとき。

**問題**
ラベルを決める判定が、「右クリックしたノード」ではなく、別の基準（全ノードのうち1つでもイラストがある、先頭のノード、選択中のノード）で決まっていても、簡単なテストでは、気付けない。例えば、イラストのないノード A を右クリックしたのに、別のノード B にイラストがあるために、「再生成」と表示される。

**原因（詳細）**
- 実装は、「メニューを開いたノードの識別子で、ノードの配列から対象を探し、そのイラストの有無を渡す」という1行（`menuNode`）だった。
- 追加されたテストは、「イラストのあるノードが1個だけの構成」と、「全てのノードにイラストがない構成」の2件だった。この2つの構成では、判定を、`nodes.some(...)`（どれか1つにイラストがあるか）、`nodes[0]`（先頭のノード）、選択中のノードのいずれに変えても、両方の結果が同じになる。つまり、**対象の取り違えを検出できない**（T1）。

**修正**
イラストのないノード1と、イラストのあるノード2を持つ構成を作り、ノード1を右クリックすると「イラストを生成」、ノード2を右クリックすると「イラストを再生成」になるテストを追加した。判定の式を、`nodes.some`、`nodes[0]`、`selectedNodeId` に、一時的に変えて、いずれも赤くなることを確認した（確認後に元に戻した）。

**汎用的な教訓**
「対象のものについて」判定する処理のテストは、**対象と、対象でないものを、区別して作る**（対象にだけ条件を満たす値を持たせる構成と、対象でないものにだけ条件を満たす値を持たせる構成）。1つだけが条件を満たすデータでは、「どれでも1つ当たればよい」実装と、区別できない。

### B5. 削除したあとに残る状態は、設計として決める

**発生する状況**
データ（ノードのイラスト）を削除したとき、そのデータに関連する、別の場所の状態（生成のプレビュー、テクスチャのキャッシュ、開いているメニューの表示）が、残るか消えるか。

**問題**
関連する状態が、意図せず残る（消し忘れ）と、削除したはずの内容が表示される。逆に、消すべきでないものを消すと、他の操作（再設定）が壊れる。

**原因（詳細）と判断**
次の状態について、残る、または追従することを、設計として確認した。
- **生成のプレビュー**: ノードに設定されたイラストとは別の状態（生成の結果）で、削除しても残るのが仕様。削除したあとに、プレビューから「ノードに設定」で、付け直せる。生成中に削除しても、結果は、ノードの識別子とテキストで照合されるため、削除の影響を受けない（削除は、マップの置き換え（`resetRevision`）や中断（abort）を経由しない）。
- **テクスチャのキャッシュ**: 実行環境（runtime）の破棄、またはアンマウントまで、まとめて残す既存の方針。削除したあと、同じ画像を付け直したとき、読み込み直さずに使える。再生成と削除を繰り返すと、128px のテクスチャが溜まるが、量が小さい（計画で範囲外とした）。
- **右クリックメニューのラベル**: 描画のたびに、ノードの配列から求めるので、古い値は残らない。メニューを開いている間に、ノードが削除されると、メニューは閉じる（対象ノードの変化を検出する既存の判定）。

**汎用的な教訓**
データを削除する機能では、そのデータに**関連する状態を列挙**し、それぞれ、「残す、消す、追従する」を、理由とともに決める。列挙した結果は、計画の「既知の制限」に書く。

## 3. テストの指摘

### T1. 対象の取り違えを検出できないデータ構成

（B4 の詳細）

**発生する状況**
「対象のものについて判定する」処理を、条件を満たすものが1つだけのデータで、テストしたとき。

**問題**
判定の対象を取り違える変更（`some`、先頭、選択中への変更）をしても、テストが通る。

**原因（詳細）**
テストの構成が、「条件を満たすものがちょうど1個」と「1個も満たさない」の2つだけだった。この構成では、「条件を満たすものが、どれか1つでもあるか」と「対象のものが、条件を満たすか」が、同じ結果になる。

**修正**
対象と、対象でないものを、区別する構成にした。実装を一時的に壊して（変異）、テストが赤くなることを確認した（B4 参照）。

**汎用的な教訓**
側面パネルの整理 T1（変異に耐えるテスト）の具体例。テストを書いたら、判定の式を、近い別の式に、一時的に置き換えて、赤くなることを確認する。

### T2. 条件付きの表示の「配置」を守るテストがない

**発生する状況**
複数の状態で表示される条件付きの要素（削除ボタン）を、「別の要素（設定済みのイラストの表示）の内側」ではなく、「独立した位置」に置く、という設計のとき。

**問題**
ビューモデルのテスト（`canRemove: true`）は、状態ごとの判定を確認するが、コンポーネントの中で、ボタンが、どのブロックに属するかは確認しない。ボタンを、「設定済みのイラストの表示」ブロックの内側に移す変更（プレビュー表示中は、設定済みのイラストが表示されないので、ボタンも消える）をしても、既存のテスト（すべて、プレビューのない状態）では、検出できない。

**原因（詳細）**
- 設計上、削除ボタンは、「設定済みのイラストの表示」とは独立して出る必要がある（設定済みのイラストが、見えていなくても、存在するため）。
- ビューモデルの判定と、コンポーネントでの配置は、別の層の責務で、片方のテストが通っても、もう片方の退行は検出できない。
- タスクごとのレビューで、すでに指摘されていた（Minor として台帳に記録した）が、最終レビューまで、繰り越された。

**修正**
プレビュー表示中（イラストあり、生成成功、同じテキスト）でも、削除ボタンが DOM に出て、押すと `onRemove` が呼ばれるコンポーネントのテストを追加した。

**汎用的な教訓**
設計上の重要な配置（「この要素は、あの要素の内側に置かない」）は、判定のテストだけでなく、**描画のテスト**でも守る。繰り越した Minor は、最終レビューで、必ず整理する（P2）。

### T3. 位置の変化を「小さくなった」だけで検証している

**発生する状況**
イラストを削除したあと、自動レイアウトで、兄弟ノードが上に再配置されることを、テストするとき。

**問題**
「削除前より小さい（上にある）」という比較だけでは、再配置が、**元の位置に正しく戻る**ことまでは、確認できない。例えば、削除後に、少しだけ上に動くが、元の位置とは違う、という不具合を検出できない。

**原因（詳細）**
テストの期待値を、「`toBeLessThan(削除前)`」で書いた。不等号は、変化の方向だけを確認する。往復の規則（B3）が、「元の状態に戻る」ことなので、テストも、元の位置との**一致**で確認するのが適切である。

**修正**
設定前の位置（`yBefore`）を記録し、削除後の位置が、`toBe(yBefore)` で一致することを確認する形に強めた。実装が、すでに正しく戻るため、追加の RED にはならなかった（強い比較に変えても、通ることの確認）。

**汎用的な教訓**
往復する操作（設定→削除）のテストは、**元の値との一致**で確認する。変化の方向だけを見る比較（大きい、小さい）は、検出力が弱い。

### T4. 暗黙の前提に頼った比較

**発生する状況**
テストの期待値が、「テスト用のヘルパーが作る既定値が、本番の定数と、たまたま一致している」ことに頼っているとき（`toEqual(node(2))` が、高さ 60 を暗黙に確認している）。

**問題**
ヘルパーの既定値が、将来変わると、テストが、意図とは違う理由で、通る、または落ちる。「高さが、本番の定数 `RECT_HEIGHT` に戻る」というテスト名の意図が、テストの本文から読み取れない。

**修正**
`expect(result[1].height).toBe(RECT_HEIGHT)` を明示した。

**汎用的な教訓**
テスト名が示す意図（「定数に戻る」）は、期待値に、**その定数を直接書いて**表す。ヘルパーの既定値との偶然の一致に頼らない。

### T5. 既存のテストの `toEqual` 全体比較に、新しい項目を足す変更

**発生する状況**
ビューモデルに、新しい項目（`generateLabel`、`canRemove`）を足したとき、既存のテストの、戻り値全体を `toEqual` で比較している箇所（約5か所）が、そのままでは落ちるとき。

**問題**
既存のテストの期待値を変えてよいか。「既存のテストの期待値は変えない」という制約と、衝突するように見える。

**判断**
次の条件を満たすので、許容した（レビューで確認した）。
- 追記した値は、各ケースの入力（イラストの有無）から、一意に決まる。
- 既存の項目の期待値は、変えていない。
- 新しい項目を足した以上、全体比較には、追記が必要である。

**汎用的な教訓**
「既存のテストの期待値を変えない」の本質は、**既存の挙動の確認を弱めない**こと。新しい項目を足すことによる、全体比較への追記は、既存の項目の期待値を変えない限り、許容できる。レビューでは、「追記が、新しい項目だけか」を確認する。

## 4. ドキュメント・PR 本文の指摘

### D1. 文言の変更が、計画の全体に届かない（取りこぼしと、書き換えすぎ）

**発生する状況**
レビューの指摘で、利用者向けの文言（「イラストを削除」から「設定済みのイラストを削除」）を変えたとき。

**問題**
1回目の修正では、実装、テスト、README を直したが、**計画ファイル**（リポジトリに残る記録）と、ROADMAP の現在地に、旧文言が残った。計画ファイルを直したあと、今度は、**書き換えすぎ**た箇所があった（計画の中の、コミットメッセージの例まで、新しい文言に書き換えた。実際のコミットは、旧文言のまま履歴に残っているので、計画と履歴が食い違う）。

**原因（詳細）**
- 文言は、実装、テスト、README、ROADMAP、計画の複数のファイルに、それぞれ別の文脈で書かれている。検索の対象を、実装とテストに絞ると、文書の取りこぼしが出る。
- 計画ファイルの中には、「利用者に見える文言」（ボタンの名前、手動確認の手順、テスト例）と、「過去の作業の記録」（コミットメッセージの例）が混ざっている。後者は、**履歴の記録**なので、文言を変えると、実際の履歴と食い違う。検索と置換を機械的に行うと、両方を書き換える。
- 加えて、計画の別の記述（テクスチャの寿命）も、実際の挙動（実行環境の破棄まで残る）と、微妙にずれていた。レビューで、まとめて見つかった。

**修正**
- 旧文言が残る箇所を全て検索し、利用者に見える文言は、新しい文言に統一した。
- コミットメッセージの例は、実際のコミットの文言に戻した（履歴と一致させる）。
- テクスチャの記述を、実際の挙動に直した。末尾に、実装後の変更を1行追記した。

**汎用的な教訓**
- 文言を変えるときは、実装、テスト、README、ROADMAP、**計画**を、全て検索する。
- 計画の中の、「利用者に見える文言」と「過去の記録（コミットメッセージの例、当時の判断）」を区別する。後者は、履歴と一致させるために、書き換えない。
- 置換のあと、**取りこぼし**（旧文言が残る）と、**書き換えすぎ**（記録を変えた）の両方を、レビューで確認する。

### D2. 実機で確認していない項目の扱い（継続）

**発生する状況**
右クリックメニューの幅（176px）への文字の収まり、削除ボタンの見た目、ダークモード、削除後の再読み込みなど、実ブラウザでしか確認できない項目が、自動テストでは確認できないまま、ROADMAP の項目を完了にするとき。

**問題と対応**
イラストの紐付けの整理 D2 と同じ。PR 本文のテスト方法に「実装者は、実ブラウザでの手動確認を行っていない」と明記し、マージ前の確認手順を載せた。メニューの幅は、コード上の見積もり（内側 142px に対して、「イラストを再生成」は約 112〜126px）で収まる見込みだが、「未検証」と書いた。

**汎用的な教訓**
見積もりと実測は別。見積もりで収まる見込みでも、実機で見ていないことは、未検証と書く。

## 5. レビューの進め方・作業手順

### P1. サブエージェントが、コミットのトレーラーに自分のモデル名を書く（再発）

**発生する状況**
実装を担当するサブエージェント（安価なモデル）に、コミットを任せたとき。

**問題**
コミットメッセージの末尾が、指定した `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>` ではなく、サブエージェント自身のモデル名（`Claude Haiku 4.5`）になった（最初のタスクで発生）。

**原因（詳細）**
外部 API 連携の整理 P5 と同じ。サブエージェントは、自分のモデル名を、自然な既定値として書く。依頼文に、「厳密にこの文字列」と書いていても、1回目の依頼文には、「自分のモデル名は使わない」という禁止の言い回しが、含まれていなかった。

**修正**
- コミットを確認したところ、トレーラーが違っていた。まだ push していないコミットだったので、メッセージだけを修正した（`git commit --amend`）。修正後は、再度確認した。
- 2つ目のタスクから、依頼文に、「厳密にこの文字列」「自分のモデル名や『Claude Haiku』などは絶対に使わない」「コミット後に、出力が完全一致することを確認する」を、明示的に書いた。以降のコミットでは、発生しなかった。

**汎用的な教訓**
トレーラーのような、利用者が指定した固定文字列は、依頼文に、**禁止する値**（自分のモデル名）も書き、**実行者に完全一致の確認**をさせ、さらに、**依頼した側も、`git interpret-trailers --parse` で確認する**。push する前なら、`--amend` で直せる。push 済みなら、直さずに、履歴に残す判断が要る。

### P2. 繰り越した軽微な指摘は、最終レビューで整理する

**発生する状況**
タスクごとのレビューで、軽微な指摘（Minor）が出たが、そのタスクの承認を妨げないため、台帳に記録して、次のタスクに進んだとき。

**問題**
記録だけでは、誰も読まなければ、そのまま捨てられる。実際には、繰り越した指摘のうち、「プレビュー表示中でも、削除ボタンが出ることを確認するテストがない」は、設計上の重要な配置を守るもので（T2）、放置すべきではなかった。

**対応**
- 最終レビューの依頼文に、「台帳に、繰り越した Minor がある。マージ前に直すべきものがあるか」を、観点として、**明示的に**含めた。
- 最終レビューは、繰り越した指摘のうち、T2（配置のテスト）を「マージ前に足すことを推奨」と判定した。ほかの軽微な指摘（テストの強化、`eslint-disable` に理由を書く）も、同じ修正にまとめて対応した。対象ノードが消えたときの扱いのテストは、対応しなかった（対象ノードが変わるとメニューが閉じる既存の判定があり、実害がない）。

**汎用的な教訓**
繰り越した指摘は、台帳に書くだけでなく、最終レビューの依頼文に**そのまま渡し**、取捨選択の結果を記録する（イラストの紐付けの整理 P1「観点を明示する」の応用）。

### P3. 対応しない指摘は、具体的な理由を、スレッドと PR 本文の両方に書く

**発生する状況**
PR のレビューで、対応しないと判断した指摘があるとき（B2）。

**対応**
- 指摘を、別のサブエージェントに、実コードで検証させた（事実か、重大度は妥当か、修正案に副作用はないか）。
- 結論（対応しない）と、その根拠（既存の慣習との関係、修正案の副作用、実害の範囲）を、スレッドに返信してから Resolve した。
- PR 本文の「既知の制限」と「PR レビューでの対応」の両方に、同じ内容を書いた（後から PR を読む人が、スレッドを開かなくても、判断を理解できる）。
- コードを変更しなかったので、コミットも、再レビューも行わなかった。

**汎用的な教訓**
対応しない指摘も、検証してから決める。理由は、スレッド（指摘した人が読む場所）と、PR 本文（後から読む人が読む場所）の両方に書く。

### P4. 環境による差（`sed -i`）

**発生する状況**
1行の文言の訂正を、`sed -i 's/…/…/' ファイル` で行おうとしたとき（macOS）。

**問題**
macOS の `sed` は、`-i` のあとに、バックアップの拡張子を要求する。GNU の書き方（`sed -i 's/…/…/' ファイル`）だと、「invalid command code」というエラーになり、何も変更されない。ただし、そのあとの `git add`、`git commit` は実行されたため、**変更のないまま**、コミットの手順だけが進んだ（コミットは作られなかったが、成功したように見えかねない）。

**対応**
エラーを確認し、`sed` ではなく、編集用のツールで直した。直したあと、差分を確認してから、コミットした。

**汎用的な教訓**
- ファイルの編集は、環境差のある `sed -i` ではなく、編集専用のツールを使う。
- 複数のコマンドを `&&` や改行で連ねるときは、**途中の失敗で、後続が空振りしても、成功に見えない**ように、各段階の結果（差分の有無）を確認する。

### P5. 繰り返しのレビューを、いつ終えるか

**発生する状況**
「指摘がなくなるまで繰り返す」という指示で、レビューを繰り返すとき。

**対応**
- マージ前のレビューは、1回目が「承認（Minor 2件）」、2回目が「承認（Minor 1件、書き換えすぎ）」、その後は、軽微な訂正だけで、再度のレビューは不要と判断した。
- 単一責任の確認は、2ラウンドとも0件で終えた（S1）。
- PR 上のレビューは、1回の指摘（B2）を、対応しない理由とともに閉じた。コードの変更がないため、再レビューは行わなかった。

**汎用的な教訓**
「対応すべき指摘がなくなる」ことが終了の条件で、「指摘が0件」である必要はない。承認で、残りの指摘が、軽微で、1行の訂正にすぎない場合は、訂正のあとに、再レビューを省いてよい（その訂正は、レビュアーが指摘した内容を、そのまま反映したものであるため）。ただし、**コードの挙動を変える修正は、必ず再レビューする**。

## まとめ: 同種の機能のレビューチェックリスト

すでにある機能に、「付けたものを外す」「作り直す」という逆向きの操作を足す機能のレビューでは、次を確認する。

1. **破壊的な操作の文言**: ボタンの文言に、**対象**が入っているか。画面に「見えている対象」と「操作の対象」が異なりうる状態（プレビューと確定値の共存など）で、利用者が何を消すと読むか（B1）。
2. **要素が消えたあとのフォーカス**: 操作したボタンが消える、または無効になる UI で、フォーカスの行き先が、アプリの方針と一致するか。方針がアプリ全体にあるなら、1つの部品だけで直さない（B2）。
3. **逆操作の対称性**: 設定→削除→設定が、元の状態に戻るか。設定時と削除時の規則（高さなど）が対になっているか。前の機能で判断待ちにした点が、設計の問題として、表面化していないか（B3）。
4. **対象の取り違え**: 「対象のものについて」判定する処理のテストが、対象と対象でないものを、区別した構成か（B4、T1）。
5. **関連する状態の残り方**: 削除したデータに関連する別の状態（プレビュー、キャッシュ、開いているメニュー）が、残る、消える、追従するかを、理由とともに決めたか（B5）。
6. **テストの検出力**: 条件付きの表示の配置を、描画のテストで守っているか（T2）。往復する操作を、元の値との一致で確認しているか（T3）。期待値に、定数を直接書いているか（T4）。
7. **既存テストの扱い**: 新しい項目を足すことによる、全体比較への追記は、既存の項目の期待値を変えていないか（T5）。機能の差分に、既存テストの大規模な書き換えを混ぜていないか（S2）。
8. **文言の変更の波及**: 実装、テスト、README、ROADMAP、計画を全て検索したか。取りこぼしと、書き換えすぎ（履歴の記録）の両方を確認したか（D1）。
9. **確認できていない範囲の明示**: 実機でしか確認できないこと（見た目、文字の収まり）を、未検証と明記したか（D2）。
10. **進め方**: 繰り越した軽微な指摘を、最終レビューで整理したか（P2）。トレーラーなど、固定文字列を、依頼した側も確認したか（P1）。対応しない指摘に、具体的な理由を、スレッドと PR 本文の両方に書いたか（P3）。
