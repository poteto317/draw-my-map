# レビュー指摘の整理: オーバーレイ型メニュー（右クリックメニュー）の実装

対象: PR #13「ノード右クリックのコンテキストメニュー」で行った、ローカルのレビューループ（単一責任の確認、正しさの確認）と、PR 上のレビュー（3回）で指摘された内容。

目的: 個別の機能に依存しない形で、「どういう時に」「どんな問題が起き」「なぜ起きたか」「どう直したか」を残し、同種の機能（ドロップダウン、ポップオーバー、ツールチップ、ダイアログなど、キャンバスや他の UI の上に重ねて表示する要素）を作るときのレビュー観点として再利用する。

## 読み方

- 各項目は「発生する状況」「問題」「原因」「修正」「汎用的な教訓」の順で書く。
- 項目 ID の頭文字は分類を表す。
  - **S**: 単一責任・構造の指摘
  - **B**: 挙動・不具合の指摘
  - **T**: テストの指摘
  - **D**: ドキュメント・ルール・PR 本文の指摘
  - **P**: レビューの進め方（プロセス）に関する学び
- 「対応しない」と判断した項目も、判断の根拠ごと記録する（同じ指摘が再度出たときに議論を繰り返さないため）。

## 全体像

| 区分 | 件数 | 主な傾向 |
|---|---|---|
| 構造（S） | 7 | 1つの関数・フック・ファイルに、複数の変更理由が同居していた |
| 挙動（B） | 6 | ブラウザ・OS 間のイベント仕様の差、状態が古くなる条件の見落とし |
| テスト（T） | 6 | 同じ規則を複数の層でテストして所有者が曖昧、弱い・誤解を招くテスト |
| ドキュメント（D） | 4 | 「正本」と宣言した文書の抜け、PR 本文と差分基準のずれ |
| プロセス（P） | 5 | 観点を変えると新しい指摘が出る、確認手順そのものの落とし穴 |

## 1. 構造（単一責任）の指摘

### S1. イベントハンドラに「判定」と「副作用」が同居していた

**発生する状況**
右クリックなどのイベントハンドラ内で、「このイベントを処理してよいか」（編集中か、メニュー上か、ジェスチャ中か）、「何が対象か」（座標からのヒットテスト）、「どう反応するか」（選択、メニューを開く、閉じる、`preventDefault`）を1つの関数に書いたとき。

**問題**
分岐の優先順位が関数の中に埋もれ、順序を変えたときの影響が分からない。DOM を使うため、分岐ごとの単体テストが書けず、結合テストに頼ることになる。

**原因**
ハンドラは「イベントを受け取って何かする」ことから書き始めると、条件を上から足していく形で自然に膨らむ。条件が増えるたびに、判定（純粋な規則）と副作用（`preventDefault`、状態更新）の境目が意識されなくなる。判定に必要な情報（DOM 上の事実、ジェスチャ状態、機能の有無）が、ハンドラ内で直接 DOM から読まれていたことも、純粋関数へ切り出しにくくしていた。

**修正**
- ハンドラは、DOM から「事実」だけを集める（`isEditing`、`isTextEntryTarget`、`isInsideMenu`、`hasActiveGesture`、`canOpenMenu`、座標、領域、ビューポート、表示ノード）。
- 純粋関数 `resolveMapContextMenuAction` が、事実から「意図」を返す: `native`（標準動作を妨げない）、`suppress`（標準動作の抑止のみ）、`dismiss`（閉じる）、`select`（選択のみ）、`open`（選択して開く）。
- ハンドラは、意図に応じた副作用を呼ぶだけにした。優先順位（編集中が最優先、次にメニュー上・ジェスチャ中、その次にヒットテスト）は、純粋関数のテストで固定した。

**汎用的な教訓**
イベントハンドラは「事実の収集 → 純粋関数で意図を決定 → 意図に応じた副作用」の3段に分ける。意図は列挙型にして、分岐の網羅を型で担保する。

### S2. 1つのフックに、状態保持・失効判定・グローバルリスナーが同居していた

**発生する状況**
開閉状態を持つフックに、「古くなった状態を無効にする規則」と「ウィンドウ全体のイベントを購読して閉じる処理」まで書いたとき。

**問題**
失効の規則（リセット、非表示、削除など）を変えたいだけなのに、リスナーの購読コードを含むフックを触ることになる。逆に、閉じるトリガー（Escape、Tab、外側クリックなど）を足すときに、状態保持のコードを読み解く必要がある。

**原因**
「メニューの開閉に関すること」という大きな括りで1つのフックにまとめたため。実際には変更の理由が3つ（状態の持ち方、いつ古くなるか、何で閉じるか）あり、それぞれ別のタイミングで変わる。

**修正**
- 失効の判定は、純粋関数 `isNodeContextMenuStale` に分離した。
- 閉じるリスナーは、`useNodeContextMenuDismissal(isOpen, onDismiss)` に分離した。
- 元のフックは、状態の保持と、この2つの組み立てだけにした。

**汎用的な教訓**
「いつ古くなるか」（規則）と「何で閉じるか」（購読）は、状態の保持から切り離す。規則は純粋関数にし、購読は `isOpen` を受け取る専用フックにする。

### S3. DOM を特定するセレクタが複数箇所に重複し、しかも汎用すぎた

**発生する状況**
「イベントの対象がメニューの内側か」を判定するために、`closest('[role="menu"]')` を、フックとコンポーネントの両方に直接書いたとき。

**問題**
将来、別の `role="menu"` の要素（ヘッダーのメニューなど）が追加されると、その内側のクリックでも「メニュー内」と判定される。また、判定方法を変えるときに、複数箇所を直す必要がある。

**原因**
`role` 属性は、アクセシビリティのための意味付けであり、「このメニューを識別する目印」としては汎用的すぎる。判定の仕組み（どの属性を見るか）が、利用側に散らばっていた。

**修正**
- 専用の識別属性（`data-node-context-menu`）を定義し、属性名を1か所の定数（`NODE_CONTEXT_MENU_ATTRIBUTE`）に集約した。
- 判定は `isInsideNodeContextMenu(target)` に集約し、他のモジュールは属性名を知らない構造にした。
- 文字入力欄の判定（`isTextEntryTarget`）も、同様に独立した小さなモジュールにした。

**汎用的な教訓**
識別のための属性は、意味付けの属性（`role`、`aria-*`）と分け、専用の `data-*` 属性にする。属性名の定義と判定ロジックは1つのモジュールに閉じ込め、利用側は述語関数だけを使う。

### S4. 寸法を、スタイルとレイアウト定数の2か所で管理していた

**発生する状況**
メニューの位置を画面内に収める補正（クランプ）に使う寸法定数と、実際の見た目を決める CSS クラス（`h-9`＋`p-1`）が、別々に書かれていたとき。

**問題**
コード上は「高さ 44px」の定数なのに、実際の描画は 46px になり、補正の計算がわずかにずれる。値を変えるときに、片方だけ直し忘れる。

**原因**
CSS の `box-sizing: border-box` では、`height` に境界線（border）も含まれる。クラスの合計（ボタン 36px＋パディング 8px）は 44px に見えるが、1px の境界線が上下に加わり、実際は 46px になる。寸法の「元の値」がどちらなのか、定義が2つあった。

**修正**
寸法を、レイアウト定数（`NODE_CONTEXT_MENU_SIZE`）だけから決める形にした。メニュー本体は `style` で幅と高さを指定し、内側のボタンは `h-full` とした。テストで、描画された寸法が定数と一致することを確認した（見た目の差は、実高が 46px から 44px になった1点のみ）。

**汎用的な教訓**
位置計算に使う寸法と、描画される寸法は、同じ定数から決める。「合計すればこうなるはず」という計算に頼らず、`style` で明示する。

### S5. 同じ絞り込み処理が、複数のハンドラに重複していた

**発生する状況**
`nodes.filter((node) => visibleNodeIds.has(node.id))` が、ダブルクリックと右クリックの両方のハンドラに、それぞれ書かれていたとき。

**問題**
絞り込みの条件を変えるときに、片方だけ直し忘れる。ハンドラが呼ばれるたびに、配列が作り直される。

**原因**
既存のダブルクリック用の処理をコピーして、新しいハンドラを作ったため。

**修正**
`useMemo` で `visibleNodes` を1つだけ作り、両方のハンドラが共有する形にした。

**汎用的な教訓**
新しいハンドラが既存のハンドラと同じ導出値を使うなら、コピーせず、導出値を1か所に持ち上げる。

### S6. 1つの巨大なテストファイルに、新しい機能のテストを足し続けた

**発生する状況**
既存の大きなコンポーネントのテストファイルに、新機能の結合テストを約 165 行追加したとき。

**問題**
ファイルが肥大し、新機能に関係するテストを探しにくい。機能の削除や移動のときに、ファイルを分けられない。

**原因**
同じコンポーネントのテストなので、既存のファイルに足すのが最短だったため。リポジトリには既に、関心ごとにテストを分ける前例（`MapStageVisibility.test.tsx`）があったが、参照されなかった。

**修正**
右クリックの結合テストを、新規の `MapStageContextMenu.test.tsx` に分離した。移動の前後でテストの総数が変わらないこと、移動したテストの名前と本体が同一であることを確認した。

**汎用的な教訓**
新しい関心ごとのテストは、既存の前例を探し、同じ流儀でファイルを分ける。移動は「純粋な移動」にして、名前と本体は変更せず、総数を照合する。

### S7. 小さな判定関数を作るかどうかの基準（対応しなかった判断）

**状況**
複数のレビューで、次の指摘が出た。いずれも「対応しない」と判断した。

| 指摘 | 判断の根拠 |
|---|---|
| ダブルクリック用の座標変換と、メニュー用の座標変換が、約4行重複している | 共通のプリミティブ（座標変換、ヒットテスト）を使った4行で、実体のロジックは1か所にある。共通化すると、既存モジュールを変更し、戻り値を広げる必要があり、割に合わない |
| 9個のフラットな入力を、グループ化する | 呼び出し元は1つで、変更の理由は「右クリックの方針」の1つだけ。入れ子にしても凝集度は変わらず、深さが増えるだけ |
| 判定のモジュールを `domain/` に移す | 既存の類似モジュールも同じ場所にあり、配置の好みの問題 |
| 3行のモジュール（`textEntryTarget.ts`）は小さすぎる | メニューとは無関係の汎用述語で、複数箇所から使われる。独立させるのが正しい分割 |

**汎用的な教訓**
「重複している」「小さい」「入れ子にできる」は、それだけでは対応の根拠にならない。変更の理由が複数あるか、利用者が増えるかで判断する。

## 2. 挙動・不具合の指摘

### B1. macOS の Ctrl+クリックで、メニューが開かない

**発生する状況**
macOS で、ノード上を Ctrl を押しながらクリックしたとき。

**問題**
ノードは選択されるが、独自のメニューも、ブラウザ標準のメニューも出ない。

**原因（詳細）**
1. macOS では、Ctrl+クリックは「副ボタンのクリック」として扱われ、`contextmenu` イベントが発火する。
2. ところが、その前に、通常の左ボタンの `pointerdown`（`button === 0`、`ctrlKey === true`）も発火する。
3. このアプリのポインター処理は、`button === 0` の `pointerdown` を受けると、ノード移動のジェスチャを開始し、ノードを選択する。このジェスチャは、`pointerup` が来るまで「進行中」として保持される。
4. `contextmenu` はマウスを押している間（`pointerup` の前）に発火するため、その時点で「ジェスチャが進行中」である。
5. 右クリックの判定には、「ドラッグやパンなどのジェスチャ中は、メニューを開かない」という保護があった。右ボタンを使う通常の右クリックでは、ジェスチャは開始されない（右ボタンの `pointerdown` は無視される）ので、この保護は意図どおり働く。
6. しかし Ctrl+クリックでは、ジェスチャが開始されているため、この保護が「ドラッグ中だ」と誤認し、メニューを抑止する。標準メニューも `preventDefault` で抑止されるため、何も出ない。
7. 根本的な原因は、「ジェスチャが進行中」という状態が、「実際にドラッグしている」ことと同義ではない点にある。ドラッグが始まったかどうかは、移動量が閾値を超えたかで決まり、その情報はジェスチャの内部にあり、外から参照できなかった。

**修正**
`contextmenu` のハンドラの先頭で、`event.ctrlKey` が真で、かつジェスチャが進行中なら、そのジェスチャをキャンセルしてから判定する。Ctrl+クリックは副ボタンのクリックであり、それが開始した主ボタンのジェスチャは、ドラッグではないため。判定の純粋関数やジェスチャの実装は変更していない。

**テスト**
ノードの `pointerdown` の後、`ctrlKey` 付きの `contextmenu` を発火し、メニューが開くこと、進行中だったジェスチャが以降の `pointermove` でノードを動かさないことを確認した。Ctrl を伴わない右クリックの場合（既存テスト）は、従来どおり抑止されることも維持した。

**既知の制限（対応しなかった）**
Windows / Linux で、Ctrl を押したまま左ボタンでドラッグしている最中に右クリックすると、ドラッグが中断される。まれな操作で、ノードは最後に確定した位置で止まるだけで、何も壊れない。ジェスチャ内部の状態を外へ公開する変更に見合わないため、対応しなかった。

**汎用的な教訓**
OS やブラウザによって、同じ操作に対して発火するイベントの組み合わせと順序が異なる。「進行中のジェスチャがあれば抑止する」のような保護は、プラットフォーム固有の操作（Ctrl+クリック、長押し）で誤動作しやすい。副ボタンの扱いは、実機のイベント列（`pointerdown`、`contextmenu`、`pointerup` の順序）をもとに確認する。

### B2. タッチの長押しで、メニューが開かない（既知の制限）

**発生する状況**
タッチ端末で、ノードを長押ししたとき。

**問題**
`contextmenu` は発火するが、メニューが開かない。

**原因**
B1 と同じ構造。長押しの間、タッチの `pointerdown`（主ボタン相当）で開始されたジェスチャが進行中のため、ジェスチャ中の保護が働く。`contextmenu` イベントの側から、入力がタッチか、ペンか、マウスかを確実に区別する方法がなく、B1 のように `ctrlKey` で判別することもできない。

**対応**
対応しない。確かな判別手段がなく、今回の範囲外のため、既知の制限として PR 本文に明記した。

### B3. 表示位置が変わると、メニューがノードから離れて残る

**発生する状況**
メニューを開いたまま、`F` キー（選択ノードを画面中央へ移動する）を押すなど、ホイール以外の方法でビューポートが変わったとき。

**問題**
メニューは開いたときの画面位置に残るが、ノードの位置は変わる。メニューが、対象のノードから離れた場所に浮く。

**原因**
メニューは、開いた時点の「画面座標」に固定されて表示される。ビューポートが変わると、同じノードの画面座標も変わるが、メニューはその変化を知らない。閉じる条件として、ホイール（ズーム）だけは購読していたが、キーボードのショートカットによる移動や、リセットなど、他の経路は購読していなかった。「ビューポートが変わる経路」を列挙して購読する方式は、経路が増えるたびに漏れる。

**修正**
メニューを開いた時点のビューポート（`offsetX`、`offsetY`、`scale`）を、状態と一緒に保持する。現在のビューポートが、保持した値と異なるとき、メニューを「失効」と判定する。経路を列挙する代わりに、「結果として変わったか」を比較するため、今後別の経路が増えても漏れない。比較は、参照ではなく、フィールドごとの値の比較にした（B6 参照）。

**既知の挙動（対応しなかった）**
対象ノードがすでに画面中央にある場合、`F` を押してもビューポートは変わらないため、メニューは閉じない。メニューの位置は対象に対して正しいままで、実害がないため、仕様どおりと判断した。

**汎用的な教訓**
画面座標に固定して表示する要素は、「座標が変わりうる原因」を購読するのではなく、「固定した時点の基準」を保持し、現在の基準と比較して失効させる。

### B4. Tab やフォーカス移動で、メニューが閉じない

**発生する状況**
メニューが開いている間に、Tab キーでフォーカスを移動したとき。

**問題**
メニューが開いたまま残る。さらに、その状態で Enter を押すと、フォーカスが外れた後のキーボードショートカットが動作し、ノードが追加される。

**原因**
WAI-ARIA のメニューの慣例では、フォーカスがメニューから出たら、メニューは閉じる。しかし、閉じる条件が「Escape」「外側のクリック」「ホイール」「ウィンドウのフォーカス喪失」の4つだけで、フォーカスの移動を扱っていなかった。キーボードだけで操作するユーザーは、マウスの外側クリックを使わないため、メニューを閉じる手段が Escape しかなかった。

**修正**
当初は `focusout` を購読して閉じた（B5 でさらに修正）。最終的には、Tab キーの押下でも閉じ、フォーカスが別の要素（メニューの外）へ移った場合も閉じる。

### B5. Safari で、メニュー項目をクリックしても動作しない（B4 の修正による退行）

**発生する状況**
Safari（WebKit）で、メニューを開き、項目をマウスでクリックしたとき。

**問題**
マウスのボタンを押した瞬間にメニューが消え、クリックが項目に届かず、項目の処理が実行されない。Chrome では起きないため、開発中に気付きにくい。

**原因（詳細）**
1. B4 の修正で、`focusout` イベントを購読し、「フォーカスがメニューから離れたら閉じる」とした。判定は「`relatedTarget`（フォーカスの移動先）がメニューの内側でなければ閉じる」だった。
2. `relatedTarget` は、フォーカスがどの要素にも移らないとき（本文や、ブラウザの外へ出たとき）は `null` になる。当初のコードは、`null` も「メニューの外へ出た」と判定した。
3. Safari では、ボタンをマウスでクリックしても、ボタンにフォーカスが移らない（ボタンはマウスでフォーカスできない要素として扱われる）。メニューを開いたとき、項目のボタンは `autoFocus` でフォーカスされているが、そのボタンを `mousedown` すると、フォーカス可能な祖先がないため、フォーカスが解除される。
4. このとき、ボタンの `focusout` が `relatedTarget === null` で発火する。コードはこれを「メニューの外へ出た」と判定し、メニューを閉じる。
5. `focusout` は離散イベントのため、React は更新を同期的に反映し、メニューは `mousedown` の時点でアンマウントされる。`mouseup` の時点にはボタンが存在せず、`click` が発火しない。
6. 根本的な原因は、`relatedTarget === null` の意味が曖昧な点にある。「別の要素へ移った」のか、「フォーカスが失われた」のか、「ブラウザの外へ出た」のか、「マウスで押したがフォーカス不可だった」のかを区別できない。

**修正**
1. `focusout` で閉じるのは、`relatedTarget` が `null` でなく、かつメニューの外のときだけにした。`null` のケースは、別のリスナーで担保されている（外側のクリックは `pointerdown`、ウィンドウの離脱は `blur`）。
2. Tab キーの押下で閉じるようにした（Tab で本文へ移るとき、`relatedTarget` が `null` になるため）。
3. メニューの `mousedown` を `preventDefault` し、押下でフォーカスが外れないようにした（`click` は、`mousedown` の `preventDefault` では抑止されない）。

**テスト**
`relatedTarget: null` の `focusout` では閉じないこと、メニュー外の要素への移動では閉じること、メニュー内への移動では閉じないこと、Tab で閉じること、`null` の `focusout` の後に項目をクリックして通知が呼ばれること、`mousedown` が `preventDefault` されること、を単体と結合の両方で確認した。

**汎用的な教訓**
- ブラウザ間で、フォーカスとクリックの関係が異なる。特に Safari は、ボタンをクリックしてもフォーカスが移らない。フォーカスの喪失を契機にした「閉じる」処理は、Safari での動作を必ず確認する。
- `relatedTarget` が `null` になる場合を、「フォーカス移動の結果」として扱ってはいけない。
- 修正が、別のブラウザや別の経路で、別の問題を生むことがある（B4 の修正が B5 を生んだ）。リスナーを足す修正は、「その契機が、意図しない場面で発火しないか」を再確認する。

### B6. 項目をダブルクリックすると、ノードが作られる

**発生する状況**
メニューを開き、「イラストを生成」を素早くダブルクリックしたとき（習慣的な操作として、十分ありうる）。

**問題**
1回目のクリックで項目が実行され、メニューが閉じる。2回目のクリックは、メニューがあった位置の下にあるキャンバスやノードに届く。その結果、ダブルクリックの処理が動き、新しいノードが作られる（ノードの上なら、ラベルの編集が始まる）。

**原因（詳細）**
1. ブラウザの `dblclick` イベントは、「2回目のクリックの対象の要素」に発火する。クリックの回数は、時間と位置で数えられ、要素は関係しない。
2. メニューのコンポーネントには、`onDoubleClick` の伝播を止める処理（`stopPropagation`）があり、メニュー上のダブルクリックがキャンバスへ伝わらないようにしていた。
3. しかし、1回目のクリックでメニューが同期的に閉じる（クリックは離散イベントのため、React は更新を即座に反映する）。2回目のクリックの時点で、メニューは存在しないため、2回目はキャンバスの要素が対象となる。メニューの `stopPropagation` は、そもそも呼ばれない。
4. 「メニュー内のイベントを遮断する」という設計は、メニューが存在し続けることを前提としており、「1回目のクリックで自分が消える」ケースを想定していなかった。

**修正**
- 純粋関数 `isDoubleClickFromMenuActivation(activatedAt, now)` を新設した（時間の窓は 500ms）。
- 項目の実行時に、実行時刻を `ref` に記録する。キャンバスの `dblclick` ハンドラは、実行から 500ms 以内なら、何もせずに戻る。
- `Date.now()` は、メニューを実行した後にだけ読むようにした。通常のダブルクリックで読むと、`Date.now` をモックしてカウンターとして使う既存のテスト（ノード ID の採番）が壊れたため。

**テスト**
純粋関数の境界（窓の内側、ちょうど窓の長さ、窓の外側、時計が戻った場合、メニュー未実行）、実行直後の空白へのダブルクリックと、ノード上へのダブルクリックで、ノードが作られず、編集も始まらないこと、時間が経過した後は通常どおり追加できることを確認した。

**既知の制限（対応しなかった）**
OS のダブルクリック速度が最遅に近い設定の場合、2回のクリックの間隔が 500ms を超えることがあり、ガードが効かない。ユーザーが設定を極端に遅くし、かつ項目をダブルクリックした場合にしか起きない。代替案は、`mousedown` の `detail`（連続クリックの回数）で数える方法だが、実装が複雑になり、得るものが小さいため見送った。

**汎用的な教訓**
「自分が消えるクリック」の直後の2回目のイベントは、下の要素へ届く。メニューやダイアログが、操作の直後に閉じる場合、その直後のイベント（ダブルクリック、キーのリピート）が、下の要素に誤って作用しないか確認する。

## 3. テストの指摘

### T1. 同じ規則を、複数の層でテストして、所有者が曖昧になっていた

**発生する状況**
モジュールを分割した後も、元のモジュールのテストが、分割された先の規則（リスナーの挙動など）を、そのまま再テストしていたとき。

**問題**
同じ規則のテストが複数のファイルにあり、規則を変えたときに、どのテストを直すべきか分からない。分割の意図（所有者を明確にする）が、テストの構造で崩れる。

**原因**
既存のテストを「変更しない」という制約を優先し、分割の後に、テストの責任を見直さなかった。

**修正（誰が何をテストするか）**
- 規則を持つモジュールのテストが、規則の全分岐を持つ（例: 失効の判定は、リセット、非表示、削除、ビューポートの各条件を個別に確認）。
- それを組み立てる側のテストは、「接続されていること」だけを確認する（例: フックのテストは、Escape でメニューが閉じることを1件だけ確認）。
- 結合テスト（コンポーネント）は、「判定結果を、副作用に正しく変換すること」を確認する。

**汎用的な教訓**
テストは「どのモジュールが、どの規則を持っているか」を表す。規則のテストは、持ち主に置く。組み立てる側は、接続のテストだけ持つ。

### T2. 値の比較と、参照の比較を区別するテストが無かった

**発生する状況**
ビューポートの比較を、フィールドの値で行う実装の場合。

**問題**
将来、比較を参照の等価（`!==`）に変えても、すべてのテストが通る。実際には、同じ値の新しいオブジェクトが毎回作られるため、メニューが開いた直後に閉じてしまう（なお、最新のビューポートは、値が同じでも、オブジェクトが新しくなることがある）。

**原因**
テストが、すべて同じオブジェクト（同じ参照）を渡していたため、参照の比較でも、値の比較でも結果が同じになった。

**修正**
同じ値で新しいオブジェクトを渡す（`{ ...viewport }`）テストを、失効の判定と、フックの両方に追加した。

**汎用的な教訓**
値の等価を契約とする関数は、「同じ値の別のオブジェクト」を渡すテストを必ず持つ。

### T3. 「戻しても復活しない」ことを確認するテストが、1つの条件にしか無かった

**発生する状況**
状態の失効を、レンダー中の状態のリセット（`setState`）で行っている場合。

**問題**
リセットが、導出だけの値（`isStale`）に置き換えられると、条件が元に戻ったとき（ノードが非表示から再表示へ）に、メニューが復活する。この退行を検知できるのは、リセット回数（`resetRevision`）の条件だけだった。

**原因**
復活を確認するテストが、最初に書かれた条件にしか追加されなかった。

**修正**
「非表示にして、再表示すると、復活しない」「ビューポートを元に戻しても、復活しない」を、フックのテストに追加した。

**汎用的な教訓**
失効（無効化）を持つ状態は、条件ごとに、「失効した後、条件が戻っても復活しない」ことを確認する。

### T4. 複数のイベントを1つのテストに合算し、失敗の原因が分からなかった

**発生する状況**
外側のクリック、ホイール、ウィンドウの離脱の3つを、1つのテストで続けて発火し、呼ばれた回数（3回）だけを確認していたとき。

**問題**
1つのリスナーが壊れ、別のリスナーが2回発火しても、合計が3になり、テストが通る。失敗しても、どのイベントが原因か分からない。

**修正**
イベントごとに、独立したテストに分割した（それぞれ、ちょうど1回呼ばれることを確認）。

**汎用的な教訓**
複数の契機を、合計の回数で確認しない。契機ごとに、独立したテストにする。

### T5. テストの道具が、意図と違うイベントを発火していた

**発生する状況**
ウィンドウの `blur` を、テストライブラリの `fireEvent.blur(window)` で発火したとき。

**問題**
このヘルパーは、`blur` だけでなく、`focusout` も発火する。`focusout` のリスナーが追加された後、`blur` のテストで、閉じる処理が二重に呼ばれ、回数の確認が失敗した。さらに、`blur` のリスナーだけを確認したいのに、`focusout` のリスナーでも通ってしまう。

**原因**
テストライブラリのヘルパーが、実際のブラウザの挙動を再現するために、関連するイベントを併せて発火する仕様だった。

**修正**
`blur` のテストでは、素のイベント（`new Event("blur")`）をウィンドウに発火し、リスナーを個別に検証した。

**汎用的な教訓**
テストのヘルパーが、複数のイベントを発火することがある。特定のリスナーを検証するときは、そのイベントだけを発火する。

### T6. そのほかのテストの品質に関する指摘

| 指摘 | 内容 | 対応 |
|---|---|---|
| 到達不能な DOM の構造 | `<textarea>` の子に `<span>` を入れたテスト。HTML の仕様上、`<textarea>` の中身はテキストであり、要素にならない。テストの名前が、実際には起きない状況を想定していた | 名前を、実際に確認していること（`closest` で解決できる要素）へ変更した。要素の構築も、`innerHTML` でなく `createElement` で行った |
| 属性名のリテラル | テストのデータに、属性名の文字列（`data-node-context-menu`）を直接書いており、定数の定義と二重になっていた | 定数のインポートへ統一した（属性名を変えたとき、無関係な理由でテストが落ちるのを防ぐ） |
| 同じ規則の重複 | 非有限の座標の処理を、下位のモジュールと、上位の判定の両方でテストしていた | 規則の持ち主（下位）だけに残した。上位では、「対象なし → `dismiss`」の対応だけを確認した |
| 変異による確認の落とし穴 | 「この行を無効化すると、テストが落ちること」を確認するため、実装者が `sed` で該当行をコメントアウトしたが、パターンが一致せず、変更が適用されないまま「テストが通った」 | 無効化した後に、変更が実際に適用されたことを確認する（行番号で指定する、差分を確認する）。確認を終えたら、元の内容と完全に一致することを差分で確認する |
| 前提の事前確認の欠落 | 「ノードが動かない」テストが、修正が無くても、先行するメニューの確認で落ちるため、単独では意味がないように見えた | 残した。別の誤った修正（ジェスチャを継続したまま、メニューを開くだけ）を検知できる、固有の価値があるため |
| `Date.now` のモック | 時刻を読む処理を、ダブルクリックのハンドラの先頭に置くと、`Date.now` をカウンターとして使う既存のテストが壊れる | メニューの実行後にだけ読む形にした |

## 4. ドキュメント・ルール・PR 本文の指摘

### D1. 「正本」と宣言した文書に、既存のルールが抜けていた

**発生する状況**
新しい共通ルールの文書（`AGENTS.md`）が、「ルールは必ずここへ書く正本」と宣言する一方、リポジトリに既にあるルール文書（`.github/copilot-instructions.md`）の内容を含めず、参照もしなかったとき。

**問題**
`AGENTS.md` だけを読むエージェントが、日本語で書くルールや、マージ後の後処理（ロードマップの照合、worktree とブランチの整理）を知らずに動く。また、「ユーザーの指示なしに worktree やブランチを削除しない」という新しいルールが、「マージ後に worktree とブランチを整理する」という既存のルールと、適用の場面（マージ前か、マージ後か）が書かれていないため、矛盾して読める。

**原因**
新しい文書を、既存のルール文書の存在を確認せずに作った。「どのルールが、すでにどこにあるか」の棚卸しが無かった。

**修正**
- 「言語」「Pull Requestレビュー」「PRマージ後の後処理」の節を追加した。
- ブランチ保持のルールの見出しに「マージ前の扱い」と明記し、マージ後は後処理に従うと書いた。
- 2つの文書の関係（内容を一致させる。食い違う場合は、PR レビューとマージ後の後処理について、`.github/copilot-instructions.md` を優先）を明記した。

**汎用的な教訓**
新しいルール文書を作るときは、既存のルール文書を一覧し、(1) 取り込む、(2) 参照する、(3) 優先順位を決める、のいずれかを行う。時間軸の違い（マージ前と後）や、対象者の違いで適用が分かれるルールには、適用の条件を明記する。

### D2. PR 本文の事実が、差分と食い違っていた

**発生する状況**
PR の本文に、「既存のテストファイルから、9件のテストを新しいファイルに移した」と書いたとき。

**問題**
PR の差分（基準ブランチとの差）では、既存のテストファイルは変更されておらず、新しいファイルは、17件のテストを含む「新規ファイル」である。9件を「移した」という記述は、差分を見るレビュアーを混乱させる。

**原因**
本文を、自分の作業の履歴（途中のコミットで、右クリックのテストを追加し、その後、別ファイルへ移した）をもとに書いた。レビュアーが見るのは、基準ブランチとの最終的な差分であり、履歴ではない。履歴の視点と差分の視点がずれていた。

**修正**
「既存のテストファイルは変更していない。右クリックの結合テスト（17件）は、新規のテストファイルに追加した」に直した。テストの件数は、実際の `it(` の数を数えて確認した。

**汎用的な教訓**
PR 本文は、「基準ブランチとの差分」を基準に書く。作業の履歴（途中で移した、直した）を、そのまま書かない。件数、ファイルの一覧は、差分から機械的に確認する。

### D3. 手動確認の手順が、仕様の例外を反映していなかった

**発生する状況**
手動確認の手順に、「`F` キーを押すと、メニューが閉じる」と書いたとき。

**問題**
対象ノードがすでに画面中央にあると、ビューポートが変わらないため、メニューは閉じない（仕様どおり）。手順どおりに確認した人が、「閉じない」ことを不具合と誤解する。

**修正**
手順に、「表示位置が変わる場合は閉じる（変わらないときは閉じない）」と条件を明記した。

**汎用的な教訓**
「対応しない」と決めた例外は、レビューのやり取りだけでなく、確認手順や仕様の記述にも反映する。

### D4. コメントの言語（対応しなかった判断）

**状況**
追加したコードのコメントが英語で、一部のコメントが日本語であり、混在しているという指摘があった。

**判断**
対応しない。基準ブランチのコードのコメントは英語が主流で、日本語のコメントは見当たらない。規約（日本語で書く）は、返答とレビューの文章が対象で、コード内のコメントは対象外。どちらに統一するかは好みの問題で、既存の慣行に合わせた現状で足りる。統一したい場合は、別途ルールとして定め、一括で対応する。

**汎用的な教訓**
指摘の事実（何が混在しているか）と、規約の対象範囲を、先に確認する。複数の人が「主流」について異なる事実を述べたとき（「コメント自体が無い」と「英語が主流」）、コマンドで確認する。

## 5. レビューの進め方（プロセス）の学び

### P1. 最初のレビューが「指摘なし」でも、観点を変えると、新しい指摘が出る

**状況**
PR の最初のレビューは、本番コードに絞った確認で、「指摘なし」だった。2番目の確認者に、「最初の結論を信用せず、独立に確認する」と指示すると、ルール文書との整合と、PR 本文の事実の確認で、2件の指摘が出た。

**原因**
最初のレビューは、コードの正しさに観点が偏り、周辺の文書や、PR 本文の記述を、差分や既存の文書と照合しなかった。

**対策**
- レビューを依頼するときに、観点（コードの正しさ、テスト、ドキュメントとルール、PR 本文の事実）を分けて指示する。
- 2番目の確認者には、前のレビューを「評価する」ことと、「独立に再確認する」ことの両方を依頼する。
- 「指摘なし」の結論でも、確認者に、見落としの有無を検討させる。

### P2. ループの収束は、「観点を変えて、指摘が無くなる」ことで判断する

**状況**
単一責任の確認では、3つの観点（コンポーネントの境界、純粋モジュールと API の形、テストとドキュメント）を並行し、その後、見落とし探しと、収束の確認を行った。1つの観点で「指摘なし」でも、別の観点で指摘が出た。

**対策**
- 1つの観点の「指摘なし」を、収束とみなさない。
- 収束の確認では、これまで却下した項目の一覧を渡し、「新しい根拠が無い限り、再報告しない」と指示する。同じ議論の繰り返しを避ける。
- 「指摘なしも正しい結果であり、作り出さない」ことを、依頼文に明記する。

### P3. 修正が、新しい不具合を生むことがある

**状況**
B4 の修正（`focusout` で閉じる）が、B5（Safari で項目をクリックできない）を生んだ。修正した直後のレビューで検出されたが、修正した本人のテストでは、検出できなかった。

**対策**
- リスナーの追加や、条件の変更を伴う修正の後は、必ず、修正の差分に対する再レビューを行う（修正の確認と、新しい不具合の探索の両方）。
- 再レビューに、「修正が、意図しない場面で発火しないか」「ブラウザ間の差がないか」という観点を、明示的に渡す。

### P4. 「コミットしない」という制約の下で、差分をレビューに渡す方法

**状況**
ユーザーから「コミットしない」と指示された作業で、タスクごとのレビューに、差分が必要だった。

**対策**
実際のインデックスやブランチに触れずに、一時的なインデックス（`GIT_INDEX_FILE` を別の場所に指定）で、作業ツリーのスナップショット（ツリーオブジェクト）を作り、ツリー間の差分（`git diff <ツリー> <ツリー>`）をレビュー用のファイルとして渡した。ブランチの履歴や、ステージングの状態を汚さない。

### P5. 自分の PR には、Approve を付けられない

**状況**
PR の作成者と、レビューを投稿するアカウントが同じ場合、GitHub は、承認（Approve）を拒否する（`Can not approve your own pull request`）。

**対策**
レビューは、コメント（`COMMENT`）として投稿し、本文の先頭に判定（「承認推奨」「修正依頼」「指摘なし」）を明記する。Approve が付けられない理由も、本文に書き、判定が承認の意思表示であることを伝える。

## 6. 汎用チェックリスト（オーバーレイ型の UI を作るとき）

### 構造
- [ ] イベントハンドラが、「事実の収集 → 純粋関数による意図の決定 → 副作用」の3段に分かれているか。
- [ ] 状態の保持、失効の規則、グローバルな購読が、別々の単位になっているか。
- [ ] DOM を識別する属性は、専用の `data-*` 属性か。属性名の定義と判定は、1つのモジュールに閉じているか。
- [ ] 位置の計算に使う寸法と、描画される寸法は、同じ定数から決まっているか（境界線やパディングを含めた実寸で確認したか）。
- [ ] 新しいハンドラが、既存のハンドラと同じ導出値を、コピーして使っていないか。

### 挙動
- [ ] 右クリック、Ctrl+クリック（macOS）、長押し（タッチ）で、実際に発火するイベントの組み合わせと順序を確認したか。
- [ ] 画面座標に固定して表示する要素が、座標の基準が変わったとき（ズーム、パン、キーボードのショートカット、リセット）に失効するか。基準を保持して比較する方式になっているか。
- [ ] フォーカスの喪失で閉じる処理が、Safari で動作するか（ボタンのクリックでフォーカスが移らない）。`relatedTarget === null` を「外へ出た」と扱っていないか。
- [ ] キーボードだけで、開く・項目を実行する・閉じる（Escape、Tab）ことができるか。フォーカスがメニューから出た後に、グローバルなショートカットが誤動作しないか。
- [ ] 操作の直後に、自分が閉じる場合、直後のイベント（ダブルクリックの2回目、キーのリピート）が、下の要素に作用しないか。
- [ ] 「進行中のジェスチャがあれば抑止する」という保護が、プラットフォーム固有の操作を誤って抑止していないか。

### テスト
- [ ] 規則のテストは、規則を持つモジュールにあるか。組み立てる側は、接続のテストだけか。
- [ ] 値の等価を契約とする比較に、「同じ値の別のオブジェクト」を渡すテストがあるか。
- [ ] 失効する状態に、条件ごとの「戻しても復活しない」テストがあるか。
- [ ] 複数の契機を、合計の回数で確認していないか。ヘルパーが、余分なイベントを発火していないか。
- [ ] 実装を無効化して、テストが落ちることを確認したとき、無効化が実際に適用されたことを確認したか。
- [ ] 属性名などの契約値は、定数から参照しているか。テストの名前が、実際に確認していることと一致しているか。

### ドキュメント・PR
- [ ] 新しいルール文書が、既存のルール文書を取り込む、または参照しているか。適用の場面（時間軸、対象）の違いが書かれているか。
- [ ] PR 本文の件数、ファイル一覧、動作の説明が、基準ブランチとの差分から確認できるか（作業の履歴を書いていないか）。
- [ ] 「対応しない」と決めた例外が、手動確認の手順にも反映されているか。

### レビュー
- [ ] 観点（コード、テスト、ルール・文書、PR 本文）を分けて依頼したか。
- [ ] 「指摘なし」の後も、独立した確認者に、見落としを探させたか。
- [ ] 修正の後に、修正の差分に対する再レビューを行ったか（修正が、新しい不具合を生んでいないか）。
- [ ] 却下した項目の一覧を、次のレビューに渡し、再報告を避けたか。
