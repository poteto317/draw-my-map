# 保存状態の表示 設計

日付: 2026-11-04
対象: ROADMAP Phase 16 候補006「保存状態の表示」

## 意図と成功条件

編集中のマップ本体について、現在の内容がブラウザの保存領域に書けたかを、通知が消えてもヘッダーで把握できるようにする。保存失敗時には現在の内容をJSONで救出できることを伝える。状態は実際の保存結果に従い、空の初期マップや復元失敗を「保存済み」と誤表示しない。

## 現状と制約

- `useMapPersistence` がノードとレイアウトを `serializeMapDocument(createMapDocument(...))` で文字列化し、`useMapStoragePersistence` を通じて復元と自動保存を組み合わせる。
- `useMapStorageRestoration` は初回の `readBody` を読み、V2/V3 は正規化した文字列、V1 は旧文字列を比較基準にする。読み取り不能・不正JSON・本体なしの全てで `initialPersistedSnapshot = currentSnapshot` とする。復元失敗には警告を出すが、この比較基準だけから保存成功を推論できない。
- `useMapStorageAutoSave` は変更後300msのデバウンスで `writeBody` を同期実行する。`lastPersistedSnapshotRef` は `saved` の場合だけ更新する。`failed` なら通知を出し、次の内容変更・明示保存要求・`flushPendingSave` で再試行できる。失敗しただけではタイマーによる自動再試行は起きない。通常のタイマー保存成功では現在 `clearSaveFailureNotice` が呼ばれず、古い失敗通知が残り得る。`flushPendingSave` の成功では呼ばれる。
- `MapStorageSession.writeBody` は `saved | failed | inactive` を返す。`saved` はマップ本体への書き込み成功を意味し、更新日時を持つ一覧インデックスの書き込み失敗は `saved` のまま。保護モード、またはセッション番号が古い/無効な保存先は `inactive`。`flush` の `unchanged` は「書けた」の意味ではなく、復元前・保存内容と同一・非稼働の全てを含む。
- マップ作成・切替・枝移動前は同期 `flush` を呼ぶ。失敗時は操作を止める。別マップの削除後は空いた容量で `flush` を再試行する。開いているマップの削除は保存待ちを捨ててセッションを進める。JSON取り込みは同じ内容でも強制保存要求を立てる。JSON書き出しは現在のメモリ上の snapshot を使用する。
- 既存の `MapOperationNoticeList` は操作通知をヘッダーの全幅行に置き、失敗を `role="alert"` で通知する。`AppHeader` のマップ名・操作コントロールの並びに常設の状態表示はない。

## 決めたこと

`dev-flow-kit/commands/feature.md` の設計時の選択規則に従い、実装可能な推奨案を担当エージェントが選んだ。設計書は独立レビュー後に自動承認するフローであり、この段階で利用者の承認待ちは置かない。

### 比較した案

1. **保存フックに結果と比較基準を集約し、ヘッダーに常設表示する（採用）**。書き込み結果と現在の snapshot が同じ場所にあるため、通知と表示のずれを抑えられる。既存のセッション・保存方式は維持する。
2. `OperationNotice` に保存済み/保存中を足す。操作通知は入れ替わり、失敗もJSON取り込み通知等で置換されるため、常設表示の要件を満たさない。
3. `localStorage` を表示コンポーネントから読み直す。保存先の世代、保護モード、旧形式の正規化と強制保存要求を再実装することになり、誤判定が増える。

### 状態の正本

表示用の保存状態は現在の `MapStorageSession` を持つエディタの `useMapStorageAutoSave` で、復元結果、最後に `saved` を返した snapshot、強制保存要求、最後の `writeBody` 結果から導く。`useMapPersistence` → `MapEditor` → `AppHeader` に渡す。通知文言や `MapFlushResult.unchanged`、一覧の `updatedAt` を保存成功の証拠にしない。保存基準は byte 単位で同じ `currentSnapshot` 文字列。V2/V3 の復元時は codec の正規化文字列を初回成功基準、V1 は旧文字列を比較基準にして新形式への書き戻しを待つ。`saved` を返した書き込みだけを次の基準にする。マップの名前・一覧の更新日時・JSONファイルへの書き出しはこの表示の対象外。

復元フックは初回の結果を `restored`（有効な本体あり）、`empty`（本体なし）、`failed`（読み取り不能または解析不能）として保存フックへ渡す。`hydrated` と snapshot 基準は従来通り保持する。`empty` と `failed` の初期 snapshot を「書けた証拠」に使わない。失敗警告は従来の通知のまま残す。保護モードの判定には `Home` が既に持つ `MapLibraryView.storageMode` を `MapEditor` → `useMapPersistence` → 保存フックへ明示的に渡す。`inactive` の戻り値だけでは保護モードと旧セッションを区別できないため、旧セッションには成功を表示しないが保護モードの文言を誤用しない。

### 表示と遷移

| 場面 | 常設の表示 | 条件と次の遷移 |
| --- | --- | --- |
| 復元前 | `保存状態を確認中` | `hydrated=false`。書き込みをせず、`flush` の `unchanged` でも保存済みにしない。 |
| 有効な本体の復元直後 | `保存済み` | 現在 snapshot が復元基準と同一の場合だけ。V1 の移行待ちは `保存待ち`。 |
| 本体が無い新しいマップ | `保存前` | 初期の空マップには本体の書き込み実績がない。編集/強制要求で `保存待ち`。 |
| 復元失敗後の空マップ | `復元できませんでした` | 警告を残し、実際に `saved` が返るまで `保存済み` にしない。編集後は保存待ちへ進むが、失敗の由来は通知で追える。 |
| 編集・JSON取り込み後の300ms待ち | `保存待ち` | 現在 snapshot と成功基準が異なる、または同一でも強制保存要求がある。連続編集でタイマーが延びる現行動作を反映する。 |
| `writeBody` 実行中 | 表示を切り替えない | `localStorage.setItem` は同期。React が「保存中」を描画する間はないので、架空の進行表示や遅延は加えない。候補006の「保存中」は実際の待機状態を `保存待ち` として正確に表現する。 |
| タイマー/flush の `saved` | `保存済み` | 書いた snapshot が現在の確定済み snapshot と一致する場合。通常のタイマー成功でも失敗通知を消す。異なる新しい編集があれば `保存待ち` を保つ。 |
| タイマー/flush の `failed` | `保存失敗` | 成功基準を更新しない。失敗通知の救出案内は維持する。新たに編集しても次の `saved` または確認済み成功基準への復帰まで `保存失敗` を優先し、再試行待ちを隠さない。次の内容変更・明示要求・flush でのみ再試行する。 |
| 失敗後、確認済みの保存済み snapshot に戻る | `保存済み` | 復元済みまたは書込済みの確実な成功基準に戻った場合に限る。別 snapshot に向けた古い強制要求は失効させ、失敗通知も消せる。現在 snapshot 自体への強制要求は実際の保存まで維持する。本体なし/復元失敗の仮の基準へ戻っても `保存失敗` を維持する。 |
| 保護モード | `ブラウザへ保存できません` | `storageMode=protected` を優先し、編集後も `保存済み` としない。既存の切替不可表示と起動通知は維持する。 |
| 旧セッションの `inactive` | 旧画面には新しい成功状態を反映しない | A→B→Aを含むセッション世代の切替で旧タイマーと表示は破棄。旧セッションの `inactive` を成功扱いしない。 |

`flushPendingSave` は最後の確定済み snapshot を同期で書く。成功なら保留タイマーを消して成功基準を進め、失敗なら失敗を残す。`unchanged` だけでは表示を変更しない。別マップ削除後の flush 再試行も同じ経路を通し、成功した場合だけ回復する。現在マップの切替・削除・枝移動でエディタを再マウントすると新セッションの復元結果から表示を作り直し、旧マップの状態を引き継がない。`requestSnapshotSave` が現在の snapshot と同じ内容を指定しても保存完了までは `保存待ち` とする。書込失敗後は、本体なし・復元失敗の仮の基準への復帰では失敗を解除しない。

### UI とアクセシビリティ

マップ名の近く、ヘッダーの通常行に短い状態テキストを常設する。`operationNotices` の全幅行に混ぜず、操作通知が無いときも表示する。色だけに頼らず上表の文字列を出す。通常の状態変化には `role="status"` と `aria-live="polite"` を一つだけ使い、失敗を常設領域から再度 `alert` にはしない。保存失敗は既存の `MapOperationNotice` の `role="alert"` が一回伝える。300msごとの待機表示を読み上げ過多にしないよう、同一文言の再通知を避ける。状態要素にはマップ名と独立したアクセシブルな説明（例 `保存状態: 保存済み`）を持たせる。JSON救出の詳細文は既存の失敗通知に任せ、常設表示には重複させない。

## 範囲外と注意点

- 手動保存ボタン、自動再試行の新設、最大待機時間の変更、保存先やデータ形式の変更、依存パッケージの追加は行わない。連続入力が300ms未満の間隔で続くと保存されない既存仕様は L-399 のリスクとして記録する。
- 読み取り失敗後に編集すると、現行実装は空のマップを書き込める。今回の表示は復元失敗を成功扱いしないが、保存保護方式そのものの変更は対象外。警告が先に見えなくなる可能性も含め、実装レビューでは保存済みの表示を「書き込み成功後」に限定する。失敗時の救出は現在のメモリの JSON 書き出しであり、失われた元データの復旧を保証しない。
- 別タブでの変更検出・競合防止は候補008。今回の `保存済み` はこのタブの現セッションの `writeBody` 成功のみを意味し、他タブとの整合やバックアップを保証しない。
- 本体成功・一覧インデックス失敗のときは `保存済み` とする。文言の対象を本体に限定し、マップ一覧全体の保存成功とは解釈させない。

## 実装時に検証する事例

TDDで、復元前、本体なし、復元成功（V1/V2/V3）、読み取り失敗、不正JSON、通常の変更と300ms待ち、連続編集の最新 snapshot、書き込み失敗後の編集と成功、失敗後の既知の保存済み snapshot への復帰、JSON取り込みの同一 snapshot 強制保存、同期 flush の成功/失敗、別マップ削除後の再試行、保護モード、旧セッションの `inactive`、マップ切替時の表示リセット、タイマー成功後の古い失敗通知消去、ヘッダーの配置と aria を確認する。組み立て役での props 配線も結合テストで確認する。`client` 変更後は `npm run verify` を実行する。
