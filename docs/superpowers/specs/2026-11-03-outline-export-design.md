# Phase 15 候補005: Markdown・箇条書きへの書き出し 設計

## 意図と範囲

現在のマップの全ノードを、他の文書で再利用できるインデント付きのテキストファイルとして保存する。Phase 13 の「箇条書きから追加」と向かい合う入口をヘッダーに置く。表示モード、選択、折りたたみ、重要度フィルタ、保存状態によらず、メモリ上の正本 `nodes` を対象にする。

対象は Markdown (`.md`) とプレーンな箇条書き (`.txt`) のファイル書き出しだけ。クリップボード、選択枝だけの書き出し、プレビュー、JSON形式の置換、取込みparserの拡張、依存ライブラリの追加は含めない。正本・履歴・保存内容は一切変更しない。

## 判断した方式

1. **採用: 共通の全件走査から2形式を出す。** Markdownは各行 `- `、テキストは各行 `・` を使い、どちらも1階層につき半角スペース2個を付ける。形式ごとに明示したヘッダーボタンを置く。Phase 13のparserが両記号を認識し、利用者が形式を選べる。
2. 単一の `.md` だけにする案はUIが小さいが、箇条書きのテキストファイルを直接使いたい用途を満たさない。
3. JSONを文字列化してMarkdown中に埋める案はID・属性を保持できるが、普通の箇条書きとしての再利用性が落ち、Phase 13の取込み対象にもならない。

この形式選択と下記の出力上限はエージェントの推奨判断であり、利用者が個別に承認したものではない。今回の仕様文書作成は親タスクの指示に基づき進める。出力上限は、10,000段の鎖だけでインデントが約1億文字になり得るため、ブラウザの停止やメモリ枯渇を避ける判断である。Phase 13の取込み文字数上限と同じ値にする。

## 出力の契約

- `nodes` 全件を `buildOutlineRows(nodes)` で先行順へ変換する。根の順は正本配列に現れる順、同じ親の子の順も正本配列に現れる順。配列が先行順でなくても親子関係に沿って並べる。深さは行の `depth - 1` を使い、選択や描画用の `displayState.displayNodes` / `visibleNodeIds` は参照しない。非表示・折りたたみ中のノードも含む。
- ノード1個を1行にし、行頭は `"  ".repeat(depth)`、続いて形式ごとの記号とラベルを置く。改行はLF、最終行にもLFを1つ付ける。先頭にタイトル、BOM、メタデータ、空行は付けない。空マップは警告「書き出すノードがありません。」としてファイルを作らない。
- 深い木でも走査は既存の反復処理を使い、整形もループで行う。再帰、子孫ごとの全配列検索、途中の部分ファイル書き出しはしない。全文生成前に形式ごとの出力長を積算し、上限超過ならノードを省かず書き出し全体を拒否する。生成・Blob作成が失敗したら全体を失敗として通知する。
- `MAX_OUTLINE_EXPORT_CODE_UNITS = 1_000_000`（UTF-16コード単位）を上限とする。各行の長さは `2 * (row.depth - 1) + prefix.length + normalizedLabel.length + 1`（末尾LF）であり、全行分を加算する。ラベルは下記の正規化と空ラベルの代入後の長さを使う。`Number.isSafeInteger` で深さ・各行長・累計の安全性を確かめ、上限を越えた時点または非安全整数になった時点で専用の上限超過結果を返す。`repeat`、`join`、巨大なインデント文字列、Blob、ダウンロードはこの判定後に限る。ちょうど1,000,000は許可し、1,000,001は拒否する。
- `buildOutlineRows` が `invalidStructure` または `duplicateIds` を示したら書き出しを中止し、構造不正のエラーを通知する。到達不能ノードの仮の深さ1行を正常な階層と誤認させず、部分的なファイルも作らない。元データを修復しない。
- ラベルの `\r\n`、`\r`、`\n`、U+0000〜U+001F、U+007Fは半角スペースに置換し、1ノードを1物理行に保つ。前後の空白は `trim()` により落とし、内部の空白と通常のMarkdown記号はそれ以上変換しない。空になったラベルには目視できる `（空のノード）` を代入し、ノードを省かない。Markdown記号はエスケープしない。たとえばラベル先頭の `#`、`*`、`[ ]` はテキストとして出力され、Markdownレンダラーが装飾として解釈することがある。文字列をHTMLとして扱わず、コード実行もしない。
- テキスト出力は `・` の直後にラベルを置く。Markdown出力は `- ` の直後にラベルを置く。例: 根 `企画` と子 `仕様` は `.md` で `- 企画\n  - 仕様\n`、`.txt` で `・企画\n  ・仕様\n`。

## 取込みとの往復範囲

Phase 13 の `parseOutlineText` は `.md` / `.txt` をファイルから直接読まない。書き出したテキストを取込み欄へ貼り付けると、上限内かつ正しい構造の非空ラベルについて、ノード数・親子関係・根と兄弟の順序は再構成できる。2スペースのインデントは `determineOutlineUnitWidth` の1段幅と一致し、各行の先頭記号は `extractOutlineLabel` が1個だけ除く。ラベルがさらに `- ` や `・` で始まっても、プレフィックスを1個だけ除くため元の記号は残る。

完全な可逆性は保証しない。空ラベルはPhase 13で記号だけの行として捨てられるのでプレースホルダーへ変わる。前後空白、改行、タブ、制御文字は1行化/取込み正規化で失われる。Markdownレンダリングはラベル中の記号を装飾として扱いうるが、parserはMarkdownエスケープや装飾を解釈しない。書き出し文字数は取込みと同じ最大1,000,000 UTF-16コード単位だが、取込みには別に空行でない10,000行の上限があるため、10,001件以上の書き出しは再取込みできない。テキスト形式は `id`、座標、サイズ、重要度、イラスト、履歴、マップ名などを表現しないため、再取込み時にこれらは保持されない。元のデータを完全に保存・復元する用途は既存のJSON書き出し/読み込みを使う。

## UI・ダウンロード・通知

- `MapEditor` の共通ヘッダーの操作群へ「Markdown書き出し」「箇条書き書き出し」の2ボタンを置き、map/outline両モードで表示する。既存のJSON、PNG、SVGと同じボタン操作で即時にダウンロードを始め、ダイアログは出さない。外側のダイアログや取込み・枝移動ダイアログで既存editor根が `inert` の間は操作できない。保護モードでも既存JSON書き出しと同様、メモリ上のマップを救出できる。
- 新しいドメイン整形関数とダウンロードサービスを分ける。後者はUTF-8テキストのBlobを作り、`URL.createObjectURL`、`<a download>` のクリック、`finally` の `URL.revokeObjectURL` を使う。MIMEは `.md`: `text/markdown;charset=utf-8`、`.txt`: `text/plain;charset=utf-8`。ファイル名は既存の `createMapFileName` の安全化・日時規則を拡張して `<mapName>-YYYYMMDD-HHMMSS.md|txt` とし、JSON/画像と同じ基準で無効文字と予約名を処理する。
- 書き出し専用の通知系統を `MapOperationNoticeList` に追加し、保存/JSON通知とは独立させる。成功は「Markdownファイルを書き出しました。」「箇条書きファイルを書き出しました。」、空マップは警告、上限超過または非安全整数は形式共通の警告「書き出すテキストが大きすぎます。JSONで書き出してください。」、構造不正・生成/ダウンロード例外は形式に応じて「…ファイルを書き出せませんでした。」とする。上限超過時はBlob/ダウンロードを呼ばず、部分ファイルを作らない。例外本文やラベル内容を通知に含めない。ダウンロード関数が正常に戻った時だけ成功を表示する。ブラウザによるディスクへの最終保存成功は観測できないため、通知の意味は既存JSONと同じく「ダウンロードを開始した」である。
- 保存失敗の通知が出ていても、現在の `nodes` から書き出しを試行できる。保存の成功/失敗とテキスト書き出しの成否を混同しない。書き出し失敗で正本、選択、表示モード、Undo/Redoを変更しない。

## 実装・検証の境界

実装計画ではTDDで次を固定する: 異なる根と兄弟の配列順、配列が先行順でない森、非表示/折りたたみ/重要度フィルタの全件、深い鎖と幅広い森、空/重複ID/親不在/循環、ラベルの改行/空白/制御文字/Markdown記号/空文字、2形式の正確なLFとMIME・安全なファイル名、例外時のURL破棄と誤成功通知なし、保存失敗と書き出し結果の独立、map/outline双方のヘッダー配線。出力長は両形式でちょうど1,000,000と1,000,001の境界を確認し、超過時にBlob/ダウンロードを呼ばないことを確認する。10,000段の鎖は小さなノードモデルとラベルから出力長を推定して拒否し、巨大な文字列をテスト内でも生成しない。parserとの結合テストは保証範囲のラベルと階層に限定し、ID/属性が保持されるかのような期待を書かない。`client` 変更後は `client` で `npm run verify` を実行する。最終タスクで `ROADMAP.md` の候補005・現在地・最終更新日を実装事実に合わせて更新する。

参照したレビュー知見: L-001（実際の結果を見た成功通知）、L-013（改行形式の意図的な新規生成と損失の明記）、L-048（既存parser/ダウンロードの契約）、L-056（保存失敗との独立）、L-458/L-460（表示対象から正本を作り直さず全件を対象にする）、L-472（配列内の兄弟順）、L-060/L-061（map/outlineと保護状態を含む組み立て配線）。`dev-flow-kit/scripts/README.md` に本設計の作成へ直接使う汎用スクリプトはない。
