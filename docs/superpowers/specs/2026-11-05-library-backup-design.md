# 全マップの一括バックアップ・復元（候補007）設計

作成日: 2026-11-05。対象: Phase 16 の候補007。状態: 実装前の設計判断（ユーザー承認済みとは扱わない）。

## 目的と境界

ブラウザ移行・端末交換のため、現在編集中の内容を含むライブラリ全件を一つのファイルで持ち出し、移行先にまとめて追加できるようにする。成功表示は全件の読取・検証・書込が確認できたときだけ行う。欠損、部分読取、容量不足で黙って項目を落とさず、既存のマップを破壊しない。

対象外: 既存ライブラリの全置換、既存 ID への上書き、重複マップの自動判定、他タブ競合の一般解決（候補008）、ゴミ箱（候補015）、クラウド同期。バックアップファイルはローカルに保存される平文 JSON で、暗号化と自動クラウド送信はしない。

## 既存実装からの制約

- `mapLibraryStorage.ts` は `draw-my-map.maps.v1` の一覧と `draw-my-map.maps.v1.doc.<id>` の本体を別キーに保存する。`mapIndex.ts` の `decodeMapIndex` は不正行を飛ばして `repaired` を返すため、バックアップの完全性検証にそのまま使って「読めた」としてはいけない。一覧は最低1件、ID は `[A-Za-z0-9_-]{1,64}`、名前は最大50コードポイント。
- `useMapLibrary.ts` の `createMap` は一覧だけを書き、本体キーが無い新規マップが正常に存在する。現在の編集状態は `useMapPersistence.ts` の `currentSnapshot` が正本で、300ms 待ちの自動保存が本体へ反映する。`flushPendingSave` は未復元時・変化なし・旧セッションで `unchanged` を返し得るため、「本体が読めた」「書けた」の証明にはならない。`useMapStorageRestoration.ts` の読取・解析失敗後には空の編集状態があり得る。
- `mapLibrarySession.ts` はセッション番号で古い editor の書込と flush 登録を拒み、`useMapLibrary.ts` が `libraryRef` をコミット済み状態と同期する。`pickNewMapId` は一覧と孤立した本体キーの両方を確認し、読取失敗時の ID も使用済みとする。追加復元もこの境界を使う。
- `branchMoveTransaction.ts` は本体2件と一覧をまたぐ操作にジャーナルを使い、起動時に `mapLibraryStartupRunner.ts` が通常の読取より前に復旧する。新しい一括復元も複数キー操作として専用ジャーナルと起動時復旧が要る。既存の枝移動中ジャーナルと同時には走らせない。
- `mapDocumentCodec.ts` の V1〜V3 の検証・正規化はノードの親子関係、数値、イラストの形式と寸法まで扱う。ファイル外枠の検証は別途必要。`mapJsonFileReader.ts` は `File.text()` の例外を扱い、`mapJsonDownload.ts` は Blob URL を `finally` で解放する。
- `page.tsx` がライブラリ画面と editor を組み立てる。`MapLibraryDialog.tsx` は `dialogClickCapture`、`useDialogFocusTrap`、画面単位のフォーカスを持つ。`MapLibraryNameForm.tsx` は IME 中 Enter とキーリピートを除外し、`MapLibraryDeleteConfirm.tsx` は安全側のキャンセルを初期フォーカスにする。新しい確認画面もこれに合わせる。

## 方式の比較と採用

1. **版付き単一 JSON + 追加復元（採用）**: 1ファイルで移行でき、復元時に既存マップを保てる。全件検証と複数キーの復旧記録が必要。ID はすべて新規発行する。
2. マップごとの複数 JSON または ZIP: 個別救出しやすいが、全件が揃ったか確認しづらく、ZIP の依存と失敗経路が増える。既存の1件 JSON とも別の集合管理が必要。
3. 既存一覧をファイル内容で全置換: 移行先の再現は簡単だが、既存マップや未保存編集を消す危険がある。候補007の初回実装には採らない。

採用は本設計の判断であり、ユーザーから方式を選択・承認された記録ではない。

## ファイル形式と制限

例（実際の `document` は V3 の全ノードを含む）:

```json
{
  "format": "draw-my-map-library-backup",
  "version": 1,
  "exportedAt": "2026-11-05T00:00:00.000Z",
  "currentMapId": "source-a",
  "maps": [
    {"id": "source-a", "name": "旅", "createdAt": "2026-11-01T00:00:00.000Z", "updatedAt": "2026-11-05T00:00:00.000Z", "document": {"version": 3, "layoutMode": "manual", "nodes": []}}
  ]
}
```

外枠と各行は `unknown` から厳密に検証する。形式識別子・version・有効な日時・1件以上の配列・ユニークで有効な元 ID・`currentMapId` の包含・名前の既存規則への適合・各 `document` の V3 全検証を要求する。余分なキーは保存に持ち込まず、既知のフィールドだけで新しい構造を作る。将来版、通常の1件 JSON、途中で切れた JSON、1件でも壊れた行、重複 ID は全件拒否する。インポート時に V1/V2 の個別マップ形式を暗黙移行しない。マップ内ノード ID はマップごとに閉じているため維持し、ライブラリのマップ ID だけを新規発行する。名前・作成日時・更新日時は有効性確認後に維持し、元の `currentMapId` は資料として保存するが、追加復元では移行先の現在のマップを切り替えない。

設計上の明示上限は **1ファイル 32 MiB（UTF-8 バイト数）、マップ 1000 件**。書き出し側も生成後の Blob サイズと件数を調べ、超過時はファイルを作らず理由と1件 JSON の救出経路を伝える。読み込み側は `File.size` を `File.text()` より前に検査する。上限内でもブラウザのメモリ・`localStorage` 容量の成功は保証できず、失敗を明示する。固定の「必要空き容量倍率」は案内しない。ファイル名は日時付きの `draw-my-map-library-backup-YYYYMMDD-HHMMSS.json` とし、マップ名を混ぜない。

## 書き出しの流れ

マップ一覧に「全マップをバックアップ」を置く。通常モードだけで使用可能とし、保護モードは既存の現在マップの「JSON書き出し」へ案内する。読み取り開始時に一覧のセッションと生の一覧 JSON を控え、`decodeMapIndex` が `ok` かつ `repaired: false` で、内容が現在の `MapIndexV1` と一致することを確認する。補正で一覧から落ちた行がある可能性を無視しない。専用・枝移動のジャーナルがあれば拒否する。現在の map は editor が登録する **最新の有効な `currentSnapshot`** を取得し、保存待ちや保存失敗があってもその内容を採る。登録には map ID とセッション番号、初回復元の結果、当該 mount で本体への `writeBody` が一度でも `saved` を返した証拠を結び付ける。未登録・復元中・旧セッションは拒否する。初回 `restoreOrigin: "failed"` の場合はこの保存成功の証拠が付くまで拒否し、成功後は保存待ちや後続の保存失敗があっても、その時点の最新 editor document を含められる。初回復元結果は履歴として固定し、資格の回復は別の証拠で判定する。`saveStatus` の表示値、`flush: unchanged`、仮の保存基準から資格を推論しない。単なる `flush` や本体キーの読取で現在の編集内容を代用しない。初回に読めなかった旧本体までバックアップで救出できるとは案内しない。

他のマップは各本体キーを個別に読む。読取例外・不正 JSON は一件でも全体を止め、対象名を知らせる。本体キー `null` は新規作成直後の正常な空マップとも、外部で失われた本体とも区別できない。該当名と件数を確認画面で明示し、利用者が続けた場合に限り V3 の空マップをファイルに含める。無言で省略も空と決め打ちもしない。現在マップの本体キーが `null` でも、前段の資格を満たす editor snapshot を採る。すべての document は既存 codec で検証・V3 化してから格納する。一覧に無い孤立した本体キーは削除失敗の残骸である可能性があり、ライブラリのマップとして収録しない。検出した場合は「一覧に無い保存データは含まれない」と件数を明示する。最後に一覧の生値とセッションを再照合し、変わっていれば中止して再試行を促す。非同期の待ちを挟む場合は各 `await` の後にも世代を確認する。成功通知は Blob・URL・ダウンロード click の同期処理が例外なく終わった後に「ダウンロードを開始した」とだけ述べ、端末への保存完了を保証しない。

## 追加復元の流れ

マップ一覧の「バックアップから復元」でファイルを選ぶ。読み込み中は二重起動を防ぐ。読み取りと解析は書き込みより前に済ませ、全件の名前・件数と「既存マップは残る／新しい ID で追加する／現在のマップはそのまま」を確認画面に出す。既定フォーカスはキャンセル。確認を閉じたときは起点ボタンに戻す。現在マップの未保存内容は `flush` で確定し、`failed` は復元を拒否する。通常の追加復元成功時は現在の session/editor を維持して再マウントしない。`unchanged` の意味を「保存済み」と誤用せず、別途復元完了・現セッション・現在の一覧状態を確認する。復元失敗で `recoveryRequired` となる場合は後述の保護モード移行を行う。

ファイル読込を待った後・確認後に、最新のセッションと一覧の生値を読み直す。`flush` が一覧の更新日時を書き換え得るため、確認ボタン後は先に `flush` し、次にプレビュー時の一覧・セッションと照合する。変わっていれば今回は書かず、最新の一覧で確認をやり直す。ID はファイル内のものを保存先キーには使わず、`pickNewMapId` 相当で全件分を生成する。既存一覧・孤立本体・同じ復元で先に予約した ID の衝突を避け、発行不能・読み取り例外なら書く前に止める。追加後の最終一覧 JSON をメモリ上で一度だけ組み立て、現在の ID と既存エントリを保つ。保存先の既存本体が無いこと、一覧生値が変わっていないこと、両ジャーナルが無いことを再確認する。ここから確定まで同期処理とし、同一タブのライブラリ操作をロックする。他タブとの真の原子性は候補008に委ねるが、検知した不一致は拒否する。

### 複数キー書込・クラッシュ復旧

`localStorage` に複数キーのトランザクションは無い。専用の `draw-my-map.library-restore.v1` ジャーナルを最初に書く。内容は形式・版、操作前の生一覧、作成する全 ID と期待する各本体 JSON、追加後の生一覧。ファイルの値をそのまま信じず、外部ファイルの入力境界と書込計画で正規化・検証してから記録する。journal codec は body JSON を V3 として検証するが、書込値との byte 一致を確かめる証拠であるため、decode 後も JSON 文字列の原文を保持する。未知キーの除去は journal 外枠と body 項目の object に限る。ジャーナルの容量は本体と別に必要である。書込順は **ジャーナル → 新規本体全件 → 最終一覧1回 → ジャーナル削除**。最後の削除を確定点とする。既存の本体キーには書かない。

途中失敗は、一覧を書いたなら操作前の生値へ戻し、書込済み新規キーだけを逆順に削除する。`null` だったキーの復旧は削除、既存文字列の復旧は元の文字列を正確に書き戻す。戻しの各 I/O も失敗し得るので残りも試し、全て戻ったときだけジャーナルを削除する。結果を `saved` / `failed`（元通り）/ `recoveryRequired`（部分適用の可能性）で分ける。`recoveryRequired` では、書込直前に editor から得た最新の有効な document JSON を `createProtectedStorageSession` の `initialJson` に必ず渡して保護モードへ移る。既存 `Home` の `${mapId}:${storageMode}` key に従って editor は再マウントされるが、nodes・layoutMode・illustration の内容はこの JSON から再構成され、個別 JSON に救出できる。選択、Undo/Redo 履歴、viewport など document 外の UI 状態はリセットしてよい。一覧操作・本体保存を止め、救出と再起動後の確認を伝える。「復元成功」は `saved` の後だけ。`failed` はメモリの一覧を変えない。

起動では `mapLibraryStartupRunner.ts` が通常の一覧修復より先に専用ジャーナルを調べる。枝移動ジャーナルと同時に存在、読取不能、壊れた記録、操作前・操作後のどちらでもない一覧、期待値以外の新規本体、戻し失敗のいずれも **自動で上書きせず保護モード**。保護起動で救出する現在本体は、非修復で有効な保存中一覧の `currentMapId` と名前を優先し、保存中一覧が不正・無い・読めないときだけ有効な専用 journal の操作前一覧に fallback する。選んだ現在本体は既存 codec が有効とする V1/V2/V3 の JSON 原文を `initialJson` に渡す。本体が不正・無い・読めない場合は `null` とし、別マップの本体を代用しない。これは新規 journal body に V3 を要求する規則とは別である。正常な途中記録なら、操作前一覧へ戻し、自分が記録した新規本体だけを消し、ジャーナル削除後に通常起動する。途中で止まっても次回同じ手順を再実行できる。既存の `recoverBranchMove` と専用復旧の順序・互いの拒否判定を一か所で組み立てる。ジャーナルが残る間の枝移動・復元の新規実行を拒否する。成功後にだけ hook の一覧を更新し、現在の session は保つ。

## UI・通知

一覧のバックアップ・復元ボタンは目的を区別する。ファイル選択の `accept` は補助であり、内容検証の代用にしない。読み込み・検証・確認・実行・完了/失敗を明確に出す。同じエラーを繰り返してもライブ領域で再告知する。壊れたファイルや容量不足は短い日本語と再試行先を示し、ファイルの全 JSON や画像 data URL は通知・ログへ出さない。復元確認のキャンセルと成功後は一覧へ戻す。書き出しで空本体の確認を出した場合、どのマップが空として収録されるかを示し、キャンセル可能にする。

`MapLibraryDialog` の画面単位 group、フォーカストラップ、`onClickCapture` を使う。復元確認はキャンセルを先頭・既定フォーカスにし、マウス `detail > 1` と Enter/Space の `repeat` を抑止する。ファイル入力とダイアログの Escape/Enter は `isComposing` と `keyCode === 229` を尊重する。非同期ファイル読込中に閉じた・別セッションになった結果は UI に反映しない。無効表示だけに頼らず handler 側も進行中を拒否する。

## 検証と実装時の分割

TDD で codec・読取・トランザクション・復旧・hook・組立 UI の順に RED を確認する。ただし型に必須フィールド・合併型メンバーを足すタスクでは、その呼出側・網羅 switch・既存テストを同じタスクで更新し、各タスク末に typecheck と対象テストを通す。最終的に `client` の `npm run verify`。実ブラウザを観測できない場合、Jest（jsdom）を実ブラウザでの確認と書かない。

受入れの主要例: 現在の300ms保存待ち・保存失敗中の編集がファイルに入る／初回復元失敗から本体書込成功前はバックアップを拒否し、この mount の `writeBody: saved` 後は再び許可、後続の保存待ち・失敗中も最新 editor document を含める／`saveStatus` の一時値・`flush: unchanged`・仮 baseline だけでは資格を回復しない／新規作成だけの `null` 本体は名を挙げて確認し空 document を含める／他マップの読取例外・不正 JSON・未対応版・重複 ID・巨大ファイルで一切書かない／通常の追加復元成功後も既存のキー・現在の編集内容・session/editor を維持／同じファイルを再度復元しても別 ID／ID 衝突と読取失敗時に既存キーを上書きしない／本体の途中・一覧・ジャーナル削除の各失敗でロールバックまたは保護モード／`recoveryRequired` で再マウントしても最新 document の nodes・layoutMode・illustration を保護セッションから復元し個別 JSON で救出できる／ロールバックの `removeItem` 失敗後に再起動して復旧／壊れたジャーナル・両ジャーナル・他者変更で保護／ファイル読込中の A→B→A と確認後の一覧変更で古い結果を適用しない／実際の `Home` → dialog → hook → storage の結合を通す／Enter 長押し・ダブルクリック・IME・フォーカス復帰を確認する。容量テストはジャーナルを置く時、各本体、一覧を書く時で分ける。手動では Chrome/Firefox/Safari のダウンロード、ファイル選択、容量不足、実 IME、キーボード、読み上げを確認する。
