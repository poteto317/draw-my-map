# Phase 12: 複数マップの保存・切り替え 設計

作成日: 2026-10-21
基準: main `785c56f`。作業ブランチは `codex/phase12-multi-map`（`.worktrees/codex/phase12-multi-map`）。

## 目的・範囲

テーマごとにマップを分けて保存し、ブラウザ内で切り替えながら継続して編集できるようにする。ROADMAP Phase 12 の次の5項目を、1つの PR で実装する。

1. 名前を付けてマップを新規作成する
2. 保存済みマップの一覧を表示し、編集対象を切り替える
3. マップの名前変更・削除に対応する
4. マップごとに自動保存し、既存の単一マップの保存データを移行する
5. マップ切り替え時に、編集履歴や非同期処理が別マップへ混在しないようにする

## 対象外

- 他のタブ・ウィンドウとの同時編集。`storage` イベントは購読しない。複数のタブで同じオリジンを開いた場合は、最後に書き込んだ側の内容が残る（後述「他タブとの関係」）。
- マップの複製、並べ替え（手動の順序）、フォルダ分け、検索、ゴミ箱（削除の取り消し）。
- 複数マップをまとめた書き出し・読み込み。JSON は1マップ単位のまま。
- JSON の形式の変更。V3 のまま変えず、マップ名を JSON に含めない。
- `beforeunload`・`pagehide` での保存待ちの書き込み。ページを閉じる直前 300ms 以内の変更が保存されない現在の挙動は変えない。
- `app/layout.tsx` の `title` と `lang` の修正（依頼されていないため）。
- IndexedDB など localStorage 以外の保存先への移行。

## 決めたこと

### ユーザーが決めたこと（2026-10-21）

1. **範囲**: Phase 12 の全5項目を1つの PR にまとめる。
2. **切り替えの方式**: エディタ部分を `key={mapId}` で再マウントする。切り替え・新規作成・削除の前に、現在のマップの保存待ちを同期で書き込む（flush）。flush に失敗したら、切り替えを中止してエラーを通知する。
3. **削除**: 自作の確認ダイアログを出す。最後の1つを削除したら、空の「無題のマップ」を自動で作り、常に1つ以上残す。開いているマップを削除したら、最後に更新した別のマップへ切り替える。
4. **JSON**: 読み込みは今までどおり、現在のマップの中身を置き換える。JSON の形式は V3 のまま変えない。マップ名は、書き出すファイルの名前にだけ使う。
5. **削除の前の flush の扱い**（決定2の補足。設計書の作成者の提案を、ユーザーが2026-10-21に承認）: 開いているマップを削除するときは、そのマップの保存待ちは削除と一緒に捨て、flush しない。開いていない別のマップを削除するときは、エディタを再マウントしないため事前の flush はせず、削除で空いた容量を使えるよう、削除の後に保存待ちの書き込みを再試行する。切り替えと新規作成（いずれも再マウントを伴う）は、flush に失敗したら中止してエラーを通知する。容量不足のときに、不要なマップを削除して容量を空けられなくなる事態を避けるため。

### 推奨案として採用したこと（ユーザーへの確認前の、計画作成者の判断）

コントローラーが推奨案として採用したもの:

- 保存構造は、一覧のインデックス（id・名前・作成日時・更新日時・現在の id）と、マップ本体（中身は V3 のまま）を別のキーに分ける。
- 移行は、起動時に旧キー `draw-my-map.map.v1` があり、インデックスが無い場合に、デコードに成功したときだけ1件として登録する。旧キーは移行に成功してもすぐには消さない。
- 名前は重複を許可し、内部は id で区別する。前後の空白を除き、空なら「無題のマップ」にする。長さの上限は50文字。
- 容量は複数のマップで localStorage の約5MBを共有する。保存に失敗したときの通知に「不要なマップを削除」の案内を加える。
- 他タブとの同時編集は対象外にし、最後に書き込んだ側が優先されることを仕様に明記する。
- `app/layout.tsx` の `title` と `lang` の修正は対象外にする。

この設計書の作成者が推奨案として決めたもの（下の各節で根拠を書く）:

- キー名は、インデックス `draw-my-map.maps.v1`、本体 `draw-my-map.maps.v1.doc.<id>` にする。旧キー `draw-my-map.map.v1` と前方一致で重ならないようにするため。
- 新規作成ではインデックスだけを書き、本体は最初の自動保存で書く。本体の無いインデックス項目は「空のマップ」として正常に扱う。
- 削除は、インデックスを先に書き、本体の削除を後にする。本体を消せなかった場合は孤立した本体として残し、読み込み時は無視する（自動では消さない）。
- 旧キーは、移行した次の起動で消す（インデックスの `legacyCleanupPending` で管理する）。本体か一覧が容量不足で書けない場合だけは、移行した起動のうちに消す（「旧キーからの移行」の 6）。
- インデックスが壊れているときは、壊れた内容を退避キーへ写してから、保存済みの本体から一覧を作り直す。退避か書き込みに失敗したら、保存しない保護モードで開く。
- 書き出すファイルの名前は `<マップ名>-YYYYMMDD-HHmmss.<拡張子>` にする。
- 名前の長さはコードポイント数で数える。上限を超えた名前は切り詰めず、ダイアログ内でエラーを表示して確定させない。
- マップの一覧と作成・名前変更・削除は、ヘッダーのボタンから開く1つのモーダルダイアログで行う。
- 切り替え前に開始していた PNG 書き出しと JSON 読み込みは、再マウント後に結果が出ても捨てる（ダウンロードも通知もしない）。

## Global Constraints

- 新規依存なし。`Node`、`NodeMapState`、V3 の保存形式、JSON の形式、履歴の形式を変えない。
- localStorage を直接読み書きするのは、新しい保存サービス（`services/persistence/mapLibraryStorage.ts`）だけにする。フックやコンポーネントは `localStorage.getItem` や `setItem` を直接呼ばない（L-476）。既存の `MAP_STORAGE_KEY` は旧キーとして移行処理だけが使う。
- インデックスの解析・正規化・更新・名前の正規化・ファイル名の変換は純関数（`domain/mapLibrary/`）、状態と操作の順序は React フック（`hooks/useMapLibrary.ts`）、配線は `Home`、表示と操作は部品、という既存の境界を守る。
- 保存の結果は列挙した結果型で返し、呼び出し元は成功したときだけ状態更新・通知・後続処理を行う（L-001）。localStorage を先に書き、成功してから React の状態を更新する（L-545）。
- 同じイベント内のインデックス更新は、最新のインデックスを持つ ref を基準に順に計算し、古いクロージャの値で前の更新を消さない（L-453）。ref はレンダー中に書き換えず、操作の中で次の値を計算したときと `useLayoutEffect` で同期する（L-468、L-521）。
- エディタの外へ結果を書き出す非同期処理（保存、ダウンロード、シェルへの通知）は、マップ id の値ではなくエディタの世代（セッション番号）で照合する（L-571、L-103）。
- 新しい props とコールバックは必須にする。実際の `Home` から `MapEditor` とヘッダーまで通す結合テストで配線を確かめる（L-060）。
- TDD で進め、`client` の変更後に `npm run verify` を実行する。タスク単位のサブエージェント実装と、別担当の仕様・品質レビューを行う。
- コミット・push・PR 作成は依頼されたときだけ行う。最後のタスクで `ROADMAP.md` を実態に合わせて更新し、Phase 13 を完了にしない。

## 全体の構成

```
Home（シェル。アンマウントされない）
├─ useMapLibrary            … 起動の判定、インデックスの状態、作成・切り替え・名前変更・削除、セッション番号、flush の登録先
├─ MapLibraryNoticeRegion   … シェルの通知の常設ライブリージョン（keyed の部分の外。inert にしない）
├─ MapEditor key={mapId}    … 現在の Home の中身（useNodes、履歴、表示状態、自動保存、書き出し、MapStage など）
│   └─ AppHeader
│       └─ mapControls（シェルから渡す）: 現在のマップ名、「マップ一覧」「新しいマップ」ボタン
└─ MapLibraryDialog         … 一覧・新規作成・名前変更・削除確認（シェルが状態を持ち、エディタの外に描画する）
```

- 現在の `app/page.tsx` の `Home` の中身を `components/map/MapEditor.tsx` へ移し、`Home` はシェルにする。`MapEditor` は `mapId`、`mapName`、`storageSession`（後述）、`mapControls`、`shortcutsEnabled`（ダイアログを開いている間は `false`。後述）を必須の props として受け取る。シェルの通知はエディタへ渡さず、シェルが keyed の部分の外に表示する（「通知の文言」）。
- ダイアログの開閉状態や、操作後のフォーカスの戻し先は、再マウントで消えないようにシェルが持つ。
- シェルは、起動の判定が終わるまではエディタを描画せず、「マップを読み込んでいます…」を `role="status"` で表示する。判定は `useEffect` で行う（サーバー描画と localStorage の内容がずれないようにするため。現在の復元と同じ）。判定を1回だけ確定させる方法は「起動と移行」に書く。React Testing Library の `render` は effect まで実行するため、既存のページのテストは描画直後にエディタを取得できる。

## 保存構造

### キー

| 用途 | キー | 中身 |
| :--- | :--- | :--- |
| インデックス | `draw-my-map.maps.v1` | `MapIndexV1` の JSON |
| マップ本体 | `draw-my-map.maps.v1.doc.<id>` | V3 の JSON（`serializeMapDocument` の出力。今と同じ） |
| 壊れたインデックスの退避 | `draw-my-map.maps.v1.corrupt-backup` | 壊れていたインデックスの生の文字列 |
| 旧キー（移行元） | `draw-my-map.map.v1` | V1〜V3 の JSON（既存） |

- 本体のキーは `mapBodyKey(id)` という1つの純関数で作る（L-539）。id に使える文字を `A-Z a-z 0-9 _ -` に限るため、区切りの `.` と衝突しない。
- 旧キーは `draw-my-map.map.v1` で、新しいキーはすべて `draw-my-map.maps.v1` で始まる。前方一致で本体を探すときは `draw-my-map.maps.v1.doc.` を接頭辞にするため、旧キーや退避キーを本体と取り違えない。

### インデックスの型

```ts
// domain/mapLibrary/mapIndex.ts
export type MapIndexEntry = {
  id: string;          // /^[A-Za-z0-9_-]{1,64}$/
  name: string;        // 正規化済み。1〜50コードポイント
  createdAt: string;   // ISO 8601（UTC、toISOString の形式）
  updatedAt: string;   // 同上
};

export type MapIndexV1 = {
  version: 1;
  currentMapId: string;          // maps のいずれかの id
  maps: MapIndexEntry[];         // 作成順。1件以上
  legacyCleanupPending: boolean; // 旧キーを次の起動で消すか
};
```

- `maps` の配列順は作成順で、表示順には使わない。一覧の表示順は「更新日時の新しい順 → 作成日時の新しい順 → id の昇順」にする（同じ規則を「最後に更新した別のマップ」の選択にも使う）。
- 保存形式は `JSON.stringify(index)`（整形しない）。

### マップ本体の型

- 今の V3 の `MapDocument` のまま変えない。エンコードは `serializeMapDocument`、デコードは `parseMapDocumentJsonWithVersion` を使う。V1・V2 の本体（移行前の旧キーと同じ扱い）も読めるが、新しく書く本体は常に V3。
- 本体のキーが無いことは「空のマップ（まだ一度も保存していない）」を表す。新規作成の直後や、最後の1つを削除して自動で作ったマップがこの状態になる。

### id の生成

- `generateMapId()` は `crypto.randomUUID()` が使えればそれを使い、使えなければ `Date.now().toString(36)` と `Math.random().toString(36).slice(2, 10)` を `-` でつないだ文字列にする。テストでは生成関数を差し替えられるようにする（`useMapLibrary` の省略不可の依存として注入し、`Home` が既定の関数を渡す）。
- 生成した id が、インデックスの既存の id と一致する場合、または `mapBodyKey(id)` のキーが localStorage に既にある場合（孤立した本体）は作り直す。孤立した本体の id を再利用すると、新しいマップに古い内容が出るため。10回作り直しても決まらなければ、作成を中止して通知する。
- id は乱数で作るため、実質的に再利用されない（削除した id は記録しない）。インデックスに id を書く前に、その id を検証用の正規表現で確かめる。

### 日時の扱い

- 作成日時と更新日時は `now().toISOString()`（UTC）で保存する。`now` は注入する（テストで時刻を固定する。L-181）。
- 更新日時を更新するのは、そのマップの本体の書き込みが成功したときだけ（自動保存、flush、JSON 読み込みの後の強制保存）。名前の変更と切り替えでは変えない。作成時は作成日時と同じ値にする。
- 一覧の表示は「更新: YYYY/MM/DD HH:mm」（ローカル時刻）。`toLocaleString` を使わず、数値から組み立てる純関数にする。テストはタイムゾーンを固定して行う。
- 読み込んだ日時が `Date#toISOString` の形式でない項目（`Date.parse` で読めない値に加え、`"2026"`・`"2026-10-21"`・タイムゾーン付きの別表記など、`new Date(Date.parse(t)).toISOString()` と一致しない値）は、項目を捨てずに `1970-01-01T00:00:00.000Z` として扱う（表示は「更新: 不明」）。`updatedAt` は本体を次に保存したときに上書きされ、`createdAt` は補正後の値のまま残る（L-470）。

### インデックスの読み込みと正規化

`decodeMapIndex(raw: string): DecodeResult` を純関数として作り、起動時の判定はすべてこの関数の結果で行う（L-576。読み取りと修復で別々の判定をしない）。

- 結果は `{ kind: "ok", index, repaired }`、`{ kind: "corrupt" }` のどちらか。`raw === null` は呼び出し側で「無い」として別に扱う（L-002）。
- JSON として読めない、トップレベルがオブジェクトでない、`version !== 1`、`maps` が配列でない、は `corrupt`。
- `maps` の各項目は、`id` が正規表現に合う文字列であること、`name` が文字列であることを必須とする。満たさない項目は除外する（本体は孤立した本体として残る）。`name` は正規化し直す（空なら「無題のマップ」、50コードポイントを超えていれば先頭50コードポイントに切り詰める）。日時は上の規則で補う。
- 同じ id が2回以上出たら、最初の項目だけを残す。
- 有効な項目が1件も残らなければ `corrupt`。
- `currentMapId` が `maps` に無い、または文字列でない場合は、表示順の先頭（最後に更新したマップ）を現在のマップにする。
- `legacyCleanupPending` が真偽値でなければ `false` として扱う。
- 正規化で値を直した場合は `repaired: true` を返す。起動時に直した内容はすぐには書き込まず、次にインデックスを書くときに反映する（起動時の書き込みを減らし、読み取りの経路で保存データを変えないため）。

## 起動と移行

### 判定を1回だけ確定させる

- 起動の処理は、localStorage から読み取った値を入力に「書き込む内容・開く状態・通知」を決める純関数 `planMapLibraryStartup(snapshot, deps)`（`domain/mapLibrary/mapLibraryStartup.ts`）と、その計画を書き込みとともに実行する `runMapLibraryStartup(storage, deps)` に分ける。
- 起動の処理は書き込みを伴い、書き込んだ結果が次の判定の入力を変える（例: 移行で `legacyCleanupPending: true` のインデックスを書いた直後にもう一度判定すると、旧キーの後始末が同じ起動中に走り、起動時の通知も2回目の結果で上書きされる）。そのため「何度実行しても同じ結果」にはならない。開発時の StrictMode では effect が2回動くので、次のとおり1回だけ確定させる。
  - シェルは `startupRef = useRef<MapLibraryStartupResult | null>(null)` を持つ。effect は、`startupRef.current` が `null` のときだけ `runMapLibraryStartup` を実行して結果を ref に入れ、その後に ref の結果から state（インデックス、現在の id、保護モード、起動時の通知）を設定する。2回目の effect は ref の結果をそのまま state に設定するだけで、localStorage を読み書きしない。
  - この effect は購読やタイマーを持たず、cleanup が無い。StrictMode の擬似的なアンマウントと再実行では同じコンポーネントの ref が保たれるため、L-469 の「ref の印と cleanup の併用で処理が失われる」問題には当たらない。
  - 起動時の通知は、確定した結果の一部として state に入るため、2回目の effect で別の結果に上書きされない。
  - シェルが本当にアンマウントされて作り直された場合（ページの再読み込みなど）は、新しい起動として判定し直す。
- 移行と旧キーの後始末は、同じ起動の計画に同時に入らない（移行した起動では後始末をしない）。StrictMode で包んだ結合テストで、移行した起動のあとも旧キーが残り、起動時の通知が消えないことを固定する。

### 起動の分岐

起動時に次の順で判定する。各分岐で書くインデックスの値、保護モードかどうか、通知は、「分岐ごとのインデックスと通知」の表にまとめる。

1. **localStorage を使えない**（`window.localStorage` の取得や `getItem` が例外を投げる）: 保護モード（後述）で、空の「無題のマップ」を1件メモリ上に作って開く。
2. **インデックスがあり、`decodeMapIndex` が `ok`**: そのインデックスで開く。`legacyCleanupPending` が `true` なら旧キーの後始末（後述）を行う。
3. **インデックスがあり、`corrupt`**: 「インデックスの破損」（後述）。
4. **インデックスが無く、旧キーも無い**: 初回起動。`{ version: 1, currentMapId: <新しい id>, maps: [{ 無題のマップ }], legacyCleanupPending: false }` をインデックスに書く（本体は書かない）。書けなければ保護モード。
5. **インデックスが無く、旧キーがある**: 移行（次の節）。

### 旧キーからの移行

1. 旧キーの文字列を `parseMapDocumentJsonWithVersion` でデコードする。
2. **デコードに成功した場合**:
   1. 新しい id を作る。
   2. 本体キーへ `serializeMapDocument(document)`（V3）を書く。ノードの id・座標・イラストなどの中身は、デコード結果をそのまま引き継ぎ、作り直さない（L-456）。V1 は今の復元と同じく V3 へ正規化して書く。
   3. インデックス `{ version: 1, currentMapId: id, maps: [{ id, name: "無題のマップ", createdAt: now, updatedAt: now }], legacyCleanupPending: true }` を書く。
   4. 2 の書き込みが容量不足以外で失敗したら、何も書かずに保護モードで旧キーの内容を開く（保護モード用の `storageSession` の `readBody` が旧キーの生の文字列を返す）。旧キーは変えないため、次の起動で再び移行を試す。
   5. 3 の書き込みに失敗したら、2 で書いた本体キーを消して元に戻す。本体キーは書き込み前に無かったことを確かめているため（id の生成時に確認済み）、戻す操作は `removeItem` にする。戻す操作自体の失敗も結果として受け取り、失敗した場合はその本体を孤立した本体として残す（読み込み時は無視される）。どちらの場合も 4 と同じ保護モードと通知にする（L-537）。ただし、3 の失敗が容量不足で、本体を消せた場合は 6 のやり直しへ進む（ローカルレビュー第13周の指摘1で追加）。
   6. 2 の書き込みが容量不足（`DOMException` の `name` が `QuotaExceededError` か `NS_ERROR_DOM_QUOTA_REACHED`、または `code` が 22 か 1014）で失敗したとき、または 3 の書き込みが容量不足で失敗して 2 の本体を消せたときだけ、「旧キーを1回分残す」方針の例外として、メモリ上に旧キーの元の文字列を控えたまま「旧キーを消す → 本体を書く → インデックス（`legacyCleanupPending: false`）を書く」の順でやり直す（ローカルレビュー第12周の指摘1で追加）。Phase 11 までは1つのマップで容量を全部使えたため、旧キーが容量の約半分を超えると、旧キーと本体を同時に置けず、2 が毎回失敗して保護モードから抜け出せなくなるため。
      - やり直しで成功したら通常のモードで開く。旧キーはもう無いため、インデックスは `P: false` にする（結果は `{ ok: true, legacy: "removed" }`。通常の移行の成功は `{ ok: true, legacy: "kept" }`）。
      - 旧キーを消せなかったら、何も書かずに 4 と同じ保護モードにする（`legacy: "kept"`）。
      - やり直しの本体の書き込みに失敗したら、旧キーを元の文字列で書き戻す。インデックスの書き込みに失敗したら、書いた本体を `removeItem` で消してから（書き戻しに要る容量を空けるため）旧キーを書き戻す。旧キーは書き込み前にあったキーなので書き戻し、本体キーは無かったキーなので `removeItem` にする（L-537）。4 と同じ保護モードと通知にする（`legacy: "restored"`。本体を消す操作の成否は `bodyRollback: "notNeeded" | "removed" | "failed"`）。
      - 書き戻しにも失敗したら（`legacy: "lost"`）、旧キーはブラウザに残らない。旧キーの元の文字列は保護モードのセッション（`initialJson`）で画面に開いたままなので、通知の文言を変えて JSON での書き出しを促す。再読み込みすると、旧キーもインデックスも無い初回起動として空のマップで始まる。
      - 旧キーの書き戻しは `mapStorage.ts` の `restoreStoredMapJson` で行い、localStorage を直接触るのは `mapLibraryStorage.ts` と `mapStorage.ts` の関数だけ、という境界を保つ（L-476）。
   7. 移行に成功したときは通知を出さない。一覧には「無題のマップ」として表示される。
3. **デコードに失敗した場合**: 旧キーは消さず、変更もしない（読めないデータを消さない）。初回起動と同じく空の「無題のマップ」でインデックスを作り、`legacyCleanupPending: false` にする。インデックスを書けなければ保護モード。

### 2回目以降の起動と旧キーの後始末

- インデックスがあれば、旧キーの有無にかかわらず移行は行わない。
- `legacyCleanupPending: true` のときだけ、旧キーを `removeItem` する。成功したら `legacyCleanupPending: false` にしてインデックスを書く。旧キーの削除に失敗したら、`true` のまま次の起動で再試行する。インデックスの書き込みに失敗しても、次の起動で旧キーの削除（既に無いキーの削除）を再試行するだけなので害はない。通知は出さない。
- 移行が成功した起動のうちに旧キーを消さないのは、移行直後に問題が見つかったときに、開発者ツールで旧キーから戻せる余地を1回分残すため。容量は2重になるが、次の起動で解消する。ただし、2重にすると本体を書けない場合（旧キーが容量の約半分を超える場合）は、移行の 6 のやり直しで旧キーを先に消すため、この余地は残らない。

### インデックスの破損

1. 壊れたインデックスの生の文字列を `draw-my-map.maps.v1.corrupt-backup` へ書く（既にある場合は上書きする）。
2. localStorage のキーを `key(i)` で列挙し、`draw-my-map.maps.v1.doc.` で始まり、残りが id の正規表現に合うものを集める。id の昇順に並べ、名前を「復元したマップ 1」「復元したマップ 2」…、日時を `now` にした項目を作る。本体の中身はここでは読まない（開くときにデコードする）。
3. 本体が1件以上あれば、それらで新しいインデックスを作る（`legacyCleanupPending: false`。旧キーがあっても触れない）。現在のマップは表示順の先頭。
4. 本体が1件も無ければ、旧キーの有無や状態にかかわらず、移行はやり直さず、旧キーにも触れない。空の「無題のマップ」1件のインデックス（`legacyCleanupPending: false`）を書く。旧キーが残っていても、インデックスがある以降の起動では移行しないため、旧キーはそのまま残る（開発者ツールで取り出せる）。
5. 新しいインデックスを書く。
6. 1 または 5 の書き込みに失敗したら、壊れたインデックスは上書きせずに残し（5 が失敗した場合は元の文字列のまま）、保護モードで開く。この分岐では本体を書かないため、戻す物は無い。
7. 通知は下の表のとおり、分岐ごとに実際に行ったことに合わせる。

### 保護モード

- localStorage へ書き込めない、または書き込むと保存済みのデータを壊すおそれがあるときのモード。シェルの状態 `storageMode: "persistent" | "protected"` で表す。
- 保護モードでは、保護モード用の `storageSession`（「自動保存」の節）をエディタへ渡す。自動保存と flush は書き込まず、通知も出さない。「マップ一覧」「新しいマップ」ボタンを無効にする。ボタンの近くに「保存できないため、マップの切り替えは使えません。」を表示する（L-057）。JSON の読み込み・書き出しと画像の書き出しは使える。
- ページを再読み込みすると、起動時の判定をやり直す。

## 複数キーの書き込み順序と整合性

### 原則

- 1つの操作で書き換えるキーは、可能な限りインデックス1つにする。新規作成・名前変更・切り替えはインデックスだけを書く。
- 本体とインデックスの両方に関わる操作は、「読み込み時に無害な中間状態」を経由する順序にする。
  - 本体だけがある（インデックスに無い）: 孤立した本体。読み込み時は無視する。自動では消さない（何のデータか判断できないものを消さないため。L-004）。インデックスの破損時の作り直しでは拾い直す。
  - インデックスにだけある（本体が無い）: 空のマップとして開く。通知は出さない（新規作成直後と同じ正常な状態）。
- 本体を書いてからインデックスを書く操作（移行）では、インデックスの書き込みに失敗したら本体を戻す。戻す操作は書き込み前の値で分ける（無かったキーは `removeItem`、あった値は書き戻す）。戻す操作の失敗も結果に含める（L-537）。
- 書き込みはすべて `mapLibraryStorage` の関数を通し、`{ ok: true } | { ok: false, error }` を返す。例外を外へ投げない（L-056）。

### 操作ごとの順序

| 操作 | 順序 | 途中で失敗したとき |
| :--- | :--- | :--- |
| 新規作成 | flush → インデックス（項目追加・現在の id 変更） | flush 失敗: 中止（何も変わらない）。インデックス失敗: 中止（本体は書いていないので戻す物は無い） |
| 切り替え | flush → インデックス（現在の id 変更） | flush 失敗: 中止。インデックス失敗: 中止（flush で書いた本体は、そのマップの最新の内容なので戻さない） |
| 名前変更 | インデックス（名前変更） | 失敗: 名前は変わらない |
| 開いていない別のマップの削除 | インデックス（項目削除）→ 本体の削除 → 現在のマップの flush（再試行） | インデックス失敗: 中止。本体の削除失敗: 孤立した本体として残し、warning を通知。flush 失敗: 自動保存の失敗と同じ通知 |
| 開いているマップの削除（ほかにマップがある） | インデックス（項目削除・現在の id を次のマップへ）→ セッション番号を進める → 本体の削除 → 再マウント | インデックス失敗: 中止（開いたまま、保存待ちも残る）。本体の削除失敗: 孤立した本体として残し、warning |
| 最後の1つの削除 | インデックス（項目を新しい「無題のマップ」に置き換え、現在の id も新しい id へ）→ セッション番号を進める → 本体の削除 → 再マウント | 同上 |
| 自動保存・flush | 本体 → インデックス（更新日時） | 本体失敗: 保存失敗として通知。インデックス失敗: 保存は成功として扱い、通知しない（本体が正本。次の保存で更新日時を書き直す） |
| 移行 | 本体 → インデックス | 上記「旧キーからの移行」 |
| インデックスの作り直し | 退避キー → インデックス | 上記「インデックスの破損」 |

- インデックスを書いた後に React の状態（シェルのインデックス、現在の id、セッション番号）を更新する。書き込みに失敗したら状態を変えない（L-545）。
- 開いているマップを削除する場合は、本体を消す前にセッション番号を進める。これにより、まだアンマウントされていない旧エディタの保存（タイマーや flush）がシェルの照合で拒否され、消した本体が書き戻されない。

## 自動保存

### マップ id と保存先を対で持つ

- エディタは `storageSession: MapStorageSession` を props で受け取る。シェルが、切り替えのたびに新しいオブジェクトを作る。

```ts
type MapStorageSession = {
  mapId: string;
  readBody: () => MapDocumentResult<string | null>;   // 本体の読み込み（復元に使う）
  writeBody: (json: string) => MapBodyWriteResult;    // 本体の書き込み＋更新日時の更新
  registerFlush: (flush: () => MapFlushResult) => () => void;
};

type MapBodyWriteResult =
  | { status: "saved" }
  | { status: "failed"; error: string }
  | { status: "inactive" };   // セッションが古い、または保護モード。書き込まない

type MapFlushResult =
  | { status: "saved" }
  | { status: "unchanged" }   // 保存待ちが無い、または復元前
  | { status: "failed"; error: string };
```

- `writeBody` は、作られたときの `mapId` とセッション番号を閉じ込める。呼ばれたときに、セッション番号がシェルの現在のセッション番号と一致し、`mapId` がインデックスにあるときだけ書く。そうでなければ `inactive` を返し、何も書かず、通知もしない。照合はマップ id ではなくセッション番号で行う。A → B → A と切り替えたときに、最初の A のエディタの書き込みが、2回目の A のエディタに紛れ込まないようにするため（L-571、L-103）。
- `useMapStorageAutoSave` と `useMapStorageRestoration` は `storage` の代わりに、`writeBody`・`readBody` を受け取るように変える。localStorage の取得はサービス側で行う。
- 保護モードでは、`createProtectedStorageSession(mapId, initialJson: string | null)` で作ったセッションを渡す。
  - `mapId` はメモリ上だけの id（`generateMapId()` で作り、どこにも書かない）。
  - `readBody` は、起動の結果で決めたメモリ上の文字列を `{ ok: true, value: initialJson }` で返す。移行に失敗した場合は旧キーの生の文字列、それ以外は `null`（空のマップ）。デコードは通常と同じく `useMapStorageRestoration` が行うため、V1・V2 の旧キーも今と同じく読める。
  - `writeBody` は常に `{ status: "inactive" }` を返し、何も書かない。そのため自動保存は通知を出さず、flush は `unchanged` になる。
  - `registerFlush` は登録を受け付けるが、保護モードではシェルが flush を呼ぶ操作（切り替え・新規作成）が無効なので呼ばれない。解除の関数は何もしない関数を返す。

### デバウンスと flush

- 300ms のデバウンス、同じ内容なら書かない、`requestSnapshotSave` による強制保存、失敗時に通知して次の変更で再試行する、という今の挙動は変えない。
- `useMapStorageAutoSave` に `flushPendingSave(): MapFlushResult` を追加する。
  - 復元が終わる前（`hydrated === false`）は `unchanged` を返し、何も書かない。空のマップの内容で、まだ読み込んでいない本体を上書きしないため（L-002）。
  - 保存待ちのタイマーを取り消す。
  - 最新の `currentSnapshot` が最後に保存した内容と異なる、または強制保存の要求が残っている場合だけ `writeBody` を同期で呼ぶ。成功したら最後に保存した内容を更新して `saved`、失敗したら `failed`、`inactive` なら `unchanged` を返す。
  - 失敗したときは、タイマー経由の自動保存の失敗と同じ通知（`autoSaveFailedNotice()`）をエディタの操作通知バーにも出す。`publishNotice` は ref で持ち、`flushPendingSave` の参照を変えない。ダイアログ内の通知は閉じると消え、取り消したタイマーは次の変更まで張り直さないため、エディタにも出さないと未保存であることが画面に残らない（ローカルレビュー第1周の指摘2で追加）。
  - 最新の `currentSnapshot` は `useLayoutEffect` で同期する ref から読む（レンダー中に ref を書かない。L-521）。
- エディタは `useLayoutEffect` で `registerFlush(flushPendingSave)` を呼び、cleanup で登録を外す。シェルは「登録したセッション番号」と組で持ち、現在のセッション番号の登録だけを呼ぶ。登録が無ければ `unchanged` として扱う。
- アンマウントでは、今と同じく保存待ちのタイマーを破棄するだけで、書き込まない（既存のテストで固定している挙動を保つ）。再マウントを伴う操作は、シェルが事前に flush する。

### 切り替え・新規作成・削除のときの順序

- 切り替え・新規作成: flush を呼び、`failed` なら操作を中止して error を通知する（ダイアログ内。エディタの操作通知バーには flush 自体が自動保存の失敗の通知を出す）。ダイアログは開いたままにし、フォーカスも動かさない（利用者が不要なマップを削除できるようにする）。`saved` か `unchanged` なら次へ進む。
- 開いているマップの削除: flush しない。保存待ちは削除するマップの内容なので捨てる。インデックスの書き込みが成功してからセッション番号を進めるため、旧エディタの保存待ちは書かれない。
- 開いていない別のマップの削除: 削除の前には flush しない（再マウントしないため、保存待ちはそのまま残る）。削除が成功した後に flush を呼び、容量不足で失敗していた保存待ちを、空いた容量へ書き込み直す。`failed` なら自動保存の失敗と同じ文言でダイアログ内に通知する（エディタの操作通知バーにも flush 自体が同じ通知を出す）。`saved` なら、エディタの通知欄に残っている自動保存の失敗の通知（「ブラウザへ自動保存できませんでした。…」）を消す。消すのは、エディタの現在の通知がその保存失敗の通知である場合だけで、ほかの通知（JSON の読み込みの結果など）は消さない。そのため `useMapStorageAutoSave` は必須の引数 `clearSaveFailureNotice: () => void` を受け取り、`flushPendingSave` が `saved` を返すときに呼ぶ。`useMapPersistence` は、関数形式の state 更新で「現在の通知が保存失敗の通知なら `null` にする」関数を渡す（L-453）。
- 名前変更: flush しない。

## 切り替え

### 再マウントで破棄されるもの

`MapEditor` は `key={mapId}` で描画するため、`mapId` が変わるとエディタ以下のすべての状態とフックが破棄され、新しいマップで作り直される。

- `useNodes` の状態（ノード、選択、配置モード、ID の割り当て）と、編集履歴（Undo/Redo）。履歴は保存しないので、切り替えた後は Undo/Redo が無効になり、前のマップの操作を取り消すことはできない。
- `documentRevision` と `resetRevision`。新しいエディタではどちらも 0 から始まる。
- ビューポート、解像度フィルター（auto に戻る）、折りたたみ、検索クエリと検索の移動要求、ノードのメニュー、編集中のラベル、ジェスチャー。
- エディタ内の通知（`persistence.notice`、`imageExport.notice`、複製・クリップボード・検索の通知、自動配置の失敗表示）。今は revision でリセットされない `persistence.notice` と `imageExport.notice` も、再マウントで消える。
- 自動保存の保存待ち（タイマー）。シェルが事前に flush する（開いているマップの削除を除く）。
- イラスト生成。既存のアンマウント時の `abort` で止まる。

### 既存の documentRevision 系の仕組みとの関係

- `documentRevision` と `resetRevision` は、1つのエディタの中で文書が入れ替わったこと（JSON 読み込み、Undo/Redo）を表す仕組みとして、今のまま使う。マップの切り替えでは revision を上げない。エディタごと作り直すため、revision で守る必要がない。
- 注意点: 新しいエディタの revision は 0 から始まるため、旧エディタの revision の値と一致することがある。エディタの外へ結果を出す処理（保存、ダウンロード、シェルへの通知）を revision の値やマップ id の値で照合してはいけない。セッション番号（保存）とアンマウントの判定（非同期処理）で照合する（L-588 の世代の考え方を、エディタの単位に広げる）。
- エディタの中で閉じた非同期処理（`setState` だけを呼ぶもの）は、アンマウント後の `setState` が無視されるため、追加の対応は要らない。

### 非同期処理の扱い

| 処理 | 切り替えの後に結果が出たとき |
| :--- | :--- |
| 自動保存のタイマー | アンマウントで取り消す。書き込みは `writeBody` のセッション照合でも拒否される |
| JSON 読み込み（ファイルの読み取り中） | 結果を捨てる。`useMapJsonImport` にアンマウントの印を追加し、`await` の後で印を確かめて、`replaceMap`・`requestSnapshotSave`・通知を呼ばない |
| PNG 書き出し（ラスタライズ中） | 結果を捨てる。`useMapPngExport` にアンマウントの印を追加し、`await` の後で印を確かめて、ダウンロードと通知をしない。実行中の印（`isExportingPng`）はエディタと一緒に消える |
| SVG 書き出し | 同期処理なので影響なし |
| イラスト生成 | 既存のアンマウント時の `abort` で止まり、新しいマップに付かない |
| クリップボードの貼り付け | エディタの中の `setState` だけなので、アンマウント後は無視される |

アンマウントの印は、effect の中で `true` にし、cleanup で `false` に戻す（StrictMode の二重実行で印が `false` のまま残らないようにする。L-469）。

### 再読み込み後

- 再読み込みすると、インデックスの `currentMapId` のマップを開く。切り替えでインデックスを書くため、最後に開いていたマップが開く。

- `AppHeader` に必須の `mapControls` を追加し、`h1`「Draw My Map」の直後に置く。ヘッダーは今の `flex-wrap` のまま折り返す。

### 入力の規則

- 名前の正規化 `normalizeMapName(input)`:
  1. 制御文字（U+0000〜U+001F、U+007F）を半角空白に置き換える。
  2. 前後の空白（`String.prototype.trim` の対象）を除く。
  3. 空なら「無題のマップ」にする。
- 書式文字（U+200B などのゼロ幅文字）は、前後の空白として除く対象に含めない。
- 長さはコードポイント数（`Array.from(name).length`）で数え、上限は50。上限を超えたら確定せず、入力欄の下に「マップ名は50文字以内で入力してください。（現在 N 文字）」を `role="alert"` で表示し、入力欄に `aria-invalid="true"` と `aria-describedby` を付ける（L-057）。黙って切り詰めない。入力欄の `maxLength` 属性は UTF-16 の単位で数えるため使わない。
- 名前の重複は許可する。重複していても警告しない（一覧の更新日時と並び順で見分ける。1分以内に作った同名のマップは並び順だけで見分ける）。
- 名前変更で、正規化した結果が今の名前と同じなら、インデックスを書かずに一覧へ戻る。
- 入力欄の Enter は `<form>` の送信で扱い、IME の変換中（`isComposing` または `keyCode === 229`）の Enter と、押し続け（`event.repeat`）の Enter では送信しない（L-474・L-408）。確定は送信の1か所だけで行い、`blur` では確定しない（L-473）。
- 確定の処理（flush とインデックスの書き込み）は同期で終わるため、送信中の状態や二重送信の防止の印は持たない。確定のボタンも無効にしない（無効にするとフォーカスが落ちるため。L-157）。成功すると画面が変わるかダイアログが閉じるので、同じ確定が2回走ることはない。失敗した場合は画面とフォーカスをそのまま残し、もう一度確定して再試行できる。

### キーボード操作とフォーカス

- ダイアログは `role="dialog"`、`aria-modal="true"`、画面によらない固定の名前 `aria-label="マップの管理"`。ダイアログの要素は画面が変わっても作り直さないので、スクリーンリーダーは、同じダイアログの中でフォーカスが動いただけでは、変わった名前や説明を読み直さない。
- そのため、各画面（一覧・新規作成・名前変更・削除の確認）の中身を `role="group"` の要素で包み、`aria-labelledby` でその画面の見出しを指す。削除の確認では、group の `aria-describedby` で本文（元に戻せないこと、次に開くマップ）を指す。group は画面（と対象のマップ）ごとに key を変えて作り直すので、画面が切り替わって既定のフォーカス先へ移ると、新しい group に入ったときに group の名前と説明が読まれる。
- 名前と説明は group だけに持たせ、ダイアログの要素には `aria-labelledby`・`aria-describedby` を付けない。開いたときに見出しや本文が二度読まれないようにするため（ローカルレビュー第4周の指摘1で変更）。
- ダイアログを開いている間は、エディタ全体（`MapEditor` の根）に `inert` を付ける。キャンバス、ヘッダーのほかのボタンへフォーカスやクリックが届かないようにする。
- ダイアログを開いている間は、エディタのショートカットを処理する側で止める。シェルが `MapEditor` へ必須の props `shortcutsEnabled`（ダイアログを開いている間は `false`）を渡し、window に登録している次のフックへ必須の引数 `enabled` として渡す。`enabled` が `false` のとき、各フックのハンドラは何もせずに戻る（`preventDefault` もしない）。
  - 対象: `useMapHistoryShortcuts`（Undo/Redo）、`useNodeKeyboardShortcuts`（ノードの追加・削除など）、`useMapViewportShortcut`（`F`）、`useMapClipboardEvents`（枝のコピー・貼り付け）、`useNodeContextMenuDismissal`（メニューを閉じる）。
  - フォーカスがダイアログの外（body など）に落ちた場合でもショートカットが動かないよう、イベントの伝播を止める方式は使わない。
  - 登録は今までどおり1回にし、`enabled` は `useLayoutEffect` で同期する ref から読む（L-521）。
  - 入力欄の中の通常の文字操作（コピー・貼り付け・取り消し）は、ブラウザの既定の動作のまま妨げない。
  - テストは、各フックについて `enabled: false` で何も起きないこと、`Home` の結合テストでダイアログを開いている間に body へフォーカスを置いて Ctrl/Cmd+Z・Delete・`F`・コピーを送ってもマップが変わらないことを確かめる（L-173）。
- ダイアログを開いている間、フォーカスをダイアログの中に保つ（L-159）。
  - ダイアログの要素に `tabIndex={-1}` を付け、ダイアログの中の余白を押したときにフォーカスを `body` へ落とさずダイアログ自身で受け止める（Tab で巡る対象には含めず、ダイアログ自身から Tab なら先頭、Shift+Tab なら末尾へ移る）。
  - オーバーレイ（ダイアログの外側の背景）の `pointerdown` では `preventDefault` してフォーカスの移動を止め、ダイアログの中で最後にフォーカスがあった要素（無ければ、その画面の最初のフォーカス先）へフォーカスを戻す。
  - `document` の `focusin` を購読し、フォーカスがダイアログの外へ出たら、同じ規則でダイアログの中へ戻す。購読は開いている間だけ行い、閉じたら解除する。
  - Escape は window の `keydown`（capture）で受ける。フォーカスがどこにあっても、開いている間は下の Escape の規則で処理する。
- Tab と Shift+Tab はダイアログの中で循環させる。無効なボタンは除いて毎回数え直す（L-159）。
- 開いたときの最初のフォーカス:
  - 一覧: 開いているマップの「開く」ボタン。
  - 新規作成・名前変更: 入力欄。
  - 削除の確認: 「キャンセル」ボタン（取り消せない操作なので、既定を安全側にする）。
  - フォーカスは、画面が描画された後に `useLayoutEffect` で当てる。`autoFocus` は使わない（L-584）。
- Escape:
  - IME の変換中は何もしない。
  - 新規作成・名前変更・削除の確認の画面で押したら、その画面を開いた元へ戻る。一覧から開いたなら一覧へ戻り、ヘッダーの「新しいマップ」から開いたならダイアログを閉じる。
  - 一覧で押したらダイアログを閉じる。
  - 「キャンセル」ボタンも Escape と同じ動きにする。
- 背景（オーバーレイ）のクリックではダイアログを閉じない。入力欄からのドラッグで閉じる事故を避けるため（L-158）。
- 削除の確認の「このマップを削除」ボタンは、`keydown` の `event.repeat` の Enter・Space を `preventDefault` し、`click` の `event.detail > 1` を無視する。一覧の「削除」ボタンを押し続けたりダブルクリックしたりした入力が、確認を飛ばさないようにする（L-408）。
- フォーカスの戻し先（L-155、L-584）:

| 終わり方 | フォーカスの行き先 |
| :--- | :--- |
| 一覧を閉じる（Escape、「閉じる」、開いているマップの「開く」） | ダイアログを開いたヘッダーのボタン |
| ヘッダーの「新しいマップ」から開いた新規作成を、キャンセルまたは Escape で閉じる | ヘッダーの「新しいマップ」ボタン |
| 新規作成・名前変更・削除の画面から一覧へ戻る（キャンセル） | その画面を開いた一覧のボタン（新規作成は一覧の「新しいマップ」、名前変更・削除はその行の同じボタン） |
| 名前変更の成功 | 一覧の、その行の「名前を変更」ボタン |
| 開いていない別のマップの削除の成功 | 一覧の、削除した行の次の行の「開く」ボタン。次の行が無ければ前の行、どちらも無ければ一覧の「新しいマップ」 |
| 切り替え・新規作成・開いているマップの削除の成功（再マウントを伴う） | ダイアログを閉じ、再マウントした新しいヘッダーの「マップ一覧」ボタン |
| 操作の失敗（flush やインデックスの書き込みの失敗） | 画面とフォーカスを変えない |

- 一覧の行のボタンは要素の参照ではなく、`data-map-id` と役割の属性で探してフォーカスする。再描画や行の削除で要素が差し替わっても、戻し先を見失わないようにする。
- 再マウントを伴う場合は、シェルが「フォーカスを戻す要求」を状態として持ち、新しいヘッダーの「マップ一覧」ボタンの `ref` がつながった後のシェルの `useLayoutEffect` でフォーカスする。要求は1回使ったら消す。
- ダイアログのボタンや入力欄は、既存のヘッダーのボタンと同じフォーカスリングを表示する（`outline` を消さない）。

### 見た目

- ダイアログは画面中央、最大幅 `28rem`、余白付き。背景は半透明の黒。ライト・ダーク両方のテーマで、既存のヘッダーと同じ配色の考え方にする。
- 一覧が長い場合は、ダイアログの中の一覧だけを縦にスクロールさせる（最大高さは画面の高さの 60% 程度）。
- 幅 375px でもダイアログが画面内に収まり、ページが横にスクロールしない。長い名前は一覧では折り返して全文を表示する。

## JSON と画像の書き出し

- JSON の内容は今のまま（V3、マップ名を含めない）。JSON の読み込みは、今と同じく現在のマップの中身を置き換え、読み込んだ内容を現在のマップの本体へ強制保存する。読み込みで現在のマップの名前は変えない。
- ファイル名は `<安全なマップ名>-YYYYMMDD-HHmmss.<拡張子>` にする（拡張子は `json`、`png`、`svg`）。日時の部分は今の `createMapJsonFileName`・`createMapImageFileName` と同じ。
- `toSafeFileNameBase(name)` を純関数として作り、JSON と画像の両方で使う（L-161。入口ごとに規則がずれないようにする）。
  1. `\ / : * ? " < > |` と制御文字（U+0000〜U+001F、U+007F）を `_` に置き換える。
  2. 連続する空白を半角空白1つにし、前後の空白を除く。
  3. 先頭の `.` と空白、末尾の `.` と空白を除く（隠しファイルや Windows で扱えない名前を避ける）。
  4. Windows の予約名（`CON`、`PRN`、`AUX`、`NUL`、`COM1`〜`COM9`、`LPT1`〜`LPT9`。大文字小文字を区別しない。`CON.txt` のように、予約名に `.` で始まる拡張子が続く場合も含む）と一致したら、先頭に `_` を付ける。
  5. 結果が空なら `draw-my-map` にする。
  - 日本語や絵文字はそのまま残す。名前は50コードポイント以内なので、長さの切り詰めはしない。
- エディタは `mapName` を props で受け取り、書き出しの時点の名前を使う。名前の変更はエディタを再マウントしないので、変更後の書き出しには新しい名前が使われる。

## 通知の文言

通知を出す場所は次の2つに分ける。エディタ内の通知（自動保存の失敗、JSON・画像の書き出しなど）は今までどおりヘッダーの通知欄に出し、再マウントで消える。

- **ダイアログ内の通知**: ダイアログを開いたまま終わる操作の結果（名前変更の成功、開いていないマップの削除の成功、各操作の失敗、削除の後の保存の再試行の失敗）は、ダイアログの中に出す。ダイアログの中に `role="status"` と `role="alert"` の領域を、どの画面でも同じ位置に空のまま常設し、文言だけを差し替える（L-153）。ダイアログを開いている間はエディタが `inert` になり、ヘッダーの通知欄は支援技術から隠れるため、そこには出さない。ダイアログを閉じたら、ダイアログ内の通知は消す。
  - 同じ文言の失敗が続いても読み上げられるよう、ダイアログ内の通知（`useMapLibraryDialogState` の `notices`）は `sequence` を持ち、通知を出すたび（空にするときも）進める。ダイアログ側は、シェルの通知と共通のフック `useReannouncedNotice`（`components/layout/useReannouncedNotice.ts`）で、`sequence` が変わったら同じ `status`・`alert` の要素を一度空にし、次のフレームで文言を入れ直す（L-153・L-166。ローカルレビュー第4周の指摘2で追加）。
- **シェルの通知**（`components/layout/MapLibraryNoticeRegion.tsx`）: ダイアログを閉じて終わる操作の結果（切り替え・新規作成・開いているマップの削除の成功）と、起動時の通知は、シェルが keyed の部分（`MapEditor`）の外に常設するライブリージョンに出す。`role="status"`（status 用）と `role="alert"`（warning・error 用）の要素を最初の描画から空のまま置き、文言だけを差し替える。条件付きで挿入したり、key で作り直したりしない。置き場所はエディタのヘッダーの直前の1行（文言が無いときは高さを持たない）で、ダイアログを開いている間も `inert` にしない。
  - 再マウントでは消えず、次のシェルの通知で置き換わる。同じ文言が続いても読み上げられるよう、置き換えるときは一度空にしてから次のフレームで設定する（L-166）。ダイアログ内の通知と同じフック `useReannouncedNotice` を使う。
  - ダイアログ内の通知とシェルの通知に、同じ結果を重ねて出さない（L-249）。
  - 例外として、flush の失敗では、ダイアログ内の通知に加えて、エディタの操作通知バーにも自動保存の失敗の通知を出す。ダイアログを閉じた後も未保存であることを残すためで、ダイアログを開いている間はエディタが `inert` なので読み上げは重ならない。

| :--- | :--- | :--- |

| 切り替えの成功 | status | マップ「<名前>」を開きました。 |

- 名前は通知の中でもそのまま（正規化済み）表示する。

## エラーと境界条件

| 条件 | 扱い |
| :--- | :--- |
| 容量超過（`QuotaExceededError`） | 自動保存は既存どおり通知して、次の変更で再試行。flush の失敗は切り替え・新規作成を中止。削除はインデックスが小さくなるため通常は成功し、その後に保存待ちを書き直す。複数マップで約5MBを共有する |
| インデックスが JSON として読めない・形が違う | 「インデックスの破損」の手順 |
| インデックスの一部の項目が不正 | その項目だけを除外。本体は孤立した本体として残る |
| id の重複 | 最初の項目だけを残す |
| 有効な項目が0件 | 破損として扱う |
| 現在の id が一覧に無い | 表示順の先頭のマップを開く。次にインデックスを書くときに直す |
| 本体が無い | 空のマップとして開く（通知なし） |
| 本体が壊れている | 既存の復元と同じく、warning を出して空のマップで開く。本体は利用者が編集するまで上書きしない（flush も、復元の失敗後は変更が無ければ書かない） |
| 孤立した本体 | 無視する。自動では消さない |
| 空の名前・空白だけの名前 | 「無題のマップ」 |
| 50コードポイントを超える名前 | ダイアログでエラーを表示し、確定しない。インデックスに上限を超える名前があった場合は、読み込み時に先頭50コードポイントへ切り詰める |
| 改行・タブなどを含む名前 | 半角空白に置き換える |
| 同じ名前 | 許可 |
| 開いているマップを開く | 何もせずダイアログを閉じる |
| 切り替え中の連打・押し続け | 操作は同期で完了し、ダイアログが閉じる。ヘッダーのボタンと入力欄の `repeat` の Enter は無視する。ダブルクリックの2回目は閉じた後のキャンバスへ届くので、ダイアログの中のマウスのクリック（`detail > 0`）の時刻をシェルが控え、`MapStage` はその 500ms 以内の `dblclick` を無視する（ノードの追加・ラベル編集を始めない。コンテキストメニューの項目と同じ判定。L-150・L-408） |
| ダイアログの表示中に、エディタの非同期処理が通知を出す | エディタの通知欄に今までどおり表示する（ダイアログは閉じない） |
| localStorage を使えない | 保護モード |
| 他タブとの同時編集 | 対象外。各タブはメモリ上のインデックスを基準に丸ごと書くため、最後に書いた側のインデックスが残る。もう一方のタブで作ったマップの項目が消え、本体が孤立する場合がある。この方針を features.md に明記する |

## 受け入れ基準

1. 旧キーだけがある状態で起動すると、内容がそのまま「無題のマップ」として表示され、インデックスと本体ができる。旧キーはその起動では残り、次の起動で消える。旧キーが壊れていれば、旧キーを残したまま空の「無題のマップ」で始まり、warning が出る。
2. 「新しいマップ」で名前を付けて作ると、空のマップに切り替わり、ヘッダーに名前が出る。空欄なら「無題のマップ」。51文字ではエラーが出て作成されない。同じ名前のマップを2つ作れる。
3. 一覧から別のマップを開くと、そのマップの内容が表示される。切り替えの直前（300ms 以内）の変更も、元のマップに保存されている。切り替えた後に Undo しても、前のマップの操作は戻らない。検索クエリ、折りたたみ、ビューポート、解像度フィルターは初期状態に戻る。
4. マップ A でノードを編集してから B に切り替え、B を編集して A に戻すと、A と B の内容はそれぞれの編集だけを含む。
5. 名前を変更すると、ヘッダーと一覧に反映され、再読み込み後も残る。内容と更新日時は変わらない。
6. 開いていないマップを削除すると、一覧から消え、開いているマップはそのまま。開いているマップを削除すると、最後に更新した別のマップが開く。最後の1つを削除すると、空の「無題のマップ」が作られて開く。どの場合も確認ダイアログでキャンセルすれば何も変わらない。
7. 自動保存に失敗する状態（容量超過）では、切り替えと新規作成が中止され、error が通知され、現在のマップは開いたまま。別のマップを削除すると、保存待ちが書き込まれる。
8. 切り替える直前に始めた PNG 書き出しと JSON 読み込みは、切り替えの後に結果が出ても、ダウンロード・読み込み・通知を行わない。生成中のイラストは新しいマップに付かない。
9. JSON の書き出しは V3 のままで、ファイル名は `<マップ名>-YYYYMMDD-HHmmss.json`。PNG と SVG も同じ規則。ファイル名に使えない文字は `_` になる。JSON の読み込みは現在のマップの中身だけを置き換え、名前は変わらない。
10. 再読み込みすると、最後に開いていたマップが開く。
11. ダイアログはキーボードだけで操作でき、Escape・Tab の循環・フォーカスの戻し先が「UI」の節のとおりに動く。ダイアログの表示中は、キャンバスとエディタのショートカットが動かない。
12. インデックスが壊れていると、壊れた内容が退避キーに残り、保存済みの本体から「復元したマップ N」として一覧が作り直される。
13. `npm run verify` が成功する。`docs/specifications/data-model.md`（5章）、`docs/specifications/features.md`（1.2、6.1、6.2、6.3、8.2、11.4 と、新しい「複数マップ」の節）、`docs/testing/browser-test-cases.md`、`ROADMAP.md` が実装に合っている。
